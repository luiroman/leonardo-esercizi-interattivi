📚 Esercizi Aula G5

Zero Trust, microsegmentazione e identità · 10 esercizi · ~50 minuti

Modalità di lavoro: esercizi da svolgere in aula in coppie. Discussione plenaria dopo ogni categoria. Le soluzioni sono nascoste — apritele solo dopo aver provato.
Categoria A · Modello castello-fossato e suoi limiti
ESERCIZIO 1

Identifica l'assunto implicito

In un'azienda con firewall perimetrale + VLAN per reparto, un dipendente del marketing apre un allegato malevolo. Il malware ottiene credenziali di un account di sviluppo trovate in cache browser e accede al server Git interno.

Domanda: quale assunto del modello castello-fossato ha permesso l'attacco?

Mostra soluzione
L'assunto implicito è che tutto ciò che si trova all'interno del perimetro è fidato. Una volta che il malware è "dentro", il firewall perimetrale non ispeziona più il traffico est-ovest. Il server Git si fida di chiunque abbia credenziali valide, indipendentemente dal contesto (dispositivo compromesso, comportamento anomalo). Zero Trust avrebbe richiesto verifica continua: device posture, MFA per accesso a Git, micropolicy che limitano marketing → Git.
ESERCIZIO 2

Lateral movement: trova i salti

In una rete con 4 VLAN (Uffici, Sviluppo, Produzione, DMZ), un attaccante atterra su un PC della VLAN Uffici tramite phishing. L'obiettivo finale è il database in Produzione.

Domanda: elenca 3 possibili percorsi di lateral movement, considerando che le VLAN sono separate da firewall ma con regole "permissive" tra Uffici e Sviluppo per comodità degli sviluppatori.

Mostra soluzione
Tre percorsi tipici:
1. Uffici → Sviluppo via SMB: la regola permissiva permette accesso a file share di Sviluppo, dove trova credenziali in script o file di configurazione.
2. Uffici → AD → Sviluppo: compromissione di un account AD via Pass-the-Hash, escalation a service account che ha accessi anche a Sviluppo.
3. Uffici → Sviluppo → Produzione via deploy pipeline: trova credenziali della pipeline CI/CD che ha permessi su Produzione per i deploy.
ESERCIZIO 3

Il perimetro è scomparso?

Elenca 5 scenari concreti, presi dalla tua esperienza di stage o studio, in cui il modello "tutto dentro è fidato, tutto fuori è ostile" non si applica più.

Mostra esempi tipici
• Smart working: dipendente accede da rete domestica non controllata.
• SaaS aziendali (M365, Slack): dati aziendali vivono fuori dal perimetro per design.
• BYOD: dispositivo personale non gestito accede a dati aziendali.
• Cloud workload: VM su Azure parla con servizi on-prem via VPN - "dentro" o "fuori"?
• API B2B: fornitori esterni chiamano API aziendali con autenticazione, sono dentro o fuori?
• Microservizi cross-cloud: due servizi della stessa app girano su cloud diversi.
Categoria B · Zero Trust e tenet NIST
ESERCIZIO 4

Mappa il tenet

Per ognuna delle seguenti misure di sicurezza, indica quale dei 7 tenet NIST SP 800-207 implementa:

  • A. MFA obbligatorio per ogni accesso ad applicazioni aziendali
  • B. Conditional Access che blocca login da paesi non autorizzati
  • C. Sessioni di VPN che scadono dopo 1 ora indipendentemente dall'attività
  • D. Tutte le comunicazioni interne cifrate via mTLS
  • E. Endpoint Detection and Response (EDR) su tutti i dispositivi
Mostra soluzione
A → Tenet 6 (autenticazione dinamica prima dell'accesso).
B → Tenet 4 (policy dinamica basata su contesto).
C → Tenet 3 (accesso per-sessione, non permanente).
D → Tenet 2 (comunicazioni protette indipendentemente dalla rete).
E → Tenet 5 (monitoring continuo della postura) e Tenet 7 (telemetria continua).
ESERCIZIO 5

ZTNA o VPN?

Per ognuno di questi scenari indica se è meglio una VPN tradizionale o una soluzione ZTNA, e spiega perché:

  • A. Un consulente esterno deve accedere SOLO a un'applicazione web interna per 2 settimane
  • B. Sviluppatori che devono accedere a server di sviluppo on-prem via SSH
  • C. Dipendenti che lavorano da casa e devono accedere a M365, Salesforce e GitHub
Mostra soluzione
A → ZTNA. Granularità: una sola app, nessun accesso al resto della rete. Provisioning rapido, deprovisioning automatico a scadenza.
B → Dipende. Se il numero di server è limitato e ben definito, ZTNA. Se è un ambiente esplorativo con molti host effimeri, VPN tradizionale + bastion host può essere più pragmatico.
C → Né uno né l'altro. M365/Salesforce/GitHub sono SaaS già accessibili da Internet. Serve un IdP federato (Entra ID, Okta) con SSO + MFA + Conditional Access. La VPN sarebbe inutile o dannosa.
Categoria C · Microsegmentazione cloud-first
ESERCIZIO 6

Macro vs micro

Distingui macrosegmentazione e microsegmentazione in ognuno di questi esempi:

  • A. "La VLAN Uffici non può raggiungere la VLAN Produzione"
  • B. "Il workload con tag web-frontend può parlare con il workload con tag api-backend sulla porta 8080"
  • C. "Il subnet 10.10.20.0/24 è isolato dal resto della VPC"
  • D. "Il pod Kubernetes con label app=checkout può chiamare solo il servizio payments"
Mostra soluzione
A → Macro (segmentazione per rete).
B → Micro (segmentazione per identità del workload).
C → Macro (segmentazione per subnet).
D → Micro (segmentazione per identità del pod via label).

Il discriminante: la policy si riferisce a una RETE (macro) o a un'IDENTITÀ DI WORKLOAD (micro)?
ESERCIZIO 7

AWS Security Group · scrivi le regole

Hai 3 EC2: web-1 (Apache, porta 80/443), app-1 (porta 8080), db-1 (PostgreSQL, porta 5432). Devi configurare i Security Group rispettando default deny.

Compito: scrivi i 3 Security Group con le regole inbound minime, usando riferimenti a SG-ID.

Mostra soluzione
SG: sg-web
Inbound: 80/tcp from 0.0.0.0/0; 443/tcp from 0.0.0.0/0

SG: sg-app
Inbound: 8080/tcp from sg-web

SG: sg-db
Inbound: 5432/tcp from sg-app

Note: nessun riferimento a IP. SSH per amministrazione → bastion host con SG dedicato. Outbound: lasciare open o restringere a destinazioni specifiche (es. yum/apt repo, monitoring).
ESERCIZIO 8

Trova l'errore

Un collega ti mostra una regola Security Group:

Inbound: 0-65535/tcp from 0.0.0.0/0

Lui dice: "è solo temporanea, mi serve per debug stamattina, poi la tolgo". Cosa rispondi?

Mostra risposta tipica
Tre cose da dire:
1. "Temporanee" diventano permanenti: è un anti-pattern documentato, il rischio è che venga dimenticata.
2. Apre TUTTE le porte da TUTTO Internet: equivale a disabilitare il firewall sull'istanza. Per debug bastava aprire la porta specifica dal tuo IP.
3. Alternative pulite: SSM Session Manager (no porte aperte), bastion host, o regola limitata al singolo IP del collega con scadenza esplicita (Lambda di cleanup).
ESERCIZIO 9

Tradurre tra cloud

Hai questa policy concettuale: "Il backend può chiamare il database, nessun altro".

Compito: spiega come la implementi su AWS, Azure e GCP, indicando i costrutti specifici.

Mostra soluzione
AWS: SG sg-db con inbound 5432/tcp from sg-backend. Nessun altro SG referenziato.

Azure: ASG asg-backend e asg-db. NSG con regola Allow 5432 from asg-backend to asg-db, e regola Deny 5432 from * to asg-db a priorità inferiore.

GCP: network tag backend e db. Firewall rule allow-backend-to-db con direction INGRESS, source-tags=backend, target-tags=db, allow tcp:5432.

Tre sintassi diverse, stesso modello mentale: identità → identità, non IP → IP.
ESERCIZIO 10

Progettazione completa · 3-tier

Sei l'architetto di sicurezza per una nuova app web e-commerce su AWS. Componenti:

  • 2 web frontend (Nginx, dietro ALB)
  • 3 API backend (Node.js, porta 3000)
  • 1 database PostgreSQL (RDS, porta 5432)
  • 1 cache Redis (ElastiCache, porta 6379)
  • 1 bastion host per amministrazione SSH

Compito: disegna l'elenco completo dei Security Group e per ognuno specifica le regole inbound minime. Considera sia il traffico applicativo sia l'amministrazione.

Mostra soluzione
sg-alb: inbound 80,443/tcp from 0.0.0.0/0
sg-web: inbound 80/tcp from sg-alb
sg-api: inbound 3000/tcp from sg-web
sg-db: inbound 5432/tcp from sg-api
sg-cache: inbound 6379/tcp from sg-api
sg-bastion: inbound 22/tcp from <IP-aziendali>
sg-admin-target (assegnato a tutte le istanze): inbound 22/tcp from sg-bastion

Note: l'admin è separato dal flusso applicativo. Nessuna regola fa riferimento a IP delle istanze, solo a SG. Outbound: restringere a destinazioni necessarie (yum, monitoring, patch). Default deny implicito su tutto il resto.
