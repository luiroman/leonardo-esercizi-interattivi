1 · Hypervisor: virtualizzazione full-stack

Un hypervisor è uno strato software — in alcuni casi firmware — che astrae l'hardware fisico e permette di eseguire più sistemi operativi completi (guest) sulla stessa macchina fisica (host), in isolamento reciproco. La virtualizzazione moderna nasce negli anni '60 sui mainframe IBM (VM/370) e riemerge sui server x86 intorno al 2001 con VMware ESX. L'accelerazione decisiva arriva nel 2005-2006 con le estensioni hardware Intel VT-x e AMD-V, che rendono la virtualizzazione efficiente e sicura a livello CPU.

Le tre proprietà chiave di un hypervisor sono isolation, resource pooling e portability. Isolation significa che ogni VM ha kernel, memoria e device virtuali propri: un crash o una compromissione in una VM non tocca le altre. Resource pooling significa che l'hypervisor è lo scheduler che divide CPU, RAM, storage e rete fisici tra le VM. Portability significa che una VM è un file — un'immagine di disco virtuale con metadata — e quindi può essere copiata, clonata, migrata tra server diversi in secondi.

Queste tre proprietà sono le fondamenta del cloud computing. AWS EC2, Azure VM, Google Compute Engine sono tutti hypervisor gestiti. Le hyperscale company usano hypervisor custom derivati da KVM o Xen (AWS Nitro, Google KVM+gVisor). Senza virtualizzazione, il cloud come lo conosciamo non esisterebbe: non si può affittare un server fisico al minuto.

Concretamente: su un server fisico con 32 core e 256 GB RAM, un hypervisor può eseguire 20 VM con OS diversi (alcune Linux, alcune Windows, una con database, una con web server). Ogni VM crede di avere il proprio hardware dedicato. Senza virtualizzazione avreste un server che gira al 10% di utilizzo medio; con la virtualizzazione arrivate al 70-80%.

2 · Type 1 vs Type 2: dove gira l'hypervisor

Questa è LA distinzione da ricordare per il resto della carriera. Gli hypervisor si classificano in due famiglie in base a dove girano rispetto all'hardware.

Type 1 (bare-metal): gira direttamente sull'hardware, senza OS sottostante. L'hypervisor è l'operating system del server. Lo stack è: hardware → hypervisor → VM guest. Esempi: VMware ESXi, Microsoft Hyper-V Server, KVM, Xen, Proxmox. Vantaggi: performance vicina al bare-metal (nessuno strato OS in mezzo), attack surface minima (solo l'hypervisor, niente kernel generalista), isolamento forte. È la scelta standard per datacenter e cloud.

Type 2 (hosted): gira come applicazione sopra un OS normale. Lo stack è: hardware → host OS → hypervisor → VM guest. Esempi: VirtualBox (Oracle, gratuito), VMware Workstation/Fusion, Parallels, UTM. Vantaggi: facile da installare sul portatile, ideale per lab e sviluppo. Svantaggi: più overhead (due layer di OS), attack surface maggiore (anche il kernel host è bersaglio).

CriterioType 1 (bare-metal)Type 2 (hosted)
PerformanceVicina al bare-metalOverhead host OS
IsolamentoForte (attack surface minima)Media (host OS mediate)
Uso tipicoDatacenter, cloudSviluppo, lab, desktop
EsempiESXi, KVM, Hyper-V, XenVirtualBox, VMware WS, Parallels
Nota sulle linee sfumate. KVM è tecnicamente un modulo del kernel Linux, che funge da type 1 "quasi": il Linux sottostante è minimale e riduce l'attack surface. AWS è passato da Xen classico (type 1) a Nitro (custom, basato su KVM). La distinzione type 1/type 2 resta utile come modello mentale anche quando la realtà è più sfumata.

Regola pratica: produzione → type 1; lab e sviluppo → type 2. Il lab del corso gira su VirtualBox perché deve essere eseguibile sul portatile di ciascuno.

3 · Virtualizzazione enterprise e rischi di sicurezza

Dove trovate la virtualizzazione in produzione:

  • Cloud provider: AWS, Azure, GCP — tutto EC2/VM è virtualizzato. Nitro (AWS) usa KVM custom.
  • On-prem enterprise: VMware vSphere resta il leader storico, Hyper-V domina negli ecosistemi Microsoft, Proxmox (FOSS basato su KVM+LXC) è il più interessante emergente.
  • Telco / ISP: NFV (Network Function Virtualization). Firewall, router, EPC virtualizzati invece di scatole hardware dedicate.
  • Sviluppo: VirtualBox/Workstation per lab locali, pipeline CI/CD con VM spin-up/tear-down.
Rischi di sicurezza noti:
  • Hypervisor escape: VENOM (CVE-2015-3456) permetteva di evadere da VM a host via QEMU floppy driver. CVE-2022-31705 su VMware ESXi era un heap overflow nel device USB.
  • Side-channel attack: Spectre/Meltdown/L1TF sfruttano la cache CPU condivisa tra VM per leakage di dati cross-tenant.
  • VM snapshot leak: se gli snapshot/backup non sono cifrati, un attaccante che li ruba ha i dati in chiaro.
  • Config errate: shared folder host-guest aperte in produzione, snapshot illimitati che consumano disco.
Mitigazioni standard: patching hypervisor tempestivo, rimozione di device virtuali non necessari (floppy, USB), segmentazione VM per trust zone (produzione vs DMZ vs dev), encryption at rest dei disk image e snapshot.

4 · Container: virtualizzare l'OS invece dell'hardware

Il container è un processo come tutti gli altri, con l'aggiunta di due caratteristiche kernel-level: namespaces per l'isolamento e cgroups per i limiti di risorse. Non c'è un kernel guest, non c'è un hypervisor: il container condivide il kernel dell'host. Questa è la differenza architetturale fondamentale con le VM.

Le conseguenze sono:

  • Peso delle immagini: MB invece di GB (l'immagine contiene solo userland, non il kernel)
  • Tempo di avvio: millisecondi invece di secondi/minuti
  • Densità: centinaia di container per host vs decine di VM
  • Uniformità host-guest: un container Linux richiede kernel Linux host; non si esegue un container Windows su un host Linux e viceversa
  • Isolamento: weak-to-medium invece di strong. Un bug del kernel impatta tutti i container che girano su quel kernel.
Il trade-off principale tra VM e container è isolamento vs efficienza. Le VM hanno isolamento forte perché attraversare l'hypervisor è molto difficile. I container condividono il kernel: se il kernel ha un bug, tutti i container sono vulnerabili. Per workload ad alta sicurezza esistono soluzioni ibride: Kata Containers (container in microVM leggere), gVisor (sandbox userland che intercetta syscall), Firecracker (microVM di AWS usata per Lambda/Fargate). Sacrificano un po' di densità per isolamento forte.

5 · Linux namespaces: i 7 isolamenti

Quando un processo viene lanciato in un namespace, il kernel gli dà una vista separata di una specifica risorsa. Combinando le 7 viste separate si ottiene quello che dall'esterno sembra una macchina isolata, ma internamente è solo un processo.

NamespaceIsolaEffetto
PIDProcess IDIl container vede i propri PID da 1 in su. Non vede processi dell'host.
NETNetworkInterfacce, routing, firewall, porte separati. Il container ha il suo eth0.
MNTMountFilesystem separato. Il container ha la sua /, i suoi /usr, /etc.
IPCInter-Process Comm.Shared memory, semafori, message queues isolati. Due container non si parlano via IPC condivisa.
UTSHostnameHostname e domain separati. Ogni container può avere il suo.
USERUser IDRoot nel container può essere mappato a UID 1000 sull'host. Base della sicurezza rootless.
CGROUPControl groupVista limitata della gerarchia cgroup.
I namespaces sono stati introdotti incrementalmente nel kernel Linux: MNT nel 2002 (kernel 2.4.19), UTS e IPC nel 2006, PID nel 2008, NET nel 2009, USER nel 2013 (kernel 3.8), CGROUP nel 2016 (kernel 4.6). L'ordine riflette la difficoltà: user namespace ha richiesto anni di lavoro perché interagisce con tutto (permessi, UID mapping, capabilities). È il più importante per la sicurezza: permette i container rootless, in cui un'evasione dal container lascia l'attaccante come utente normale sull'host anziché root.

L'API di manipolazione è costituita da tre syscall: unshare() (crea un nuovo namespace per il processo chiamante), clone() con flag CLONE_NEW* (crea processo figlio in un nuovo namespace), setns() (unisce un processo a un namespace esistente). I container runtime (runc, crun) orchestrano queste syscall per conto dell'engine (Docker, Podman).

6 · cgroups: limiti e quote di risorse

Se i namespace isolano, i cgroups (control groups v2) limitano. Insieme formano il container Linux completo. I 4 controller principali:

ControllerCosa limitaEsempio Podman
cpuMax % CPU, quote, priorità schedulingpodman run --cpus=1.5 ...
memoryMax RAM, OOM killer, swap limitpodman run -m 512m ...
ioThroughput e IOPS su block device--device-read-bps=/dev/sda:1mb
pidsNumero max di processi (defence vs fork bomb)--pids-limit=100

Senza cgroups, un container malevolo o bacato può consumare tutta la RAM, il disco o la CPU dell'host, abbattendo gli altri container. In produzione i limiti non sono opzionali.

8 · Podman: perché lo preferiamo a Docker Desktop

Podman è un container engine API-compatibile con Docker (i comandi podman run, ps, exec funzionano come Docker) ma con tre differenze architetturali importanti.

1. FOSS, no license. Apache 2.0, nessuna licenza commerciale richiesta in azienda. Docker Desktop dal 2022 richiede licenza a pagamento per aziende >250 dipendenti o >$10M di revenue. Questa è una delle ragioni principali per cui molte organizzazioni sono migrate a Podman.

2. Daemonless. Non c'è un demone root che gira sempre. Podman è una CLI che forka direttamente i container. Semplifica il modello di sicurezza (niente daemon privilegiato, niente attack surface permanente) e il deployment (niente servizio da monitorare).

3. Rootless by default. I container girano come utente normale dell'host. Un'eventuale evasione lascia l'attaccante come utente normale, non root. È una difesa strutturale importante: Docker originariamente richiedeva il daemon root, con tutti i rischi del caso.

Nota. Sul Docker Engine (il motore FOSS, senza la GUI Desktop) continua a essere gratuito su Linux server. La licenza che ha fatto notizia nel 2022 riguarda solo Docker Desktop (la GUI + auxiliary services su Mac/Windows). Su Linux server, Docker Engine e Podman sono entrambe opzioni valide.

Alias comodo per chi viene da Docker: alias docker=podman nel .bashrc. I comandi sono compatibili al 95%.

9 · Pod: container che lavorano insieme

Un pod è un gruppo di container che condividono network namespace e storage. Si vedono su localhost, condividono i volumi. Il concetto nasce da Kubernetes, ma Podman lo supporta nativamente senza richiedere K8s.

Esempio pratico: un pod web-app con 3 container — nginx (reverse proxy sulla 80), node (app su 3000), postgres (DB su 5432). Nginx può parlare con Node su localhost:3000 senza network virtuale, con latenza zero.

Attenzione alla sicurezza. I container di uno stesso pod condividono la rete → se un container è compromesso, può parlare a tutti i servizi degli altri container via localhost. Il pod è ottimo per performance e semplicità, meno per isolamento forte. Per quest'ultimo, usare container separati con network bridge esplicito.

10 · RDBMS vs NoSQL: due famiglie, trade-off diversi

Non esiste un database "migliore": esistono database adatti al caso d'uso. RDBMS (SQL) e NoSQL sono due famiglie con trade-off diversi. Sei dimensioni di confronto:

AspettoRDBMS (PostgreSQL, MySQL)NoSQL (MongoDB, Cassandra, Redis)
SchemaRigido, definito a priori (DDL)Flessibile o schemaless
QuerySQL standard (SELECT, JOIN)API specifiche (find, get, aggregate)
TransazioniACID forte nativoSpesso BASE, eventual consistency
ScalingVerticale tipico (scale-up)Orizzontale nativo (sharding)
Use caseBanking, ERP, CRM, contabilitàCatalog, real-time, IoT, cache, analytics
Maturità40+ anni, battle-tested10-15 anni, evoluzione rapida
La distinzione è meno netta di quanto sembri. I RDBMS moderni (PostgreSQL, MySQL 8) supportano colonne JSON/JSONB con indici GIN: schema rigido con campi flessibili. Molti NoSQL hanno aggiunto transazioni (MongoDB 4.0+, DynamoDB Transactions). PostgreSQL con estensioni come Citus scala orizzontalmente. Il mito "SQL non scala" è datato.

Raccomandazione pragmatica: se dovete scegliere e non avete un motivo specifico per NoSQL, partite da PostgreSQL. Copre il 90% dei casi enterprise, e il costo di cambiare dopo è inferiore al costo di scegliere prematuramente NoSQL senza conoscerne i trade-off.

11 · ACID: le 4 garanzie delle transazioni SQL

ACID è un acronimo coniato da Theo Härder e Andreas Reuter nel 1983. Rappresenta il modello transazionale standard dei RDBMS. Quattro proprietà che rendono affidabili operazioni complesse.

A — Atomicity. Una transazione è indivisibile: o succede tutto, o niente. Esempio classico: bonifico 100€ A→B. Step 1: sottrai 100 da A. Step 2: aggiungi 100 a B. Se tra step 1 e step 2 il server si spegne, con atomicity lo step 1 viene rollback al restart. Senza atomicity, avreste 100€ svaniti. Implementata via WAL (Write-Ahead Log): il DB scrive ogni modifica nel log prima di applicarla, e al restart replay del log dall'ultimo checkpoint.

C — Consistency. Il DB parte in stato valido e resta in stato valido. I constraint dichiarativi (CHECK, UNIQUE, FOREIGN KEY, NOT NULL) sono sempre rispettati. Non potete inserire un ordine con cliente_id che non esiste, non potete avere due utenti con la stessa email se c'è unique constraint.

I — Isolation. Transazioni concorrenti non si vedono tra loro fino al commit. Evita letture sporche, phantom reads, non-repeatable reads. I livelli di isolation standard SQL (ANSI), dal più permissivo al più stretto:

  • READ UNCOMMITTED: legge anche dati non committati. Raramente usato.
  • READ COMMITTED: default PostgreSQL. Vede solo dati committati, ma phantom reads possibili.
  • REPEATABLE READ: rilettura dello stesso dato dà stesso risultato nella transazione.
  • SERIALIZABLE: massimo isolamento, transazioni come se serializzate.

Isolation più alto = più sicurezza, meno concorrenza. Trade-off da scegliere per workload.

D — Durability. Dopo il commit, i dati sono persistiti sul disco. Se il server crasha, al restart i dati committati sono ancora lì. Implementazione: WAL + fsync() al commit. In cloud moderno, durability = replica cross-AZ con quorum writes.

12 · BASE: il modello rilassato dei NoSQL

BASE fu coniato dagli ingegneri di eBay intorno al 2000 (Dan Pritchett, "BASE: An Acid Alternative", 2008). Nome scelto apposta per contrasto chimico con ACID. Significa Basically Available, Soft state, Eventual consistency.

BA — Basically Available. Il sistema è sempre disponibile, anche in modalità degradata. Un guasto di nodo non abbatte l'intero sistema. Quando c'è partizione di rete, il sistema risponde con dati eventualmente vecchi invece di restituire errore.

S — Soft state. Lo stato può cambiare nel tempo senza input esplicito. Tra nodi diversi può essere temporaneamente incoerente. Il TTL delle cache, i compact processes di Cassandra, i merge di CRDT sono esempi di soft state in azione.

E — Eventual consistency. Date sufficienti "tempo e quiete", tutti i nodi convergono allo stesso stato. Non è "mai consistenti", è "consistenti dopo un po'". Il "po'" può essere millisecondi (replica sincrona intra-DC) o ore (replica cross-region).

BASE è la scelta giusta per sistemi distribuiti su larga scala dove la disponibilità è più importante della consistenza immediata: Facebook feed, Amazon carrello, DNS globale, log aggregation. Tutti preferiscono "mostri qualcosa, magari leggermente vecchio" invece di "errore 500".

BASE è la scelta sbagliata per tutto ciò che riguarda soldi, diritti, inventario scarso. Un sistema bancario su BASE sarebbe un disastro: letture diverse darebbero saldi diversi, due prelievi concorrenti potrebbero andare entrambi a buon fine scoprendo il conto.

13 · CAP theorem: scegliere 2 su 3

Teorema di Eric Brewer (2000, dimostrato formalmente da Gilbert e Lynch nel 2002). In un sistema distribuito non si possono avere contemporaneamente:

  • C — Consistency: ogni read vede la scrittura più recente o riceve errore. Tutti i nodi rispondono lo stesso valore.
  • A — Availability: ogni richiesta riceve risposta, non-errore. Anche se alcuni nodi sono giù.
  • P — Partition tolerance: il sistema continua a funzionare anche se la rete tra nodi si spezza.

I tre accoppiamenti possibili:

  • CA (Consistency + Availability, no partition tolerance): sistemi single-node o single-DC senza replica distribuita. Es: PostgreSQL single-instance, MySQL classico.
  • CP (Consistency + Partition tolerance): se c'è partizione, sacrifica availability. Es: MongoDB default, HBase, Redis con sentinel.
  • AP (Availability + Partition tolerance): se c'è partizione, sacrifica consistency. Es: Cassandra, DynamoDB default.
In pratica P è sempre richiesta: le reti cadono, è un fatto. La scelta reale è tra C e A quando c'è una partizione. Sistemi CP: "preferisco non rispondere che rispondere male". Sistemi AP: "preferisco rispondere male che non rispondere".

Brewer stesso nel 2012 ha rivisto la formulazione: CAP non è un'opposizione binaria ma un continuum. Il modello PACELC (Abadi 2010) estende CAP: "if there's a Partition, choose A or C; ELSE (normal operation), choose Latency or Consistency". Più sfumato e aderente alla realtà.

Un DB può essere configurato in modo diverso per workload diversi: PostgreSQL streaming sync è CP, async è AP. DynamoDB offre eventually consistent reads (AP) o strongly consistent reads (CP-like) come scelta runtime.

14 · PostgreSQL: architettura process-per-connection

PostgreSQL ha un'architettura multi-process originale risalente agli anni '80 (università di Berkeley, progetto POSTGRES). Quando un client si connette sulla porta 5432, il daemon postmaster non serve direttamente: forka un processo backend dedicato per quella singola connessione.

Conseguenze pratiche:

  • Isolamento forte tra connessioni: un crash di un backend non tocca gli altri.
  • Memoria per processo intorno a 2-10 MB: 100 client = 1 GB di RAM solo per i backend.
  • Connection pool obbligatorio in produzione: senza, il DB muore con 200-300 connessioni dirette.

Gli strumenti di pool standard:

  • PgBouncer: il più usato, lightweight, 3 modi (session, transaction, statement pooling)
  • Pgpool-II: più feature-complete (load balancing, replication awareness)
  • RDS Proxy (AWS) e pool integrati in Azure Database for PostgreSQL

Componenti chiave in memoria

  • Shared Buffer Pool: cache in memoria condivisa tra backend. Dimensionamento tipico 25% della RAM del server, parametro shared_buffers.
  • Processi ausiliari: autovacuum (pulizia tuple morte), WAL writer, background writer, checkpointer, stats collector, archiver.

Storage su disco

  • WAL (Write-Ahead Log): ogni modifica scritta nel log prima del data file. Durability garantita: se il DB crasha, replay del WAL al restart.
  • Data files: vivono in $PGDATA/base/, ogni database ha una subdirectory, ogni tabella è uno o più file binari.
Il WAL è anche la base di: streaming replication (WAL shipping ai replica), PITR (Point-In-Time Recovery), logical replication (decoding del WAL in eventi logici). Tutto in PostgreSQL ruota intorno al WAL.

15 · PostgreSQL vs MySQL: quando scegliere cosa

I due DB SQL open-source più diffusi. Storicamente MySQL ha dominato il mondo LAMP (Linux-Apache-MySQL-PHP); PostgreSQL il mondo enterprise. Negli ultimi 10 anni PostgreSQL ha guadagnato molto terreno anche su workload generali.

Licenza — dettaglio pratico. La licenza PostgreSQL è permissiva (simil-BSD), totalmente business-friendly. MySQL è dual-licensed: GPL per uso FOSS, proprietaria per uso commerciale con distribuzione closed-source. MariaDB (fork del 2009 da Monty Widenius, creatore originale di MySQL) è GPL puro; nacque in risposta all'acquisizione di MySQL AB da parte di Oracle.

Scelta pratica nel 2026: se dovete scegliere un nuovo DB SQL senza vincoli, PostgreSQL è la scelta dominante per app moderne. MySQL resta rilevante per legacy (WordPress, molti CMS), LAMP, e dove si ha team MySQL-centrico.

16 · Oracle e SQL Server: l'enterprise legacy

Due DB proprietari che incontrerete in azienda nonostante il costo elevato.

Oracle Database

Il più vecchio RDBMS commerciale (1977). Licenza per core, tipicamente 50k€+ per core all'anno. Moltiplicate per 8-16 core per server, per tot server, per tot anni: grandi banche hanno contratti Oracle da milioni l'anno.

Feature enterprise uniche: RAC (Real Application Clusters, shared-storage cluster), Data Guard (replica + disaster recovery), Partitioning, Advanced Compression, Exadata (appliance dedicato). PL/SQL è il linguaggio procedurale, molto potente.

Dove lo trovate: banking (core banking su Oracle Temenos, Finacle), pubblica amministrazione italiana (SIOGGI, INPS, Agenzia Entrate), telco billing.

Migrazione a PostgreSQL è possibile con ora2pg (conversione schema + dati) ma lo sforzo manuale sul PL/SQL è sostanzioso.

Microsoft SQL Server

Nato nel 1989 (inizialmente con Sybase, Microsoft-only dal 1993). Dominante nei segmenti Microsoft-centric. Licenza per core, con Express edition gratuita (limiti di dimensione DB).

T-SQL è il dialetto SQL esteso. Ecosistema BI integrato: SSIS (ETL), SSAS (cubi OLAP), SSRS (reporting), Power BI come front-end. Feature avanzate: Always On Availability Groups (HA), Columnstore (analytics), Query Store (performance tuning).

Dove lo trovate: aziende Microsoft-centric, SharePoint, Dynamics, .NET legacy. Dal 2017 SQL Server Linux è supportato nativamente; esiste immagine ufficiale Microsoft container eseguibile con Podman.

I concetti SQL sono gli stessi in tutti i DB. Cambiano sintassi, funzioni built-in, strumenti di gestione. Conoscere bene PostgreSQL (il nostro lab) significa essere 80% operativi su Oracle e SQL Server.

17 · pg_hba.conf: il firewall applicativo del DB

pg_hba.conf (Host-Based Authentication) è il file più importante della sicurezza PostgreSQL. Controlla chi può connettersi, da dove, a quale database, con quale metodo di autenticazione.

Struttura: ogni riga è una regola con cinque campi.

# TYPE   DATABASE   USER      ADDRESS         METHOD
local    all        postgres                  peer
host     all        all       127.0.0.1/32    scram-sha-256
host     mydb       appuser   10.0.1.0/24     scram-sha-256
hostssl  finance    finance   10.0.2.0/24     cert
  • TYPE: local (Unix socket), host (TCP), hostssl (TCP + TLS obbligatorio), hostnossl
  • DATABASE: nome specifico, all, o lista
  • USER: utente specifico, all, o gruppo con +
  • ADDRESS: subnet CIDR o hostname (vuoto per local)
  • METHOD: come autenticare

Metodi di autenticazione principali

MetodoNote
trustNessuna password. MAI in produzione.
rejectRifiuta sempre. Utile per blacklist.
scram-sha-256Password con challenge-response moderno. Standard dal PG 10 (2017).
md5Password con md5 hash. Deprecato, vulnerabile a offline cracking.
passwordPassword in chiaro sul wire. MAI.
peerUsa identità utente OS per local socket. Utile per admin locali.

Le 4 red flag universali in pg_hba.conf:
  • 0.0.0.0/0 — apre al mondo intero
  • trust — nessuna autenticazione
  • md5 — deprecato, vulnerabile
  • password — plaintext sul wire
Se vedete uno di questi in produzione, fermate il deploy. Dopo una modifica: SELECT pg_reload_conf(); (no restart necessario).

Pattern best practice: granularità per user + DB + subnet (principio del minimo privilegio), scram-sha-256 come minimo per password, hostssl + cert per connessioni sensibili, reject all all 0.0.0.0/0 reject come ultima riga (deny by default esplicito).

18 · TLS client-DB: cifrare il traffico

Di default PostgreSQL parla in chiaro. Password, query, dati: tutto leggibile da chiunque sniffi la rete. Abilitare TLS è obbligatorio per qualunque traffico oltre il loopback locale.

Configurazione server (postgresql.conf)

ssl = on
ssl_cert_file = 'server.crt'
ssl_key_file  = 'server.key'
ssl_ca_file   = 'ca.crt'
ssl_min_protocol_version = 'TLSv1.3'
ssl_ciphers = 'HIGH:!aNULL:!MD5'

Dopo le modifiche: SELECT pg_reload_conf(); o SIGHUP.

I 6 valori di sslmode (lato client)

sslmodeCosa faProduzione?
disableNo TLS❌ MAI
allowTLS se il server lo offre❌ vulnerabile a downgrade
preferTLS preferito, fallback a plaintext❌ default psql, non sicuro
requireTLS obbligatorio, no validazione cert⚠️ minimo accettabile
verify-caTLS + cert firmato da CA nota✅ buono
verify-fullTLS + CA + hostname matches✅ standard produzione
verify-ca non verifica il hostname: un attaccante con certificato valido emesso dalla stessa CA può fare spoofing. verify-full chiude questo buco. In produzione sempre verify-full.

Verifica che funzioni

-- Dopo psql connesso
\conninfo
-- "You are connected to db 'x' via SSL"

-- Oppure query del catalogo
SELECT ssl, version, cipher
FROM pg_stat_ssl
WHERE pid = pg_backend_pid();

Per client-cert authentication (metodo cert in pg_hba): il client presenta il proprio cert X.509, il server lo valida contro la CA. Sostituisce la password. Standard in ambienti enterprise high-security.

19 · Encryption at rest: 4 layer possibili

I dati sul disco sono cifrati. 4 layer possibili, spesso combinati per difesa in profondità:

Layer 1 — Filesystem (LUKS, BitLocker)

LUKS su Linux, BitLocker su Windows. Cifra a livello block device, trasparente al DB. Il DB legge/scrive file normali, il driver di cifratura fa il resto. Pro: zero effort, zero performance impact. Attack vector: se il sistema è acceso con disco montato, la chiave è in RAM; un memory dump può estrarla.

Layer 2 — Volume cloud (EBS, Azure Disk, GCP PD)

Opzione attivata di default nei cloud moderni (dal 2020). Chiavi gestite da KMS cloud, con opzione customer-managed keys (CMK) per compliance. Pro: zero effort in cloud. Contro: se un attaccante ruba credenziali IAM legittime, ha accesso.

Layer 3 — Column-level (pgcrypto)

Estensione pgcrypto: cifra campi specifici con PGP_SYM_ENCRYPT. Usato per dati super-sensibili (SSN, carte, documenti). Chiavi in app config, env var, o HSM (AWS KMS, Azure Key Vault, HashiCorp Vault).

-- Insert cifrato
INSERT INTO users (name, ssn_enc) VALUES (
  'Alice',
  pgp_sym_encrypt('123-45-6789', :secret_key)
);
-- Read
SELECT name, pgp_sym_decrypt(ssn_enc, :secret_key) AS ssn
FROM users;

Pro: granularità massima. Contro: impatto performance su campi indicizzati (indice su valore cifrato è inutile per range query).

Layer 4 — TDE (Transparent Data Encryption)

Cifra i data file ma trasparente all'app. Non nativo in PostgreSQL community. Esiste in Oracle, SQL Server, MySQL Enterprise. Per PostgreSQL: Cybertec TDE (fork commerciale), EDB Advanced Server (a pagamento), pg_tde (extension sperimentale). Core team sta lavorando a TDE nativo per PG 18+.

Combinazione raccomandata: volume cloud (layer 2) + pgcrypto (layer 3) per campi ultra-sensibili. Il layer 1 è ridondante in cloud. Il layer 4 è un nice-to-have se disponibile.

20 · Audit logging con pgAudit

Tracciare chi ha fatto cosa è il complemento naturale dell'encryption: encryption protegge da furto, audit fornisce evidenza di chi ha acceduto. In PostgreSQL lo strumento standard è l'estensione pgAudit.

Configurazione minima produzione

# postgresql.conf
shared_preload_libraries = 'pgaudit'
pgaudit.log = 'ddl, write, role'

log_connections = on
log_disconnections = on
log_statement = 'ddl'
log_line_prefix = '%m [%p] %q%u@%d '
log_destination = 'jsonlog'   # PG 15+: formato strutturato per SIEM

Categorie di query (scelta tipica)

  • READ: SELECT, COPY ... TO (disabilitato di default: log voluminosi)
  • WRITE: INSERT, UPDATE, DELETE, COPY ... FROM
  • DDL: CREATE, ALTER, DROP
  • ROLE: GRANT, REVOKE, CREATE ROLE, DROP ROLE
  • FUNCTION: chiamate a stored procedure
  • MISC: DISCARD, FETCH, VACUUM, CHECKPOINT

Per tabelle sensibili specifiche, abilitare anche READ con ALTER TABLE ... SET (audit='read').

Destinazione log e retention. In produzione i log non devono restare solo sul server DB: vanno forwardati a SIEM (Splunk, ELK, Datadog) tramite Filebeat/Fluentd/rsyslog. Retention minima 1-7 anni per compliance: GDPR (caso dipendente), PCI-DSS (1 anno), HIPAA (6 anni), SOX (7 anni in certi casi).

Il log_line_prefix raccomandato include timestamp con millisecondi, PID, utente, database — cruciale per correlare eventi in forensics post-incidente.
