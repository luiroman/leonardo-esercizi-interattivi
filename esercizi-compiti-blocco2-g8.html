Categoria A · MongoDB Injection (Esercizi 1-5)
ESERCIZIO 1

Perché NoSQL non è immune

PASSIVO

Tante aziende migrano a NoSQL convinte che "senza SQL, niente SQLi". Spiega in 3-4 righe perché questa convinzione è falsa, citando 2 esempi concreti di injection su database NoSQL (MongoDB, Redis, o altri).

Mostra soluzione
L'injection non è una proprietà del linguaggio SQL, ma della mancata separazione tra codice e dati. Qualunque interprete che accetti comandi strutturati può essere attaccato se l'input utente viene concatenato senza controllo. MongoDB accetta query JSON: se costruisci {user: input} e l'input è {"$ne": null}, ottieni {user: {"$ne": null}} che matcha TUTTI gli utenti — operator injection. Redis accetta comandi testo separati da \r\n: se concateni un input utente in un comando e l'input contiene newline, puoi iniettare comandi (FLUSHDB, CONFIG SET) — command injection. La difesa è la stessa di SQLi: schema validation, driver che parametrizza, niente concatenazione.
ESERCIZIO 2

Operator injection MongoDB · bypass login

ATTIVO

Data questa funzione Node.js di login:

app.post('/login', async (req, res) => {
  const user = await db.collection('users').findOne({
    username: req.body.username,
    password: req.body.password
  });
  if (user) return res.json({ok: true});
  return res.json({ok: false});
});

L'attaccante invia una POST con Content-Type: application/json e body:

{"username": "admin", "password": {"$ne": null}}

Spiega cosa succede, perché l'attacco riesce, e come si difende.

Mostra soluzione
Cosa succede: la query Mongo diventa findOne({username: "admin", password: {"$ne": null}}), che si legge "trova un utente con username admin e password diversa da null". L'utente admin esiste, ha una password (diversa da null), quindi il match c'è. L'attaccante è loggato come admin senza conoscere la password.

Perché riesce: Express con express.json() fa automaticamente parse del body JSON. Il valore {"$ne": null} entra nella query come oggetto, che Mongo interpreta come operator ($ne = not equal). Il codice si aspettava una stringa, ma accetta qualunque tipo.

Difese:
  1. Type check esplicito: if (typeof req.body.username !== 'string' || typeof req.body.password !== 'string') return res.status(400).
  2. Schema validation: usa Joi, Yup, Zod per validare il body. Schema: {username: z.string(), password: z.string()}.
  3. Sanitize operatori: mongo-sanitize rimuove ricorsivamente chiavi che iniziano con $ o contengono ..
  4. Soprattutto: mai fare match password plain così — usa bcrypt lato server, query solo per username, poi bcrypt.compare(input, user.passwordHash).
ESERCIZIO 3

Operatori MongoDB pericolosi in injection

PASSIVO

Elenca e spiega brevemente almeno 4 operatori MongoDB che possono essere abusati in un attacco di operator injection (es. $ne). Per ciascuno indica come l'attaccante li usa.

Mostra soluzione
  • $ne (not equal) — {password: {"$ne": null}} matcha qualunque password non null. Bypass login classico.
  • $gt / $lt (greater/less than) — {password: {"$gt": ""}} matcha qualunque stringa. Simile a $ne, funziona anche quando $ne è sanitizzato.
  • $regex — {username: {"$regex": "^admin"}} consente enumerazione: provare "^a", "^ad", ecc. per trovare username esistenti. È l'equivalente NoSQL di blind boolean SQLi.
  • $where — accetta stringa JavaScript eseguita da Mongo. {$where: "this.password == this.username"}. In configurazioni permissive, è RCE sul server Mongo. Disabilitato di default su MongoDB Atlas; attivo in alcune installazioni legacy.
  • $exists — {admin_flag: {"$exists": true}} per enumerare i campi del documento e trovare campi sensibili non documentati.
  • $or / $and — {"$or": [{username: "admin"}, {admin: true}]} per combinazioni logiche non previste dall'app.
La difesa generale: type check — se il campo deve essere stringa, verificare typeof === 'string' prima di passarlo alla query.
ESERCIZIO 4

Mongoose vs driver native · quale è più sicuro?

ATTIVO

In Node.js ci sono due approcci per parlare con MongoDB: il driver nativo mongodb, o l'ORM-like Mongoose. Confronta i due in termini di difesa da operator injection: quale offre più garanzie by-default e perché? Cita almeno 2 meccanismi di Mongoose che aiutano.

Mostra soluzione
Driver native (mongodb): zero ORM, zero schema. Passi oggetti JavaScript direttamente al driver. Se l'app non fa type check, operator injection passa dritta. Responsabilità di sicurezza 100% sull'applicazione.

Mongoose: ORM-like con schema obbligatorio. Offre by-default:
  1. Schema type casting: se il campo è definito {username: String}, Mongoose converte (o rifiuta) input non-string. Un {"$ne": null} viene coerced a stringa, diventando innocuo ("[object Object]").
  2. Strict mode: di default Mongoose ignora campi non presenti nello schema. Questo previene che attaccante aggiunga {admin: true} in un .create().
  3. Validators: regole custom (minlength, enum, regex, funzioni) che bloccano valori non validi prima del DB.
  4. sanitizeFilter (plugin opzionale): rimuove operatori da input utente.
Verdict: Mongoose è più sicuro by-default, ma attenzione: Model.find(req.body) bypassa type casting sugli operatori di query. Sempre costruire esplicitamente il filter object. Inoltre Mongoose non protegge da tutto — va comunque fatto type check prima di passargli l'input.
ESERCIZIO 5

Fix un endpoint MongoDB vulnerabile

PRATICO

Dato questo endpoint Node.js con Express + mongodb driver:

app.get('/search', async (req, res) => {
  const docs = await db.collection('products').find({
    category: req.query.cat,
    price: { $lte: req.query.max }
  }).toArray();
  res.json(docs);
});

Identifica le 2 vulnerabilità di operator injection e riscrivi l'endpoint con le difese corrette.

Mostra soluzione
Vulnerabilità:
  1. req.query.cat può essere un oggetto (Express parsifica ?cat[$ne]=null come {$ne: null}) → bypass filtro categoria.
  2. req.query.max arriva come stringa ma Mongo fa comparison su stringhe — inoltre se attaccante passa ?max[$gt]=0 ottiene sempre {$lte: {$gt: 0}} che è sintassi non valida ma può causare errori o bypass.
Fix: 
const ALLOWED_CATS = ['electronics','books','clothing','food'];

app.get('/search', async (req, res) => {
  // 1. Type check + allowlist per category
  const cat = String(req.query.cat || '');
  if (!ALLOWED_CATS.includes(cat)) {
    return res.status(400).json({error: 'invalid category'});
  }

  // 2. Type cast esplicito per max
  const max = Number(req.query.max);
  if (!Number.isFinite(max) || max < 0) {
    return res.status(400).json({error: 'invalid max'});
  }

  const docs = await db.collection('products').find({
    category: cat,
    price: { $lte: max }
  }).toArray();
  res.json(docs);
});
Principi applicati: type coercion con String() e Number(), allowlist per categoria (lista chiusa), validation con default safe, early return con 400. Lo stesso pattern di SQLi: se puoi enumerare i valori leciti, enumerali.
Categoria B · Redis & altri NoSQL (Esercizi 6-8)
ESERCIZIO 6

Redis command injection via newline

PASSIVO

Il protocollo Redis (RESP) separa i comandi con \r\n. Spiega come questo diventa un vettore di injection se l'app concatena input utente in comandi Redis raw, e dai un esempio di payload malevolo.

Mostra soluzione
Se l'app costruisce comandi come "GET user:" + username e li manda come stringa al server Redis, un input contenente \r\n permette di iniettare comandi arbitrari. Esempio: username = "john\r\nFLUSHDB\r\n" produce il flusso: 
GET user:john
FLUSHDB
Il server Redis esegue il secondo comando. FLUSHDB cancella tutti i dati del database corrente. Altri comandi pericolosi iniettabili: CONFIG SET dir /tmp + CONFIG SET dbfilename shell.php + SAVE = writefile primitive per RCE se Redis è configurato male; DEBUG SLEEP 100 DoS; MIGRATE esfiltrazione dati.

Difesa: usare driver client ufficiale (redis-py, ioredis) che parametrizza usando binary RESP protocol, non testo concatenato. I driver moderni non sono vulnerabili by-default. Si è vulnerabili solo se si costruiscono comandi a mano o si usa eval/client.sendCommand con stringhe raw.
ESERCIZIO 7

CQL Injection in Cassandra

PASSIVO

Apache Cassandra usa CQL (Cassandra Query Language), una sintassi simile a SQL. Spiega se Cassandra è vulnerabile a injection, come, e se le difese di SQLi classiche si applicano anche qui.

Mostra soluzione
Sì, CQL injection esiste ed è molto simile a SQL injection. CQL supporta SELECT, WHERE, INSERT, UPDATE, DELETE, BATCH. Se concateni input utente in query CQL, sei vulnerabile agli stessi attacchi: bypass con ' OR '1'='1, UNION (con limiti — Cassandra non supporta JOIN, ma supporta altre primitive), etc.

Differenze da SQLi:
  • Cassandra NON supporta stacked queries (no ;DROP TABLE)
  • Cassandra NON ha information_schema classico — enumerate passa per system_schema.tables
  • Meno feature di exploitation rispetto a PostgreSQL/MySQL (no COPY TO PROGRAM, no UDF facili)
Difesa: le stesse di SQLi. Il driver Java/Python/Node di Cassandra supporta prepared statements nativi con placeholder ?. Esempio Python: 
session.execute(
    "SELECT * FROM users WHERE id = ?",
    [user_id]
)
Principio generale: qualunque linguaggio di query strutturato è vulnerabile a injection se concateni input, e la difesa è sempre la parametrizzazione nativa del driver.

Categoria C · pgAudit setup (Esercizi 9-12)
ESERCIZIO 9

Cos'è pgAudit

PASSIVO

In 5-6 righe, spiega cos'è pgAudit, che problema risolve, e quali sono le sue differenze rispetto al logging standard di PostgreSQL (log_statement).

Mostra soluzione
pgAudit è un'extension di PostgreSQL che fornisce audit logging dettagliato e strutturato. Nata perché il logging standard di Postgres (log_statement = 'all') è troppo verboso per uso in produzione (perdi il segnale nel rumore) e troppo poco dettagliato per compliance (GDPR, SOX, PCI-DSS). pgAudit risolve con 2 features chiave:
  1. Session audit: logga classi di comandi (READ, WRITE, FUNCTION, ROLE, DDL, MISC) con granularità fine. Puoi loggare solo DDL e ROLE, ignorando SELECT triviali.
  2. Object audit: logga operazioni su tabelle specifiche. Esempio: ogni accesso alla tabella sensitive_data, indipendentemente da chi lo fa.
Formato strutturato: ogni entry ha 11 campi (audit type, statement id, substatement id, class, command, object type, object name, statement, parameter, etc.) facilmente parsabile dai SIEM (Splunk, ELK).

Differenza con log_statement: log_statement = 'all' è binario (tutto o niente); pgAudit è granulare per classe e per oggetto. Inoltre pgAudit logga anche statement dentro funzioni, log_statement no.
ESERCIZIO 10

Installazione pgAudit in container PostgreSQL

PRATICO

Hai un container PostgreSQL 16 running. Installa pgAudit come extension. Produci comando docker exec o podman exec che:

  1. Installa il pacchetto postgresql-16-pgaudit dentro il container
  2. Configura postgresql.conf con shared_preload_libraries='pgaudit'
  3. Riavvia PostgreSQL
  4. Crea l'extension nel database app
Mostra soluzione
## 1. Installa pacchetto Debian (immagine postgres:16 è basata su Debian)
$ podman exec -u root pg podman apt-get update
$ podman exec -u root pg apt-get install -y postgresql-16-pgaudit

## 2. Configura shared_preload_libraries nel postgresql.conf
$ podman exec -u postgres pg psql -U postgres -c \
  "ALTER SYSTEM SET shared_preload_libraries = 'pgaudit';"

## 3. Riavvia PostgreSQL per caricare la libreria
$ podman restart pg

## 4. Crea l'extension nel database app
$ podman exec -u postgres pg psql -U postgres -d app -c \
  "CREATE EXTENSION pgaudit;"

## 5. Configura cosa loggare (es. DDL + WRITE + ROLE)
$ podman exec -u postgres pg psql -U postgres -d app -c \
  "ALTER SYSTEM SET pgaudit.log = 'ddl, write, role';"
$ podman exec -u postgres pg psql -U postgres -c "SELECT pg_reload_conf();"

## 6. Verifica
$ podman exec -u postgres pg psql -U postgres -d app -c "\dx pgaudit"
Nota: shared_preload_libraries richiede restart, non pg_reload_conf(). Invece pgaudit.log può essere cambiato con reload. In produzione: loggare sempre ddl, role; aggiungere write se la throughput lo permette.
ESERCIZIO 11

Classi di audit pgAudit

PASSIVO

pgAudit logga operazioni classificate in 7 classi. Elenca le 7 classi e per ciascuna indica: (a) cosa include, (b) quando tipicamente va abilitata in produzione, (c) impatto su throughput.

Mostra soluzione
  • READ — SELECT, COPY TO. (a) ogni lettura dal DB. (b) solo su tabelle sensibili (via object audit), mai su tutto in OLTP ad alto throughput. (c) impatto ALTO — le letture sono il 90% del traffico.
  • WRITE — INSERT, UPDATE, DELETE, TRUNCATE, COPY FROM. (a) modifiche dati. (b) sempre attivo. (c) impatto BASSO/MEDIO — le scritture sono meno frequenti.
  • FUNCTION — execution di funzioni/procedure. (a) chiamate a funzioni definite dall'utente. (b) se usi PL/pgSQL custom, utile per tracciare; altrimenti skip. (c) impatto MEDIO.
  • ROLE — GRANT, REVOKE, CREATE/DROP/ALTER ROLE. (a) permission management. (b) sempre — modifiche permessi sono rare e critiche. (c) impatto TRASCURABILE.
  • DDL — CREATE, ALTER, DROP tabelle/indici/schemi. (a) cambi strutturali schema. (b) sempre. (c) impatto TRASCURABILE.
  • MISC — DISCARD, FETCH, CHECKPOINT, VACUUM, etc. (a) comandi amministrativi. (b) opzionale, utile per troubleshooting. (c) impatto BASSO.
  • ALL — tutte le classi. (a) ovvio. (b) solo in compliance stretta (es. sistemi PCI-DSS) e con hardware abbondante. (c) impatto MOLTO ALTO.
Policy standard Leonardo: pgaudit.log = 'ddl, role, write' — tracci schema changes, permission changes, modifiche dati. Le letture le tracci solo su tabelle classified sensibili tramite object audit.
ESERCIZIO 12

Leggere un log pgAudit

ATTIVO

Dato questo entry di log pgAudit:

LOG:  AUDIT: SESSION,23,1,WRITE,UPDATE,TABLE,public.users,
UPDATE users SET role='admin' WHERE id=<unknown>,<binary_param>

Estrai tutte le informazioni che puoi da questo log. Questo tipo di query ti allarmerebbe in un contesto di SOC? Perché?

Mostra soluzione
Parsing del log:
  • AUDIT: — prefisso pgAudit che distingue le sue entries dai log normali
  • SESSION — tipo audit: session (chi ha eseguito la query a livello sessione); alternativa sarebbe OBJECT (accesso a oggetto specifico)
  • 23 — statement_id (contatore per sessione)
  • 1 — substatement_id (per statement con sub-query)
  • WRITE — classe audit
  • UPDATE — comando SQL
  • TABLE — tipo oggetto
  • public.users — nome oggetto (schema.table)
  • UPDATE users SET role='admin' WHERE id=<unknown> — statement eseguito (con parametro mascherato per privacy)
  • <binary_param> — indica che il valore è stato passato come bind param (buon segno: la query è parametrizzata)
Allarme SOC? Sì, fortissimo. Motivi:
  1. UPDATE ... SET role='admin' è privilege escalation — qualcuno sta promuovendo un account a admin
  2. Se il processo che ha fatto questa query è l'app_runtime user (che non dovrebbe avere UPDATE su role), siamo davanti a SQLi riuscita con impact critico
  3. Se è l'admin user, verificare se è stato fatto da console autorizzata o da sessione anomala (orario, IP)
Alert SIEM: regola tipica → UPDATE ... SET role o INSERT INTO admin sempre paging on-call, anche se da account admin. Questa è la ragione per cui pgAudit + SIEM è game-changer: detection in tempo reale di compromissioni.
Categoria D · Row-Level Security in PostgreSQL (Esercizi 13-16)
ESERCIZIO 13

Cos'è RLS e quando serve

PASSIVO

Spiega in 5-6 righe cosa fa Row-Level Security (RLS) in PostgreSQL, che problema risolve, e dai un esempio concreto di quando useresti RLS invece di filtrare solo nell'applicazione.

Mostra soluzione
RLS permette di definire policy per-riga su una tabella: quando un utente DB fa una query, PostgreSQL filtra automaticamente le righe in base a una condizione (policy) definita dal DBA. L'applicazione riceve già il subset filtrato, senza dover aggiungere WHERE user_id = X nella query.

Problema che risolve: in app multi-tenant o con authorization complessa, il filtering è ripetuto in centinaia di query. Un solo SELECT * FROM orders dimenticato senza WHERE user_id = data leak. Con RLS, anche se l'app sbaglia a filtrare, il DB enforza la policy.

Esempio concreto — SaaS multi-tenant: tabella customers condivisa tra tutti i tenant. Policy: USING (tenant_id = current_setting('app.current_tenant')::int). L'app setta la variabile a inizio sessione. Anche se uno sviluppatore scrive SELECT * FROM customers senza WHERE tenant_id, riceve solo le righe del tenant corrente. Applicato anche alle query di reportistica via Metabase o BI tools — impossibile sbagliare il filtro.

Connessione a SQLi: anche se c'è SQLi che permette UNION SELECT * FROM customers, RLS continua a filtrare. È defense-in-depth al livello DB.
ESERCIZIO 14

Scrivi una policy RLS per ordini

ATTIVO

Data una tabella orders(id, customer_id, product, amount) con milioni di record da migliaia di clienti: scrivi il DDL completo PostgreSQL per abilitare RLS in modo che ciascun customer veda SOLO i propri ordini. Assumi che l'app setti app.current_customer_id a inizio sessione.

Mostra soluzione
-- 1. Abilita RLS sulla tabella
ALTER TABLE orders ENABLE ROW LEVEL SECURITY;

-- 2. (Opzionale) enforce anche per table owner (senza questo, owner bypassa RLS)
ALTER TABLE orders FORCE ROW LEVEL SECURITY;

-- 3. Definisci la policy di SELECT per customer own rows
CREATE POLICY customer_own_orders ON orders
    FOR SELECT
    USING (customer_id = current_setting('app.current_customer_id')::int);

-- 4. Policy di INSERT: customer può creare solo proprio ordine
CREATE POLICY customer_insert_own ON orders
    FOR INSERT
    WITH CHECK (customer_id = current_setting('app.current_customer_id')::int);

-- 5. Policy di UPDATE/DELETE: solo propri ordini
CREATE POLICY customer_modify_own ON orders
    FOR UPDATE USING (customer_id = current_setting('app.current_customer_id')::int)
    WITH CHECK (customer_id = current_setting('app.current_customer_id')::int);

CREATE POLICY customer_delete_own ON orders
    FOR DELETE
    USING (customer_id = current_setting('app.current_customer_id')::int);

-- 6. Grant al user applicativo (senza questo non può accedere affatto)
GRANT SELECT, INSERT, UPDATE, DELETE ON orders TO app_runtime;

-- 7. App setta il customer_id a inizio di ogni sessione/transazione
-- Dal lato applicativo, prima di ogni query:
-- SET app.current_customer_id = '12345';
Attenzione: FORCE ROW LEVEL SECURITY è fondamentale se il table owner è lo stesso user dell'app — altrimenti l'app bypassa RLS (owner ha bypass implicit). In produzione: tabella creata dall'user migration, RLS attiva anche per owner, app si connette come app_runtime.
ESERCIZIO 15

RLS vs SQLi · come interagiscono

ATTIVO

Scenario: app vulnerabile a SQLi. Utente malizioso paziente esegue UNION SELECT * FROM orders via sqlmap. La tabella orders ha RLS attiva come nel esercizio 14. Cosa otterrà l'attaccante? Cosa NON otterrà? Cosa significa per la strategia defense-in-depth?

Mostra soluzione
Cosa ottiene: l'attaccante ottiene SOLO le righe che matchano la policy RLS. Se la sessione ha app.current_customer_id = 42, il UNION SELECT * FROM orders ritorna solo gli ordini del customer 42 — gli stessi che l'app gli mostrava legittimamente. Nessun vantaggio.

Cosa NON ottiene: gli ordini degli altri customer. La SQLi ha bucato l'applicazione ma il DB filtra comunque. Questa è la magia di RLS.

Casi in cui RLS fallisce:
  1. Se app.current_customer_id è settata a un ID "admin" speciale (0, -1, NULL) che bypassa la policy — attaccante potrebbe provare a manipolare la sessione.
  2. Se la policy usa current_user e l'app si collega come superuser — superuser bypassa RLS di default (serve FORCE ROW LEVEL SECURITY).
  3. Se c'è una tabella alternative senza RLS (es. un backup in schema archive) — attaccante la trova con --dbs --tables.
  4. Se l'attaccante trova modo di eseguire SET app.current_customer_id = 999; in una stacked query, può cambiare il contesto.
Defense-in-depth: RLS è una delle difese più potenti contro SQLi perché agisce a livello DB, indipendente dall'applicazione. Il pattern completo:
  1. Prepared statements (elimina 99% SQLi)
  2. LPP DB user (limita privilegi in caso di bypass)
  3. RLS (filtra righe anche con SQLi riuscita)
  4. pgAudit (detection nei log in tempo reale)
  5. WAF (rate limit + pattern blocker)
Con tutti e 5 i livelli: SQLi funzionante → ottiene solo righe già autorizzate + viene loggata + WAF la blocca dopo N tentativi. Rischio residuo = minimo.
