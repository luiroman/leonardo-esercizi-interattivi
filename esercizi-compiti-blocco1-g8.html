ESERCIZIO 1

Le 3 condizioni in 5 esempi

PASSIVO

Per ognuno di questi 5 scenari, indica se c'è SQLi e quale/i delle 3 condizioni necessarie sono presenti:

  1. App desktop che usa SQLite locale, il filtro ricerca è costruito concatenando input_utente nella stringa SQL
  2. Script CLI che prende un argomento da command line, lo concatena in query PostgreSQL
  3. App web che costruisce query dinamicamente concatenando il nome di una TABELLA da un valore di configurazione hardcoded
  4. API che riceve JSON, usa json['user_id'] come int dentro execute("... WHERE id=%s", (int(json['user_id']),))
  5. Cron job che legge un file CSV generato da export esterno e lo concatena in query
Mostra soluzione
1. SQLi SÌ. Tutte e 3 condizioni: input user-controlled (ricerca), flusso verso query, nessuna parametrizzazione.

2. SQLi SÌ (tecnicamente). Argument CLI = user-controlled, concatenato in query. La condizione 1 vale anche per script — l'utente della CLI è comunque "user".

3. SQLi NO. Condizione 1 rotta: il nome tabella viene da configurazione hardcoded, NON da input utente. Ma attenzione: se quel valore di config in futuro fosse alimentato da input esterno, diventerebbe vulnerabile.

4. SQLi NO. Parametrizzazione con %s + cast esplicito a int(). Doppia protezione: prepared + type safety.

5. SQLi SÌ, con caratteristica second-order. Il file CSV = input indiretto utente (qualcuno l'ha generato). Se quel qualcuno può mettere SQL nel CSV, c'è SQLi all'esecuzione del cron. Difesa: mai fidarsi dei CSV esterni, sempre parametrizzare anche quando "sembra" sicuro.

ESERCIZIO 3

Classifica snippet reali

ATTIVO

Ecco 4 snippet di codice. Per ognuno: (a) classifica come VULNERABILE o SICURO, (b) se vulnerabile indica tipo SQLi più probabile, (c) proponi fix.

// A · Node.js con mysql2
const user = req.query.user;
connection.query(
  `SELECT * FROM accounts WHERE username='${user}'`,
  (err, rows) => res.json(rows)
);

// B · Python con SQLAlchemy text()
from sqlalchemy import text
name = request.args.get('name')
result = session.execute(
  text(f"SELECT * FROM users WHERE name='{name}'")
)

// C · PHP con PDO
$pdo = new PDO('mysql:host=...', $user, $pass);
$pdo->setAttribute(PDO::ATTR_EMULATE_PREPARES, false);
$stmt = $pdo->prepare("SELECT * FROM users WHERE id = ?");
$stmt->execute([$_GET['id']]);

// D · Java con Statement
String q = "SELECT * FROM users WHERE name='" +
           request.getParameter("name") + "'";
Statement stmt = conn.createStatement();
ResultSet rs = stmt.executeQuery(q);
Mostra soluzione
A · VULNERABILE. Template literal JS = concatenazione. Tipo: UNION se output visibile, blind altrimenti. Fix: connection.query('SELECT * FROM accounts WHERE username = ?', [user], ...)

B · VULNERABILE. text() con f-string = concatenazione SQL. Il fatto che sia SQLAlchemy non protegge — abbiamo "sceso" al raw. Tipo: tutti, dipende da output. Fix: text("SELECT * FROM users WHERE name=:name").bindparams(name=name).

C · SICURO. PDO con ATTR_EMULATE_PREPARES=false = real prepared statement native MySQL. L'execute([...]) passa array posizionale di bind. Attenzione: senza setAttribute, PDO di default emula → fragile. Questa è la configurazione corretta.

D · VULNERABILE. Statement + concatenazione. Classico caso di SQLi Java. Fix: usa PreparedStatement + setString:
PreparedStatement ps = conn.prepareStatement("SELECT * FROM users WHERE name=?");
ps.setString(1, request.getParameter("name"));
ESERCIZIO 4

OWASP Top 10 storia

PASSIVO

SQLi è nell'OWASP Top 10 dal 2003. Scrivi una timeline breve (~150 parole) che tocchi: (1) prima apparizione, (2) anni al primo posto, (3) cosa è cambiato nel 2021, (4) perché la categoria A03:2021 è un "ombrello" più largo.

Mostra soluzione tipica
La SQL Injection appare nel OWASP Top 10 del 2003 in posizione A6, classificata tra le vulnerabilità di "flawed input validation". Nel 2007 sale ad A2 per l'esplosione delle web app 2.0. Dal 2010 al 2017 è stabile in prima posizione (A1) per 11 anni consecutivi, riflettendo la sua diffusione e l'impatto (esfiltrazione dati, RCE via DB).

Nel 2021 OWASP ristruttura la classifica con nuova metodologia (incidenza + exploitability + impatto) e la categoria "Injection" diventa A03 — un ombrello che include CWE-89 (SQLi), CWE-79 (XSS), CWE-77 (Command), CWE-94 (Code), CWE-917 (Template), CWE-91 (XML). Tutte condividono lo stesso pattern: input non fidato eseguito come codice nel contesto sbagliato.

Il "ridimensionamento" ad A03 non riflette meno frequenza — il report 2021 dichiara che 94% delle app testate aveva qualche forma di injection. È il risultato di framework moderni (ORM safe-by-default) che riducono la facilità su app nuove, mentre sulle legacy rimane pervasiva.

ESERCIZIO 6

DVWA medium · la sfida

PRATICO

Cambia security level a medium e ripeti sqlmap. La pagina ha ora protezioni (mysqli_real_escape_string, parametro numerico). Cosa cambia nell'output di sqlmap?

  1. Quali tipi di SQLi sono ancora rilevati?
  2. Quanto tempo in più serve?
  3. Quale tecnica funziona e perché?
Mostra analisi attesa
A security=medium, DVWA usa mysqli_real_escape_string($id) E il form invia id come numero (via dropdown), non stringa libera. Ma il problema è che il backend concatena senza quote: SELECT ... WHERE id = $id (nessun apostrofo intorno a $id).

Risultato:
• Error-based: ancora funziona (mysqli_real_escape_string non blocca errori SQL provocati da CAST)
• UNION-based: funziona (nessun apostrofo a cui scappare, quindi escape inefficace)
• Boolean-blind: funziona
• Time-blind: funziona

Tempo: simile al low, forse 10-20 secondi in più di detection.

Lezione: mysqli_real_escape_string è una difesa DEBOLE e contestuale — serve SOLO a scappare apostrofi dentro stringhe quotate. Se la query non mette quotes, è inefficace. Questo è il classico anti-pattern "escape" che i senior PHP developers criticano: meglio prepared statements always.

  1. Quanti tipi di SQLi sono stati confermati?

Mostra soluzione
1. Tre tipi confermati: Boolean-blind, Error-based, UNION-based. Note: sqlmap di solito prova anche time-based nello stesso run; se non è in output significa che ha saltato perché già aveva conferme sufficienti.

Flag sqlmap avanzati

ATTIVO

Per ognuno di questi scenari, scegli i flag sqlmap più appropriati tra: --level, --risk, --technique, --tamper, --threads, --delay, --random-agent, --proxy.

  1. Target protetto da WAF, serve payload obfuscated
  2. Rate limit attivo sul target, serve rallentare
  3. Voglio vedere TUTTE le richieste sqlmap in Burp Suite
  4. Test esaustivo su tutti i parametri inclusi cookie e header
  5. Serve solo detection rapida, basta un tipo di SQLi
Mostra soluzione
1 · WAF bypass: --tamper=space2comment,between,charencode (combinazione di tamper scripts). Opzionalmente anche --random-agent per non essere bloccati da signature User-Agent.

2 · Rate limit: --delay=3 --threads=1. 3 secondi tra request, nessun parallelismo.

3 · Proxying su Burp: --proxy=http://127.0.0.1:8080. Utile per logging dettagliato e manual review dei payload inviati.

4 · Test esaustivo: --level=5 --risk=3. Level=5 include cookie, header, user-agent; risk=3 autorizza payload invasivi (UPDATE/INSERT).

5 · Detection rapida: --technique=B (solo boolean-blind) o --technique=BE (boolean + error). Skip UNION, time, OOB — più veloci ma meno completi.

ESERCIZIO 11

ORM · spot the bug

ATTIVO

Trova i bug di sicurezza in questi 3 snippet ORM:

# A · Django ORM
from django.db import connection
def search(request):
    q = request.GET.get('q')
    with connection.cursor() as cursor:
        cursor.execute(
            "SELECT * FROM products WHERE name LIKE '%" + q + "%'"
        )
        return cursor.fetchall()

# B · SQLAlchemy
from sqlalchemy import text
def user_by_name(session, name):
    return session.execute(
        text(f"SELECT * FROM users WHERE name = '{name}'")
    ).first()

# C · Sequelize
async function searchPosts(tag) {
    const results = await sequelize.query(
        "SELECT * FROM posts WHERE tags LIKE '%" + tag + "%'",
        { type: QueryTypes.SELECT }
    );
    return results;
}
Mostra soluzione
A · Django bug: connection.cursor().execute() accetta un secondo argomento params. Il bug è la concatenazione.
Fix: cursor.execute("SELECT * FROM products WHERE name LIKE %s", ['%' + q + '%'])

B · SQLAlchemy bug: text() con f-string = concatenazione SQL.
Fix: text("SELECT * FROM users WHERE name = :name").bindparams(name=name)

C · Sequelize bug: sequelize.query() con concat.
Fix: usare replacements:
await sequelize.query(
    "SELECT * FROM posts WHERE tags LIKE :tag",
    { replacements: { tag: '%' + tag + '%' }, type: QueryTypes.SELECT }
);
Oppure bind (placeholder posizionale):
await sequelize.query(
    "SELECT * FROM posts WHERE tags LIKE $1",
    { bind: ['%' + tag + '%'], type: QueryTypes.SELECT }
);
ESERCIZIO 12

Allowlist dinamica per tabelle

ATTIVO

Scenario: pannello admin che permette di esportare CSV da una delle seguenti tabelle: users, orders, products, audit_log. L'utente sceglie la tabella da dropdown.

Scrivi il codice Python che implementa l'export con allowlist robusta, sapendo che il nome tabella NON può essere parametrizzato come valore.

Mostra soluzione
ALLOWED_TABLES = {
    'users': ['id', 'email', 'created_at'],          # non email password
    'orders': ['id', 'user_id', 'amount', 'status', 'created_at'],
    'products': ['id', 'name', 'price', 'stock'],
    'audit_log': ['id', 'action', 'user_id', 'timestamp'],
}

@app.route('/admin/export/<table>')
@require_admin
def export_csv(table):
    if table not in ALLOWED_TABLES:
        return "Tabella non consentita", 400
    
    columns = ALLOWED_TABLES[table]
    cols_sql = ', '.join(columns)  # sicuro: cols vengono dal dict
    
    # concat sicura: table è in allowlist, cols sono enumerate hardcoded
    cursor.execute(f"SELECT {cols_sql} FROM {table}")
    
    # ... csv response
    rows = cursor.fetchall()
    output = io.StringIO()
    writer = csv.writer(output)
    writer.writerow(columns)
    writer.writerows(rows)
    return Response(output.getvalue(), mimetype='text/csv')
Punti chiave:
1. ALLOWED_TABLES mappa chiave → colonne permesse. Ogni tabella ha la propria whitelist di colonne — evita di esporre colonne sensibili (es. password_hash per users).
2. La concatenazione f"SELECT {cols_sql} FROM {table}" è sicura PERCHÉ sia table sia cols_sql derivano dal dict finito.
3. Attenzione: NON passare columns direttamente dal request — deve sempre venire dalla server-side allowlist.
ESERCIZIO 13

LPP analisi · cosa può fare l'attaccante?

ATTIVO

In un'app che ha una SQL injection esistente, analizza cosa può fare l'attaccante nei 3 scenari seguenti:

  1. App user = postgres (superuser)
  2. App user = app_runtime con GRANT SELECT, INSERT, UPDATE su 5 tabelle business
  3. App user = readonly con GRANT SELECT su 3 tabelle business

Per ciascuno, elenca 3 impatti concreti (what can the attacker do).

Mostra soluzione
Scenario 1 · superuser (game over):
  • DROP DATABASE / DROP TABLE → distruzione dati
  • COPY TO PROGRAM → RCE (esegue comandi OS come user postgres)
  • pg_read_server_files → leggere /etc/passwd, chiavi SSH, config file
  • CREATE USER / ALTER ROLE → persistence backdoor
  • Leggere TUTTI i database, non solo quello dell'app
Scenario 2 · app_runtime CRUD limitato:
  • Esfiltrare TUTTI i dati delle 5 tabelle business (SELECT ok)
  • Modificare dati (UPDATE): cambio prezzi, redirecting ordini, alterazione saldo account
  • Inserire dati fake (INSERT): account admin nuovi se c'è logica business errata, log falsi
  • NON può: DROP, ALTER, creare user, leggere altri DB/schema, accedere al file system
Scenario 3 · readonly (blast radius minimo):
  • Esfiltrare dati delle 3 tabelle — comunque grave se contengono PII/finanziario
  • Enumeration: capire struttura DB, volumi, relazioni
  • Information gathering per attacchi successivi (es. hash password trovati → crack offline)
  • NON può: modificare nulla, accedere ad altre tabelle, RCE
Morale: LPP non impedisce la SQLi, ma trasforma un data breach catastrofico in un data leak contenuto. Essenziale per compliance (GDPR, PCI-DSS) perché riduce lo "scope" dell'incidente.
ESERCIZIO 14

WAF · scrivi regole ModSecurity

ATTIVO

Scrivi 3 regole ModSecurity (Core Rule Set style) che bloccano payload SQLi comuni. Indica anche un possibile bypass per ogni regola.

Mostra soluzione
Regola 1 · blocca UNION SELECT: 
SecRule ARGS "@rx (?i)union\s+select" \
    "id:10001, deny, status:403, \
     msg:'SQL Injection: UNION SELECT pattern'"
Bypass: UNION/**/SELECT, UNION%00SELECT, UnIoN sElEcT, UN%49ON SELECT (URL encoding di 'I').

Regola 2 · blocca quote + OR: 
SecRule ARGS "@rx (?i)'\s*or\s+['\"0-9]" \
    "id:10002, deny, status:403, \
     msg:'SQL Injection: OR tautology'"
Bypass: senza apostrofo (1 OR 1=1), con AND (1 AND 1=1), con backticks MySQL, con funzioni (1 OR MID(...)).

Regola 3 · blocca functions specifiche: 
SecRule ARGS "@rx (?i)(sleep|pg_sleep|waitfor|benchmark)\s*\(" \
    "id:10003, deny, status:403, \
     msg:'SQL Injection: time-based function'"
Bypass: encoding hex (0x73 0x6C ...), stringhe concatenate (SL||EEP), versioned comments MySQL (/*!50000 SLEEP*/).

Conclusione: le 3 regole bloccano attacchi automatizzati generici, ma un attaccante mirato ha strumenti di bypass (sqlmap --tamper) pronti. Il WAF è utile, non sufficiente.

ESERCIZIO 15

Defense in Depth · ordina le difese

PASSIVO

Ordina le 5 difese dalla più forte (strutturale) alla più debole (perimetrale), motiva l'ordine.

Mostra soluzione
1° · Prepared Statements (strutturale). Rompe la condizione 3 delle 3 necessarie per SQLi. È una separazione architetturale codice/dati a livello driver — non bypassabile.

2° · ORM (strutturale automatico). È il modo in cui la maggior parte delle app moderne applica prepared. Sicuro per API idiomatiche; inefficace se si "scende" a raw().

3° · Input Validation (contestuale). Allowlist funziona bene per enum di valori limitati. Non sostituisce prepared — complementa.

4° · LPP DB user (contenimento). NON impedisce la SQLi, ma ne riduce l'impatto quando le difese 1-3 falliscono. Fondamentale per mitigation real-world.

5° · WAF (perimetrale, blocklist). Ha bypass noti, falsi positivi, è solo pattern detection. Utile per rallentare attacchi automatizzati e logging, non per protezione strutturale.

Morale: se hai tempo limitato per hardening, dai priorità 1→2→4 (prepared, ORM, LPP). Input validation e WAF sono strumenti complementari, non sostituti.

1. Fermarsi immediatamente. Non replicare il bug.

Solo con autorizzazione scritta dall'azienda Mario può fare pentest. Fino a quel momento, qualsiasi test è reato.

        f"ORDER BY {sort_col} {order} "
        f"LIMIT %s",
        (account_id, limit)
    )
    return cursor.fetchall()
Punti chiave applicati:
• Difesa 1 (prepared): account_id e limit via %s
• Difesa 3 (allowlist): sort_col da dict chiuso, order da set chiuso
• Difesa 4 (LPP): app_user senza DROP/ALTER/SUPERUSER, SELECT limitato a 2 tabelle
• Bonus: ownership check server-side, type validation con int(), limit capped a 500
