A · Concetto hardening e framework
1scelta multipla

Definizione di hardening

Quale tra le seguenti è la definizione più corretta di "hardening"?

Corretto. L'hardening è il processo sistematico di ridurre la superficie d'attacco (servizi inutili disabilitati, porte chiuse, account limitati) e applicare il principio di least privilege. Il patching (a) è correlato ma è un'altra disciplina. Antivirus/firewall (c) sono difese reattive, non hardening.
Non corretto. La risposta è b. L'hardening agisce prima dell'attacco, riducendo cosa l'attaccante può fare quando ottiene accesso. Patching (a) chiude singole CVE ma non riduce la superficie complessiva.
2scelta multipla

CIS L1 vs CIS L2 vs STIG

Confronta i tre framework di hardening. Quale affermazione è VERA?

Corretto. STIG (Defense Information Systems Agency) è progettato per ambienti DoD USA e impone requisiti che CIS considera "nice-to-have": FIPS-validated cryptography obbligatoria, smart card authentication, retention log estesa (1 anno+), controllo TLS minimum 1.2.
Non corretto. La risposta è c. La gerarchia di rigore è: CIS L1 (baseline) < CIS L2 (più stringente, alcune limitazioni operative) < STIG (specifico DoD, requisiti più restrittivi).
3aperta

Compensating controls

Hai un server legacy Windows Server 2008 con applicazione critica non aggiornabile. CIS L1 richiede di disabilitare SMBv1 ma l'applicazione lo richiede per funzionare. Cosa fai? Suggerisci 3 compensating controls.

Mostra soluzione
1. Microsegmentazione: isolare il server in zona di rete dedicata, accettare SMBv1 solo da IP autorizzati specifici, bloccare SMB cross-zone.
2. EDR + monitoring intensivo: agente che logga ogni connessione SMBv1, alert su pattern anomali, IDS Snort/Suricata in zona dedicata.
3. Sunset plan documentato: timeline esplicita per migrazione applicazione, accettazione rischio formale firmata da business owner, revisione trimestrale.
Extra: compensating in profondità (encryption rete via IPSec se possibile), privilege restriction (account che usano l'app non amministratori), backup offline isolato per scenario ransomware.
Il punto chiave: hardening non è "applica tutto o niente". CIS prevede esplicitamente eccezioni documentate con compensating controls equivalenti.
B · /etc/passwd, /etc/shadow, /etc/group
4identifica output

Anatomia di una riga shadow

Cosa puoi dedurre da questa riga di /etc/shadow?

alice:!$y$j9T$RjT5...$XKv...:19847:0:99999:7:::
Corretto. Il "!" prima dell'hash $y$ indica account locked: la password non è più validabile, l'utente non può loggarsi via password. Tipicamente impostato con passwd -l alice. L'hash sotto resterebbe yescrypt valido se sbloccato con passwd -u alice.
Non corretto. La risposta è b. Il prefisso "!" davanti all'hash è il marker di account locked. 19847 sono giorni dal 1/1/1970 dell'ultimo cambio password (campo 3), 99999 è il max age (campo 5, =mai scaduta).
5scelta multipla

Permessi corretti CIS L1

Quali sono i permessi corretti per /etc/shadow secondo CIS L1?

Corretto. 0640 root:shadow è il default Ubuntu corretto. Solo root scrive, root e membri del gruppo shadow leggono (necessario per programmi PAM-based come login, sudo). World-readable sarebbe disastroso: chiunque sul sistema potrebbe leggere e crackare offline tutti gli hash.
Non corretto. La risposta è c (640 root:shadow). L'hash di password non deve mai essere world-readable: il filesystem layout di Ubuntu di default è già conforme.
6aperta

Audit account anomali

Scrivi 3 comandi awk one-liner che cercano potenziali anomalie in /etc/passwd.

Mostra soluzione
awk -F: '$3==0 {print $1}' /etc/passwd
→ Account con UID 0 (deve essere SOLO root). Se ne trovi altri, è backdoor.

awk -F: '{print $3}' /etc/passwd | sort | uniq -d
→ UID duplicati (anomalia: due utenti con stesso UID si confondono nel filesystem).

awk -F: '$3<1000 && $7!~/nologin|false/ {print $1, $7}' /etc/passwd
→ Account di sistema (UID<1000) con shell di login attiva. Dovrebbero avere /sbin/nologin o /bin/false. Se hanno bash è errore di hardening (o backdoor).

Bonus: awk -F: '$2==""' /etc/shadow per password vuote (CIS L1 critico).
7scelta multipla

Algoritmo hashing moderno

Quale dei seguenti algoritmi hash trovati nel campo 2 di /etc/shadow è il default consigliato su Ubuntu 22.04+?

Corretto. yescrypt ($y$) è il default da Ubuntu 22.04 e Debian 11. È memory-hard (richiede RAM significativa per ogni hash) e resiste meglio alle GPU farm rispetto a SHA-512. MD5 ($1$) è deprecato. SHA-256/512 ($5$/$6$) sono ancora accettabili ma legacy.
Non corretto. La risposta è d (yescrypt). Verificalo sul tuo sistema: sudo head -1 /etc/shadow.
C · sudoers, sudoers.d, shell escape
8scelta multipla

Lettura riga sudoers

Cosa significa questa riga di sudoers?
%admin web01=(root) NOPASSWD: /usr/bin/systemctl restart nginx

Corretto. Il % davanti al nome indica gruppo (non utente). web01 è l'host (la regola si applica solo lì). (root) è il target user. NOPASSWD non chiede password al sudo. Il comando deve corrispondere ESATTAMENTE: systemctl restart nginx permesso, systemctl stop nginx NO.
Non corretto. La risposta è c. Il % identifica un gruppo, non un singolo utente. La sintassi sudoers è: chi host=(target_user) [NOPASSWD:] comando.
9scelta multipla

Pattern pericoloso

Quale di queste regole sudoers è MOLTO pericolosa per privilege escalation?

Corretto. find ha la flag -exec che permette esecuzione di comandi arbitrari come root. Esempio: sudo find . -exec /bin/sh \; -quit apre shell root immediata. È un pattern classico di GTFOBins. Le altre regole sono più sicure: a) script root-owned specifico, c) richiede password, d) cat di un file specifico (read-only).
Non corretto. La risposta è b. find con -exec è uno degli shell-escape binary più conosciuti. Mai dare NOPASSWD su binari generici come find, vim, awk, less, more, vi.
10aperta

Pattern sicuro per automazione

Devi configurare uno script di backup notturno che gira come backup_user e deve poter eseguire tar con permessi di root. Senza usare NOPASSWD su tar generico, qual è il pattern sicuro?

Mostra soluzione
Strategia 1 (preferita): wrapper script root-owned senza input esterni
1. Crea /usr/local/bin/run-backup.sh con shebang #!/bin/bash + set -euo pipefail
2. Dentro lo script, hardcodato: tar czf /backup/etc-$(date +%F).tar.gz /etc/
3. Permessi: chown root:root /usr/local/bin/run-backup.sh + chmod 0755
4. Sudoers: backup_user ALL=(root) NOPASSWD: /usr/local/bin/run-backup.sh
backup_user può solo eseguire QUEL preciso script senza parametri. Niente shell escape.

Strategia 2 (più moderna): systemd timer come root
Niente sudo, niente NOPASSWD. Lo script gira come root via systemd timer schedulato. Più pulito perché elimina del tutto il vettore sudo.

Strategia 3 (granulare): POSIX capabilities
setcap cap_dac_read_search+ep /usr/local/bin/tar-backup dà capability di lettura senza root pieno.

La regola: NOPASSWD solo su script specifici root-owned, mai su binari generici.

11scelta multipla

I 4 momenti di PAM

Quali sono i 4 tipi di stack PAM nel ciclo di vita di una sessione?

Corretto. Sono i 4 momenti del ciclo di vita. auth verifica chi sei (password, MFA). account verifica se puoi accedere ora (orari, account scaduto). password applica policy al cambio password. session setup/teardown sessione (mount home, ulimits, log).
Non corretto. La risposta è d. Per ogni servizio (sshd, sudo, login...) PAM ha uno stack di moduli per ognuno dei 4 tipi.
12aperta

Modulo pam_faillock

Spiega cosa fa pam_faillock e perché è importante per sicurezza.

Mostra soluzione
pam_faillock implementa il blocco account dopo N tentativi di autenticazione falliti consecutivi. Configurazione tipica in /etc/security/faillock.conf o nello stack PAM:
deny=5 = blocca dopo 5 fallimenti
unlock_time=900 = sblocco automatico dopo 15 minuti
fail_interval=900 = finestra temporale entro cui contare i fallimenti

Perché è critico: blocca attacchi brute force SSH automatici. Un attaccante che prova 10000 password al secondo viene fermato dopo 5 tentativi, deve aspettare 15 minuti, in pratica brute force impraticabile (50000 anni per password decente).

Limite: distributed brute force da botnet (1 tentativo per IP) può aggirare. Per quello servono fail2ban (block IP) o rate limit a monte.

Sostituisce il deprecato pam_tally2. È nello stack auth con due righe: preauth (controlla se già lockato) e authfail (incrementa contatore se auth fallisce).

SSH: priorità di hardening

Tra le seguenti, qual è la singola misura SSH più impattante per ridurre il rischio di compromissione?

Corretto. Disabilitare auth via password elimina del tutto la classe degli attacchi brute force online (90%+ del traffico SSH malevolo su Internet). Le chiavi pubbliche con passphrase sono ordini di grandezza più resistenti. Cambiare porta (a) è "security through obscurity", utile solo per ridurre rumore nei log. Banner (b) ha valore legale, non difensivo.
Non corretto. La risposta è c. La differenza tra password auth e key-only auth è la mitigazione di interi pattern d'attacco, non incrementale.
14scelta multipla

Mount option noexec

Cosa fa l'opzione di mount noexec applicata a una partizione?

Corretto. Tipicamente applicata a /tmp, /var/tmp, /dev/shm: il kernel blocca execve() su file in quella partizione. Mitiga il pattern classico "scarico exploit in /tmp ed eseguo". Caveat: alcuni installer/compilatori falliscono con noexec su /tmp. nosuid e nodev sono complementari.
Non corretto. La risposta è b. noexec non disabilita lettura, blocca solo l'esecuzione. Esempio: cat /tmp/script.sh funziona, /tmp/script.sh fallisce con "Permission denied".
15aperta

Bind mount vs partizione fisica

Spiega le differenze di sicurezza tra usare un bind mount con noexec/nosuid/nodev e avere una partizione fisica separata con le stesse opzioni.

Mostra soluzione
Identico: protezione runtime noexec/nosuid/nodev uguale (kernel applica le opzioni allo stesso modo).

Diverso (vantaggi partizione fisica):
1. Isolamento spazio disco: attaccante che riempie /tmp con bind mount esaurisce tutta la root partition (DoS sistema, log persi). Con partizione fisica si ferma a 5 GB.
2. Garanzia attivazione al boot: bind mount applicato post-boot, c'è finestra in cui /tmp è root partition senza protezioni. Partizione fisica montata dal kernel da subito.
3. Resistenza a remount malevolo: mount -o remount,exec /tmp più tracciabile su partizione fisica (auditd, AppArmor/SELinux).
4. Snapshot/backup granulari: LVM permette snapshot di /var/log indipendenti dal resto.
5. Encryption granulare: cifrare solo /home con LUKS richiede partizione separata.
6. Compliance CIS L1: richiede esplicitamente partizioni separate, accetta bind mount come compensating control documentato.

Quando bind mount è "abbastanza": laptop personale, server in produzione che non si vuole reinstallare. Per server enterprise nuovi: parti dal layout corretto.
F · auditd, Lynis, OpenSCAP
16scelta multipla

Lynis vs auditd: differenza

Quale affermazione descrive correttamente Lynis e auditd?

Corretto. Sono complementari, non alternativi. Lynis: scansione attiva una-tantum della configurazione, ~2 minuti, produce report con score. Domanda: "il sistema è configurato bene?". auditd: servizio always-on che logga eventi mentre accadono. Domanda: "cosa è successo sul sistema?".
Non corretto. La risposta è d. Lynis = configuration audit (snapshot stato), auditd = audit logging (registrazione continua eventi). Inversione tipica, attenzione.
17scelta multipla

OpenSCAP e CIS

OpenSCAP può scansionare un sistema secondo CIS Benchmark?

Corretto. OpenSCAP è motore SCAP generico. Profili STIG ufficiali da DISA, profili CIS-equivalent da ComplianceAsCode (collaborazione community/Red Hat, github.com/ComplianceAsCode/content). Per CIS strict-ufficiale serve CIS-CAT Pro (richiede SecureSuite membership). In pratica enterprise usano OpenSCAP+ComplianceAsCode per coverage senza costi licenza.
Non corretto. La risposta è c. OpenSCAP è agnostico al framework: scansiona qualunque profilo SCAP-compliant, inclusi quelli CIS-equivalent della community.
G · Windows: GPO, LAPS, BitLocker, PowerShell, Tier model
18scelta multipla

LAPS: scopo principale

Qual è il problema principale che LAPS (Local Administrator Password Solution) risolve?

Corretto. Senza LAPS, tutti i PC enterprise hanno tipicamente lo stesso admin locale (default da imaging). Compromissione di un PC = hash admin locale identico su 1000 altri PC = Pass-the-Hash diffuso. LAPS genera password univoca random per ogni PC, ruotata periodicamente, custodita in AD con ACL. Hash diverso per macchina, lateral movement bloccato.
Non corretto. La risposta è b. LAPS è una difesa specifica contro Pass-the-Hash via account admin locale, scenario tipico in attacchi enterprise post-compromise.
19scelta multipla

BitLocker: cosa NON protegge

BitLocker con TPM+PIN protegge il disco. Quale di queste minacce NON è mitigata da BitLocker?

Corretto. BitLocker protegge il dato a riposo (PC spento), non in uso (PC acceso). Quando l'OS gira, i file sono decifrati al volo per essere usati: malware in esecuzione vede dati in chiaro come l'utente legittimo. BitLocker è complementare a hardening software, non sostitutivo. Defense in depth: layer diversi per minacce diverse.
Non corretto. La risposta è c. BitLocker non c'entra niente con malware su PC acceso: l'OS è già caricato, la chiave è in memoria, i file sono decifrati. Per il malware servono altre difese (EDR, hardening OS, AppLocker).
20aperta

Tier Model: scenario

Sei admin di un'azienda con 1 Domain Controller, 50 server, 1000 workstation. Spiega come applicheresti il Tier Model di Microsoft per limitare lateral movement, e cosa NON deve mai succedere.

Mostra soluzione
Tier 0 (Domain Controller, PKI, sistemi di gestione identità): account admin "DA-tier0" che si logga SOLO su DC, da PAW (Privileged Access Workstation) dedicata. Mai su server applicativi, mai su workstation.

Tier 1 (server applicativi: file server, app server, DB): account "SA-tier1" si logga su server, mai su workstation, mai su DC.

Tier 2 (workstation utenti): account helpdesk "WA-tier2" si logga sulle workstation per supporto, mai su server o DC.

Cosa NON deve mai succedere:
1. Domain Admin che si logga su workstation: se la workstation è compromessa, Mimikatz dump LSASS → hash domain admin in memoria → attacco prende il dominio. È il pattern N°1 di compromissione AD.
2. Tier 0 admin che si logga via RDP a server applicativo: idem, hash high-tier finisce su server tier-1.
3. Account admin condivisi tra tier: tipo "admin@dominio" usato per tutto. Singolo account compromesso = compromise tutti i tier.

Mitigazione tecnica: Authentication Policy Silos in AD impediscono fisicamente che account tier-0 si loggino fuori dal proprio tier. Combinato con LAPS (admin locali per macchina), microsegmentazione (slide L5), credential guard (LSASS protetto), forma il pattern enterprise standard contro lateral movement.

Il Tier Model è la difesa organizzativa contro Pass-the-Hash. La defense in depth richiede tutte: identità separate (Tier), tecnica (LAPS, Credential Guard), rete (microsegmentazione).
