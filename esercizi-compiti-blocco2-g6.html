Hypervisor type 1 vs type 2

Cerca e spiega la differenza fondamentale tra hypervisor type 1 (bare-metal) e type 2 (hosted). Fai 2 esempi per ciascuno e indica quando usare l'uno e quando l'altro.

Cosa cercare
Type 1 (bare-metal): gira direttamente sull'hardware senza OS sottostante. Esempi: VMware ESXi, Microsoft Hyper-V (Server), KVM (in modalità native), Xen, Proxmox VE. Uso: datacenter, cloud provider, produzione enterprise.
Type 2 (hosted): gira come applicazione sopra un OS host. Esempi: VirtualBox, VMware Workstation, Parallels Desktop, UTM (Mac). Uso: sviluppo, testing, lab personali, corso di cybersecurity come il nostro.
Differenza fondamentale: overhead e isolamento. Type 1 accede direttamente ad hardware (performance vicine al bare-metal), type 2 passa attraverso OS host (più overhead, più superficie di attacco).
Noi abbiamo usato VirtualBox (type 2) in tutto il corso perché è pratico su laptop personale.
2

Container vs VM

In max 5 righe: che differenza strutturale c'è tra una VM e un container Docker? Perché i container sono più "leggeri"?

Cosa cercare
Una VM virtualizza l'intero stack hardware: CPU, RAM, disco, rete, e ospita un OS completo con kernel proprio. Un container condivide il kernel dell'host e virtualizza solo lo spazio utente (processi, filesystem, network namespace) isolato tramite cgroups e namespaces Linux. Risultato: una VM pesa GB e parte in decine di secondi (deve bootare OS), un container pesa MB e parte in millisecondi (nessun boot). Trade-off: VM hanno isolamento più forte (kernel separato = surface di attacco ridotta), container condividono kernel (un kernel exploit può impattare tutti i container).
3

Security implications dei container

Elenca 3 differenze di sicurezza tra container e VM, con implicazioni per la difesa.

Cosa cercare
1. Kernel condiviso: se l'attaccante rompe l'isolamento del container (escape via CVE kernel o container runtime), ottiene accesso all'host e a tutti gli altri container. VM: un escape richiede hypervisor CVE (molto più rare).
2. Superficie ridotta ma immutabile: container (best practice) sono distroless o minimal = meno tool, meno CVE. Ma sono anche immutabili, quindi patch = rebuild image + redeploy (non live patch).
3. Trust chain dell'immagine: container è l'image. Se pulla da Docker Hub un'immagine malevola (typosquatting, supply chain attack), sei dentro. Servono image signing (Docker Content Trust, Sigstore) e registry privati con scanning (Trivy, Clair).
Difesa container-specific: run as non-root, read-only filesystem, drop capabilities, seccomp/AppArmor profile, network policy K8s, image scanning in CI.

SQL vs NoSQL

Quando si sceglie un database SQL (RDBMS) e quando uno NoSQL? Fai un esempio per ciascuno.

Cosa cercare
SQL (RDBMS: PostgreSQL, MySQL, MS SQL, Oracle):
• Quando: dati con schema rigido e relazioni, transazioni ACID (banche, ecommerce, ERP), reportistica complessa (JOIN multipli).
• Esempio: ordini ecommerce con righe, pagamenti, clienti, prodotti → tabelle con foreign key, transazioni che garantiscono coerenza.
NoSQL (MongoDB, DynamoDB, Redis, Cassandra):
• Quando: schema flessibile, alta scalabilità orizzontale, dati document-based o key-value, eventuale consistency accettabile.
• Esempio: catalogo prodotti marketplace con schemi variabili, cache sessioni utente, log/event storage ad alto volume.
Regola pratica: se non sai cosa scegliere, parti con SQL. È maturo, standard, la maggior parte dei casi business rientra lì. NoSQL è giustificato quando hai un vincolo specifico (scala, schema dinamico).
5

ACID in breve

Che significano A, C, I, D in ACID? Perché sono importanti per un database bancario?

Cosa cercare
Atomicity: la transazione è tutto-o-niente. Bonifico da A a B = addebito A + accredito B, entrambi o nessuno.
Consistency: la transazione porta il DB da uno stato valido a un altro stato valido (rispetta vincoli: saldi non negativi, integrità referenziale).
Isolation: transazioni concorrenti non si vedono tra loro (dipende dal isolation level: READ COMMITTED, REPEATABLE READ, SERIALIZABLE).
Durability: una volta commit, i dati sopravvivono a crash (scritti su disco, write-ahead log).
Per la banca: senza Atomicity, un crash durante bonifico lascia un cliente con soldi in meno e l'altro senza accredito. Senza Isolation, due bonifici simultanei dallo stesso conto potrebbero entrambi vedere saldo sufficiente e scoperto impossibile diventa possibile. ACID è il motivo per cui i sistemi bancari storicamente sono SQL.
6

SQL Injection: anatomia

Cerca la definizione di SQL Injection (SQLi) e fai un esempio minimo di query vulnerabile in qualunque linguaggio. Indica 2 difese concrete.

Cosa cercare
SQLi: vulnerabilità in cui input utente non sanitizzato viene concatenato in una query SQL, permettendo all'attaccante di modificare la logica della query.
Esempio vulnerabile (Python, anti-pattern):
query = f"SELECT * FROM users WHERE name='{user_input}'"
Se user_input = ' OR '1'='1, la query diventa SELECT * FROM users WHERE name='' OR '1'='1' — sempre vera, restituisce tutti gli utenti.
Difese:
1. Prepared statements / parametrized queries: il driver SQL separa query e parametri, l'input non può alterare la struttura. cursor.execute("SELECT * FROM users WHERE name=%s", (user_input,))
2. ORM (SQLAlchemy, Django ORM, Hibernate): genera prepared statements sotto il cofano, le query nativamente safe.
3. WAF (L3 ricordi?) in aggiunta come difesa esterna.
4. Principio least privilege DB: l'utente applicativo NON ha DROP TABLE o admin.

Esegui 3 container attivi

Entra dentro un container

Usa podman exec -it per aprire una shell nel container nginx e mostra il contenuto di /etc/os-release. Che distribuzione Linux gira dentro?

Soluzione
podman exec -it web sh (nginx:alpine usa sh, non bash)
Dentro il container:
cat /etc/os-release
Output tipico:
NAME="Alpine Linux"
VERSION_ID=3.20.x...

Poi: ps → vedi solo i processi del container (nginx master + worker), NON i processi dell'host. Questo è il network/pid namespace in azione.
exit per tornare all'host.
Curiosità: whoami dentro nginx:alpine risponde "root" — nginx gira come root di default, ANTI-PATTERN per sicurezza (vedremo in L8 come cambiarlo).

OWASP SQLi Cheat Sheet

Leggi (30 min) OWASP SQL Injection Prevention Cheat Sheet. Rispondi: quali sono le 4 "Primary Defenses" elencate?

Soluzione
Defense 1: Use of Prepared Statements (with Parameterized Queries).
Defense 2: Use of Stored Procedures (con parametri).
Defense 3: Allow-list Input Validation (whitelisting, mai blacklisting).
Defense 4: Escaping All User-Supplied Input (ultima spiaggia, framework-specific).

Additional defenses: Least Privilege (DB user con permessi minimi), White List Input Validation.
Takeaway: la prima difesa (prepared statements) copre il 99% dei casi. Le altre sono complementari o per casi legacy.

Docker Security Cheat Sheet

Leggi (20 min) OWASP Docker Security Cheat Sheet. Elenca 5 best practice.

Soluzione
1. Keep Host and Docker up to date (CVE del runtime).
2. Do NOT expose Docker daemon socket (/var/run/docker.sock) — chi lo ha = root sull'host.
3. Set user in Dockerfile (USER 1000) — no container as root.
4. Limit capabilities (--cap-drop=ALL --cap-add=NET_BIND_SERVICE).
5. Read-only filesystem (--read-only) e volumi temporanei specifici.
6. No privileged mode (--privileged) salvo casi eccezionali e giustificati.
7. Use trusted base images (ufficiali, firmate, scansionate).
8. Scan images (Trivy, Snyk, Docker Scout).
9. Use multi-stage builds per ridurre superficie.
10. Don't store secrets in images — usa secret manager / env vars runtime.
13

Encryption at rest

Cerca "Transparent Data Encryption" (TDE): che problema risolve e come si integra tipicamente con PostgreSQL/MySQL/SQL Server?

Cosa cercare
Problema: i file del database (data files su disco) sono in chiaro. Se l'attaccante ruba fisicamente il disco, o ha accesso al filesystem senza passare dal DB engine, legge tutto. Encryption at rest cifra i file.
TDE (Transparent Data Encryption): il DB engine cifra/decifra trasparentemente tra RAM e disco, chiave custodita in key management system esterno. L'applicazione non sa niente, query normali.
Implementazioni:
• SQL Server: TDE nativo Enterprise edition, chiavi in Service Master Key o Azure Key Vault.
• PostgreSQL: no TDE nativo (!), alternative: crittografia filesystem (LUKS, dm-crypt), oppure pgcrypto per campi specifici.
• MySQL: InnoDB tablespace encryption da 5.7+, con keyring plugin.
Cloud managed: tutti i DBaaS (RDS, Azure SQL) hanno encryption at rest di default via KMS/Key Vault.
Limiti: encryption at rest NON protegge da SQL injection o query leciti — quando il DB è acceso, i dati sono accessibili via query.

Backup 3-2-1

Cerca la regola "3-2-1" per backup. Applicala a un database PostgreSQL aziendale.

Soluzione
Regola 3-2-1:
3 copie totali dei dati (originale + 2 backup).
2 media di storage diversi (disco + nastro, o disco locale + cloud).
1 copia offsite (fuori dal datacenter/ufficio).

Applicazione a PostgreSQL aziendale:
1. Dati live sul server DB primario (copia 1, media disco locale).
2. Backup incrementale giornaliero con pgBackRest o Barman su storage dedicato on-premise (copia 2, media diverso/NAS).
3. Backup settimanale copiato su cloud storage (S3/Azure Blob) con encryption + lifecycle policy (copia 3, offsite).
Test di restore: almeno mensile (il backup non testato non esiste).
Evolution moderna: 3-2-1-1-0 (aggiunge copia offline/air-gapped + 0 errori durante restore test). Serve contro ransomware che cerca e cripta anche i backup online.

GDPR minimi

In 4-5 frasi: cosa richiede il GDPR (GDPR = Regolamento UE 2016/679) a chi gestisce database con dati personali di cittadini EU?

Cosa cercare
Il GDPR impone principi di data protection by design and by default: le misure di sicurezza devono essere progettate nel sistema fin dall'inizio (non aggiunte dopo). Richiede: (1) minimizzazione — raccogliere solo i dati necessari per lo scopo dichiarato; (2) encryption at rest e in transit come misura tecnica di protezione; (3) pseudonimizzazione dove possibile (sostituire dati identificativi con pseudonimi); (4) right to erasure ("diritto all'oblio") — l'utente può chiedere la cancellazione; (5) data breach notification entro 72 ore a Garante Privacy; (6) access control con least privilege e audit log. Le sanzioni arrivano a 20M€ o 4% del fatturato mondiale. La GDPR compliance è un driver tecnico fortissimo per architetture database moderne.

Scenario integrato M1 → M2

Connetti M1 con M2: progetta (in 5-6 punti) come metteresti in sicurezza il container PostgreSQL dell'esercizio 9, usando i principi del Modulo 1.

Soluzione tipica
1. Microsegmentazione (L5): il container DB deve essere raggiungibile SOLO dal container applicativo, non da altri pod. In K8s = NetworkPolicy con selector per-pod. In Docker Compose = user-defined network con policy.
2. Hardening (L6): il container NON gira come root (USER postgres nel Dockerfile, o --user a runtime). Filesystem read-only dove possibile.
3. Defense in depth: TLS per connessione client-DB (non in chiaro), password non in env vars in chiaro ma in secret manager, encryption at rest a livello storage.
4. Identità > IP: DB user separati per ogni applicazione con permessi specifici (least privilege), non un singolo superuser.
5. Log è tutto: audit log delle query critiche (DELETE, UPDATE su tabelle sensibili), log inviati a SIEM esterno (non solo nel container ephemeral).
6. Automazione: deploy via Helm/Terraform con policy-as-code (OPA che blocca container DB esposti pubblicamente), scanning immagine in CI.
Questo è il ponte pratico tra M1 e M2: stessi principi, nuovo dominio di applicazione.
