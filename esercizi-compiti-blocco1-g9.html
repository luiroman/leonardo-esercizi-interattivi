A · MongoDB injection
1

Definisci operator injection in 3 righe

Scrivi cos'è "operator injection" in MongoDB e perché differisce dalla SQL injection.

Mostra soluzione
L'operator injection sfrutta il fatto che le query MongoDB sono oggetti JSON-like: una chiave può essere un campo (es. username) o un operatore (es. $ne). Se l'app accetta come valore di un campo un oggetto invece di un primitive, l'attaccante trasforma il valore in operatore. Differisce dalla SQL injection perché qui non c'è interpolazione di stringhe né eval di SQL: il payload sfrutta la tipizzazione debole del parsing JSON e la fiducia del driver nei tipi.
2

I 5 operatori e il loro abuso

Compila la tabella associando ogni operatore al suo uso malevolo tipico:

  • $ne — ?
  • $gt / $lt — ?
  • $regex — ?
  • $exists — ?
  • $where — ?
Mostra soluzione
$ne → bypass condizioni di confronto (es. password). $gt/$lt → bypass su campi numerici/stringa (es. role > "u" matcha "user","v","w","x","y","z"). $regex → enumeration carattere per carattere via timing/response. $exists → discovery dello schema (campi nascosti, soft-delete). $where → esecuzione JS server-side, RCE-like, DoS via loop infiniti.
3

Trova l'attacco

Endpoint:

app.post("/reset", async (req,res) => {
  const u = await db.users.findOne({email: req.body.email})
  if (u) sendResetEmail(u.email)
  res.json({sent: true})  // sempre true per non rivelare
})

Quale payload permette di scoprire un email valido?

Mostra soluzione
{"email":{"$regex":"@gmail\\.com$"}} ritorna il primo utente con dominio gmail. Combinato con timing (sendResetEmail impiega tempo se trova l'utente, è veloce se non lo trova) → leak. Il res.json({sent:true}) finto è inutile contro questo attacco perché il timing rivela il match. Difesa: type check + sanitize + rate limiting.
4

Disabilita $where

Come si disabilita globalmente l'esecuzione di $where in MongoDB self-hosted?

Mostra soluzione
Avviare MongoDB con --noscripting oppure aggiungere in mongod.conf: 
security:
  javascriptEnabled: false
Disabilita anche $accumulator, $function in aggregation, mapReduce. È una scelta drastica ma corretta: codice nuovo non dovrebbe mai usare scripting server-side. Atlas lo disabilita di default in tier < M10.
B · Difesa MongoDB
5

I 4 layer in ordine

Elenca i 4 layer di difesa MongoDB nell'ordine in cui interceptano una richiesta HTTP malevola.

Mostra soluzione
1. Sanitize globale (express-mongo-sanitize) → rimuove chiavi $ in body/query/params PRIMA di tutto. 2. Validator schema (Zod/Joi) → middleware che valida tipo+struttura PRIMA del controller. 3. Type check inline nel controller → fail-fast finale. 4. Mongoose schema validation → casts e rifiuta tipi incompatibili al momento del save. L'ordine in cui un attacco trova le difese: sanitize → Zod → type check → Mongoose. Ognuno copre un caso che gli altri possono mancare.
6

Zod schema

Scrivi uno schema Zod per POST /transfer che riceve {from: "uuid", to: "uuid", amount: number, note: string opzionale max 200 caratteri}.

Mostra soluzione
import { z } from "zod"
const transferSchema = z.object({
  from: z.string().uuid(),
  to: z.string().uuid(),
  amount: z.number().positive().finite(),
  note: z.string().max(200).optional()
}).strict()  // rifiuta chiavi extra
.strict() è importante: senza, Zod ignora chiavi extra. Con strict, qualsiasi chiave non dichiarata fa fallire la validazione → defense-in-depth contro injection di campi inattesi.
7

Express-mongo-sanitize: trade-off

Quali sono 3 limiti di express-mongo-sanitize che lo rendono insufficiente come unica difesa?

Mostra soluzione
1. Maintenance status incerto: la libreria non riceve update da tempo, ci sono fork e alternative (mongo-sanitize, express-validator). 2. NON sostituisce schema validation: rimuove $ ma non valida che amount sia un numero positivo. 3. Falsi positivi su campi che legittimamente contengono $ (es. shop pricing, simboli valuta). 4. Difesa "ultima linea": arriva troppo tardi rispetto a un schema validator che fail-fast prima del controller. Resta utile come safety net globale, mai come unico baluardo.
C · Altri NoSQL
8

Redis ACL · scrivi la regola

Crea un utente Redis chiamato cache_app con password secret123 che può fare solo GET/SET/DEL su chiavi che iniziano per session:, e nient'altro.

Mostra soluzione
ACL SETUSER cache_app on >secret123 ~session:* +get +set +del
Decomposizione: on = abilita, >secret123 = password, ~session:* = pattern chiavi consentite, +get +set +del = comandi consentiti. Tutti gli altri comandi sono vietati di default. Verificare con ACL LIST e ACL WHOAMI dopo il login.
9

Cassandra: la tua difesa

Hai un'app Java che usa cassandra-driver. Quale API garantisce automaticamente l'escape dei parametri e impedisce CQL injection?

Mostra soluzione
Le prepared statement: 
PreparedStatement ps = session.prepare(
  "SELECT * FROM users WHERE id = ?");
ResultSet rs = session.execute(ps.bind(userId));
La sintassi è identica a JDBC. Il driver invia il template SQL al cluster Cassandra una volta sola, poi invia i parametri separati come binari. Non c'è interpolazione testuale → niente injection. Da evitare: session.execute("SELECT * FROM users WHERE id = " + userId) — è la forma vulnerabile classica.
10

Elasticsearch: object building

Riscrivi questo codice ES vulnerabile in versione sicura:

const body = `{"query":{"match":{"title":"${userInput}"}}}`
es.search({index: "products", body: JSON.parse(body)})
Mostra soluzione
Costruire l'oggetto JSON direttamente, senza concatenazione di stringhe: 
const body = {
  query: {
    match: { title: userInput }
  }
}
es.search({index: "products", body})
Il client driver serializza l'oggetto in JSON in modo sicuro: userInput è un valore string, non parte della struttura. Inoltre validare con Zod che userInput sia z.string().max(200) per evitare query DoS con regex enormi.
D · pgAudit
11

Setup pgAudit minimale

Scrivi i 4 comandi necessari per attivare pgAudit con session audit per ROLE+DDL su un PostgreSQL fresco.

Mostra soluzione
-- 1. carica libreria (richiede restart)
ALTER SYSTEM SET shared_preload_libraries = 'pgaudit';
-- ora restart Postgres: pg_ctl restart

-- 2. crea extension nel DB target
CREATE EXTENSION pgaudit;

-- 3. configura classi auditate
ALTER SYSTEM SET pgaudit.log = 'role, ddl';

-- 4. ricarica config (no restart richiesto)
SELECT pg_reload_conf();
12

Le 7 classi a memoria

Elenca le 7 classi di eventi pgAudit con un esempio di statement per ognuna.

Mostra soluzione
  • READ: SELECT, COPY FROM
  • WRITE: INSERT, UPDATE, DELETE
  • FUNCTION: chiamata a funzione, blocchi DO
  • ROLE: GRANT, REVOKE, CREATE ROLE
  • DDL: CREATE/ALTER/DROP TABLE/INDEX/VIEW
  • MISC: DISCARD, FETCH, CHECKPOINT
  • MISC_SET: SET parameter (ad es. SET row_security = off)
Setup minimo always-on: 'role, ddl'. Per dati sensibili aggiungere object audit invece di session-level 'read,write'.
13

Session vs Object

Spiega in 2 frasi la differenza tra session audit e object audit, e indica quando usare uno o l'altro.

Mostra soluzione
Session audit logga in base alla CLASSE dell'evento (pgaudit.log = 'read,write'); è facile da configurare ma genera molto rumore se attivato per READ/WRITE su DB ad alto traffico. Object audit logga in base all'OGGETTO toccato, configurato via un ruolo dedicato con grant solo sulle tabelle sensibili (pgaudit.role = 'audit_role'); ha alto signal-to-noise ma richiede pianificazione iniziale.

Usa session per le classi "always-on" (ROLE, DDL — bassi volumi). Usa object per dati sensibili specifici (PII, financial, salaries).
14

Parsa questo log

Anatomizza questo entry pgAudit campo per campo:

AUDIT: OBJECT,7,3,WRITE,DELETE,TABLE,public.salaries,
DELETE FROM salaries WHERE department='HR',<not logged>
Mostra soluzione
  • OBJECT → tipo audit (object-level via grant a audit_role)
  • 7 → audit ID (sequence number nella sessione)
  • 3 → statement ID (nel batch)
  • WRITE → classe pgAudit
  • DELETE → comando SQL
  • TABLE → tipo oggetto
  • public.salaries → schema.oggetto qualificato
  • DELETE FROM salaries WHERE department='HR' → testo query
  • <not logged> → valori parametri non loggati per privacy
Eventi DELETE su tabelle sensibili come salaries dovrebbero sempre triggerare alert SIEM, indipendentemente dall'utente.
E · Row-Level Security
15

RLS in 3 frasi

Definisci Row-Level Security in massimo 3 frasi, evidenziando il salto rispetto all'authorization in app layer.

Mostra soluzione
RLS è una feature PostgreSQL che applica un predicato di filtro a livello di riga direttamente sulla tabella, valutato dal DBMS automaticamente per ogni query. Sposta authorization da app layer a DB layer: lo sviluppatore può scrivere SELECT * FROM orders e il DB applica il WHERE in modo automatico. Il vantaggio è defense-in-depth: anche se l'app dimentica un filtro, anche se un tool di reporting si connette al DB, anche se una migration tocca i dati, la policy è inevitabile.
16

USING vs WITH CHECK

Quando uso solo USING? Quando devo aggiungere WITH CHECK? Fai un esempio in cui omettere WITH CHECK porta a un bug.

Mostra soluzione
USING filtra le righe ESISTENTI (lettura, update target, delete). WITH CHECK valida le righe NUOVE (insert, update target post-modifica).

Bug se ometti WITH CHECK: in una tabella orders(user_id, ...) con policy USING (user_id = current_user_id()), l'utente A può fare INSERT INTO orders (user_id, ...) VALUES (B_id, ...). La policy USING non si applica all'insert. La riga viene creata "appartenente" a B. Subito dopo, A non la vede più (USING la filtra). Risultato: A può creare ordini su conti di altri utenti, e poi non li vede più — perfetto per frode.

Fix: aggiungere WITH CHECK (user_id = current_user_id()). Per multi-tenant, USING e WITH CHECK quasi sempre identici.
17

FORCE RLS · trappola del proprietario

Spiega in 2 frasi perché il proprietario di una tabella bypassa RLS by default, e quali sono le 2 mitigazioni.

Mostra soluzione
PostgreSQL bypassa RLS per il proprietario della tabella (chi l'ha creata) per evitare lock-out: se il DBA crea la tabella e poi una policy mal scritta lo esclude, deve poter intervenire. Il problema è che molte app si connettono come proprietario per comodità → RLS è di fatto disattivato.

Mitigazioni: (1) ALTER TABLE invoices FORCE ROW LEVEL SECURITY applica RLS anche al proprietario. (2) Separazione architetturale: ruolo schema_owner per migrations/DDL, ruolo app_role non-proprietario per CRUD. La (2) è la best practice; FORCE RLS è la safety net.
18

Defense in depth · 4 layer

Elenca i 4 layer di defense-in-depth per un'app PostgreSQL hardened. Per ogni layer indica DOVE vive (app/boundary/DB).

Mostra soluzione
  • L1 · Input validation → APP LAYER. Type check, schema validation (Zod/Joi).
  • L2 · Parametri sicuri → APP-DB BOUNDARY. Prepared statement, ORM type-safe.
  • L3 · Authorization RLS → DB LAYER. Policy a livello riga, FORCE RLS, ruoli separati.
  • L4 · Audit pgAudit → DB LAYER. Detection + forensic trail (object audit per dati sensibili).
I 4 layer sono indipendenti. L1+L2 li abbiamo costruiti in L8 (SQL injection). L3+L4 sono ciò che PG aggiunge per chiudere il gap. Un attaccante deve bucare TUTTI E 4 i layer per arrivare ai dati.
