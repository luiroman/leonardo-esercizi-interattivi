A · Anatomia della SQL injection
1

Definisci SQL injection in 3 frasi

Senza guardare risorse, definisci SQL injection spiegando le 3 condizioni necessarie perché avvenga.

Esempio soluzione
SQL injection è una classe di vulnerabilità in cui un attaccante inietta codice SQL arbitrario in una query, sfruttando input utente non sanitizzato. Le 3 condizioni necessarie sono: (1) input controllato dall'utente, (2) flusso di quell'input verso una query SQL costruita dinamicamente, (3) assenza di parametrizzazione o validazione. Tutte e tre devono essere presenti perché l'attacco funzioni.
2

Leggi il codice Python · trova la vulnerabilità

Questo endpoint Flask è vulnerabile a SQL injection. Spiega come.

@app.post("/login")
def login():
    user = request.form["user"]
    pwd = request.form["pwd"]
    q = "SELECT * FROM users WHERE name='" + user + "' AND pwd='" + pwd + "'"
    r = cursor.execute(q).fetchone()
    if r: return "Benvenuto " + r["name"]
    return "Login failed", 401
Soluzione
La query è costruita per concatenazione di stringhe: l'input dell'utente viene inserito direttamente nella query senza parametrizzazione. Un attaccante invia: 
user = admin' OR '1'='1' --
pwd  = qualsiasi
La query finale diventa: 
SELECT * FROM users WHERE name='admin' OR '1'='1' --' AND pwd='qualsiasi'
Il -- commenta il resto. La clausola WHERE name='admin' OR '1'='1' è sempre vera. Il fetchone() restituisce il primo record della tabella — tipicamente admin — e l'attaccante è loggato senza conoscere la password.

Fix: prepared statement con placeholder %s e tupla di parametri.
3

OWASP Top 10 · posizione Injection

Leggendo OWASP Top 10 2021: in che posizione è Injection? Quale era la posizione nel 2017? Cosa ha cambiato?

Soluzione
OWASP Top 10 2021: Injection è A03 (terza posizione).
OWASP Top 10 2017: Injection era A01 (prima posizione).

Il cambiamento 2017→2021: Injection è scesa al 3° posto perché (a) prepared statement e ORM sono più diffusi, (b) i linguaggi moderni rendono la concatenazione meno idiomatica, (c) i WAF intercettano pattern noti. Al primo posto è salita Broken Access Control (A01:2021), che copre vulnerabilità IDOR e misconfiguration di autorizzazione. Injection resta comunque una delle vulnerabilità più impattanti.
B · Tipi di SQL injection
4

Tassonomia SQLi · 4 tipi

Elenca i 4 tipi principali di SQL injection e spiega come l'attaccante recupera le informazioni in ognuno.

Soluzione
1. In-band error-based: l'attaccante sfrutta messaggi di errore del DB per estrarre dati. L'app mostra l'errore al client.

2. In-band UNION-based: l'attaccante appende una UNION SELECT che legge dati da altre tabelle. Richiede stessa column count e type compatibility.

3. Blind boolean-based: nessun output diretto. L'attaccante chiede condizioni vero/falso (AND SUBSTR(password,1,1)='a') e inferisce dal fatto che la risposta cambia (200 OK o pagina diversa).

4. Blind time-based: nessun output, nessuna differenza visibile nella risposta. L'attaccante usa AND SLEEP(5) (MySQL) o AND pg_sleep(5) (PG) e misura se la risposta è istantanea (falso) o ritardata (vero). Estremamente lento ma funziona quasi sempre.
5

Payload time-based · scrivi uno

Scrivi un payload time-based per PostgreSQL che "pinga" il server se l'utente admin esiste nella tabella users. L'iniezione è in un parametro ?id=1 della URL, query presumibilmente SELECT * FROM products WHERE id = '$id'.

Soluzione
?id=1' AND (SELECT CASE WHEN (SELECT count(*) FROM users WHERE name='admin')>0 THEN pg_sleep(5) ELSE pg_sleep(0) END)--
URL-encoded: 
?id=1%27%20AND%20(SELECT%20CASE%20WHEN%20...)
Logica: se l'utente admin esiste, la query fa pg_sleep(5) (5 secondi di ritardo). Se no, pg_sleep(0), risposta istantanea. L'attaccante misura il tempo di risposta e inferisce.

Automazione: sqlmap fa questo automaticamente, migliaia di query per enumerare byte per byte.
6

UNION-based · quante colonne?

Spiega la tecnica "ORDER BY" usata dagli attaccanti per trovare il numero di colonne prima di scrivere una UNION-based injection. Perché è necessaria?

Soluzione
Per fare una UNION SELECT valida, l'attaccante deve sapere quante colonne ha la query originale (e quali tipi sono compatibili). Senza corrispondenza, il DB restituisce errore.

Tecnica incrementale ORDER BY N: 
?id=1' ORDER BY 1--   # OK
?id=1' ORDER BY 2--   # OK
?id=1' ORDER BY 3--   # OK
?id=1' ORDER BY 4--   # Errore: "ORDER BY position 4 is out of range"
L'attaccante ha scoperto: 3 colonne.

Poi costruisce la UNION: 
?id=1' UNION SELECT null, null, null--   # test compatibilità types
?id=1' UNION SELECT name, password, null FROM users--
Senza questa calibrazione, l'injection UNION fallisce subito.

sqlmap · workflow 5 step

Descrivi il workflow tipico di sqlmap contro un target (ipotetico, autorizzato). 5 step dall'identificazione al dump.

Soluzione
# 1. Detect: ha iniezione vulnerabile?
sqlmap -u "http://target/page.php?id=1" --batch

# 2. Enumerate databases
sqlmap -u "http://target/page.php?id=1" --dbs

# 3. Enumerate tables di un DB
sqlmap -u "http://target/page.php?id=1" -D dvwa --tables

# 4. Enumerate columns di una tabella
sqlmap -u "http://target/page.php?id=1" -D dvwa -T users --columns

# 5. Dump dei dati + tentativo crack password
sqlmap -u "http://target/page.php?id=1" -D dvwa -T users --dump --passwords
Flag utili:
• --cookie "PHPSESSID=..." se l'app richiede sessione autenticata
• --data "param=val" per POST
• --level 5 --risk 3 per test più aggressivi
• --os-shell se ottiene capabilities per shell sull'OS (scalare al sistema)

Etica: mai su target non autorizzati.

Prepared statements · scrivi il fix Python

Riscrivi il codice vulnerabile dell'esercizio 2 usando prepared statement con la libreria psycopg2 (o psycopg3).

Soluzione
@app.post("/login")
def login():
    user = request.form["user"]
    pwd = request.form["pwd"]
    # Prepared statement con placeholder %s
    q = "SELECT id, name FROM users WHERE name = %s AND pwd_hash = %s"
    cursor.execute(q, (user, pwd_hash(pwd)))
    r = cursor.fetchone()
    if r: return f"Benvenuto {r['name']}"
    return "Login failed", 401
Perché funziona: %s è un placeholder che il driver DB tratta come parametro binario separato dalla query. L'input utente non viene interpretato come SQL, ma sempre come valore. Qualsiasi cosa contenga (quote, --, UNION, OR 1=1) viene trattato come stringa letterale.

Nota bonus: la password non va mai in chiaro nel DB, deve essere hash con bcrypt/argon2 e confrontata con check_password(). Qui è semplificato per focus SQLi.
11

Le 5 difese · descrivile

Le 5 difese principali contro SQL injection (difesa in profondità). Elencale con una frase di descrizione.

Soluzione
1. Prepared statements / parametrized queries: LA difesa numero uno. I parametri sono separati dal template SQL. Usata con psycopg2, pg (Node), JDBC PreparedStatement.

2. ORM e query builder: libreries come SQLAlchemy, Django ORM, Prisma, Sequelize, JPA usano prepared statements automaticamente. Attenzione a raw()/execute_raw() che bypassano la protezione.

3. Input validation con allowlist: accetta solo valori noti buoni (regex, type check, whitelist enumerati). NON blocklist (attaccanti aggirano con encoding).

4. Least privilege al DB: il DB user dell'app non deve essere superuser. Solo SELECT/INSERT/UPDATE/DELETE sulle tabelle necessarie. Nessun DROP, nessun GRANT.

5. WAF (Web Application Firewall): ispeziona HTTP e blocca pattern SQLi noti. Difesa in profondità, mai sostituto di 1-4. Esempi: AWS WAF, Cloudflare, ModSecurity, CoraZa.

Least privilege · crea user app PostgreSQL

Scrivi i comandi SQL per creare un DB user appuser con la password AppPa$$2026 e permessi minimi: può solo SELECT/INSERT/UPDATE/DELETE sulla tabella orders del database shop. Niente DROP, niente CREATE, niente access ad altre tabelle.

Soluzione
-- Eseguire come superuser postgres
CREATE USER appuser WITH PASSWORD 'AppPa$$2026'
    NOSUPERUSER NOCREATEDB NOCREATEROLE;

-- Connect al DB shop
\c shop

-- Revoke tutto su public schema (PG default è troppo permissivo)
REVOKE ALL ON ALL TABLES IN SCHEMA public FROM appuser;
REVOKE ALL ON SCHEMA public FROM appuser;

-- Grant minimo sulla tabella orders
GRANT USAGE ON SCHEMA public TO appuser;
GRANT SELECT, INSERT, UPDATE, DELETE ON orders TO appuser;

-- Se la tabella usa sequenze (es. id SERIAL), servono anche:
GRANT USAGE, SELECT ON SEQUENCE orders_id_seq TO appuser;

-- Verifica
\du appuser
-- Non deve mostrare "Superuser" né "Create role"

-- Test: connect come appuser, prova DROP TABLE
-- Dovrebbe fallire: "permission denied"
Callback M1: principio del minimo privilegio. Un'eventuale SQLi con questo user non può nemmeno cancellare la tabella, figuriamoci ottenere shell.
13

Input validation · allowlist vs blocklist

Perché la difesa "allowlist" è preferita a "blocklist" contro SQL injection? Scrivi un esempio concreto di ognuna per validare un parametro sort_by che può valere name, date, o price.

Soluzione
Blocklist (pattern sbagliato): 
if "'" in sort_by or "--" in sort_by or ";" in sort_by:
    raise ValueError("SQL injection attempt")
# L'attaccante può aggirare con encoding, commenti /**/, altri payload
Allowlist (pattern giusto): 
ALLOWED = {"name", "date", "price"}
if sort_by not in ALLOWED:
    raise ValueError("Invalid sort_by")
# Qualsiasi input diverso dai 3 valori noti → rifiutato
Perché allowlist vince: richiede di conoscere l'intera classe di input buoni, che è piccola e definita. La blocklist richiede di conoscere tutti gli input cattivi, classe infinita che include encoding, Unicode tricks, double-encoding, payload mai visti prima. Deny by default è sempre più sicuro di allow by default con eccezioni.

OWASP Top 10 2021 · le 10 voci

Leggendo owasp.org/Top10, elenca le 10 voci del 2021 nell'ordine ufficiale. Indica quali sono più rilevanti per un database.

Soluzione
OWASP Top 10 · 2021:
  1. A01 · Broken Access Control ← rilevante DB (IDOR su query, Row-Level Security)
  2. A02 · Cryptographic Failures ← rilevante DB (encryption at rest, TLS, password hash)
  3. A03 · Injection ← rilevantissimo DB (SQL injection)
  4. A04 · Insecure Design
  5. A05 · Security Misconfiguration ← rilevante DB (pg_hba.conf sbagliato)
  6. A06 · Vulnerable and Outdated Components
  7. A07 · Identification and Authentication Failures ← rilevante DB (auth debole, md5)
  8. A08 · Software and Data Integrity Failures
  9. A09 · Security Logging and Monitoring Failures ← rilevante DB (pgAudit non configurato)
  10. A10 · Server-Side Request Forgery (SSRF)
6 su 10 hanno applicabilità diretta ai DB. Conoscerle è competenza base.
15

Second-order SQLi · riconosci il pattern

Un attaccante registra un nuovo utente con username '; DROP TABLE users; -- (la registrazione usa prepared statements correttamente, nessun problema). Una funzione "welcome email" poi prende il nome dell'utente e lo mette in una query per cercare template email: query = "SELECT tpl FROM email_templates WHERE user = '" + nome_utente + "'". Cosa succede?

Soluzione
Questo è un second-order SQL injection (o "stored SQLi"). Il payload malicioso è stato salvato pulito (grazie al prepared statement della registrazione) ma eseguito sporco dalla seconda funzione che concatena il valore senza parametrizzare.

La query finale: 
SELECT tpl FROM email_templates WHERE user = ''; DROP TABLE users; --'
Il DROP TABLE users viene eseguito. Disastro.

Lesson learned: prepared statements vanno usati ovunque i dati vengono messi in una query, anche quando provengono dal DB stesso. Trust nessun input, anche quelli "interni". La sanitizzazione all'input NON è sufficiente: il valore salvato è una bomba dormiente.

Scenario completo · code review

Ti passano questo endpoint Node.js Express (con libreria pg). Identifica tutti i problemi e riscrivilo sicuro.

app.get("/api/search", (req, res) => {
  const q = req.query.q;
  const sort = req.query.sort || "name";
  const sql = `SELECT * FROM products
               WHERE name LIKE '%${q}%'
               ORDER BY ${sort}`;
  pool.query(sql, (err, result) => {
    if (err) res.status(500).send(err.message);  // mostra errore al client
    else res.json(result.rows);
  });
});
Soluzione
Problemi identificati:
  1. q concatenato nella LIKE: SQL injection diretta.
  2. sort concatenato nell'ORDER BY: SQL injection tramite sort (second vector).
  3. err.message inviato al client: info disclosure (schema, tabelle, errori DB interni).
  4. SELECT *: esfiltrazione di colonne sensibili se ce ne sono.
Versione corretta: 
app.get("/api/search", async (req, res) => {
  const q = req.query.q || "";
  const sort = req.query.sort || "name";
  
  // Allowlist per sort (non si può parametrizzare ORDER BY)
  const ALLOWED_SORT = { name: "name", price: "price", date: "created_at" };
  const sortCol = ALLOWED_SORT[sort] || "name";
  
  try {
    const result = await pool.query(
      `SELECT id, name, price FROM products
       WHERE name ILIKE $1
       ORDER BY ${sortCol}
       LIMIT 100`,
      [`%${q}%`]  // parametro separato
    );
    res.json(result.rows);
  } catch (err) {
    console.error(err);  // log server-side, non al client
    res.status(500).json({ error: "Internal error" });
  }
});
Modifiche fatte:
  • Parametrizzazione di q con $1 e array [`%${q}%`] — LIKE escape resta lato SQL.
  • Allowlist per sort (ORDER BY non è parametrizzabile in SQL, va validato).
  • SELECT id, name, price invece di * — principio del minimo privilegio sui dati.
  • LIMIT 100 previene dump massivi.
  • Errore generico al client, dettagli solo nei log server-side.
  • async/await per codice più pulito.
Callback M1: defense in depth, least privilege, log è tutto, trust nobody.
