A · Virtualizzazione e container
ESERCIZIO 1

Type 1, Type 2 o container?

Classifica ognuno di questi scenari come Type 1, Type 2 o Container:

  • A. Il tuo portatile con VirtualBox che esegue Ubuntu per un lab
  • B. AWS EC2 che esegue le istanze dei clienti su hardware Nitro
  • C. Docker Desktop sul tuo Mac con MySQL girante
  • D. podman run nginx:alpine sul tuo laptop Linux
  • E. Proxmox che ospita le VM di una PMI
Mostra soluzione
A → Type 2. VirtualBox gira come applicazione sopra il tuo OS.
B → Type 1. Nitro (basato su KVM custom) gira direttamente sull'hardware. Le istanze EC2 sono VM.
C → Container. Docker Desktop è un container engine; MySQL è un container, non una VM. (Docker Desktop internamente usa una VM Linux leggera su Mac/Windows, ma MySQL è eseguito come container dentro di essa.)
D → Container. Podman fa girare nginx come processo isolato con namespace+cgroups.
E → Type 1. Proxmox è bare-metal (KVM+LXC), gira direttamente sull'hardware.
ESERCIZIO 2

Mappa il namespace

Per ognuna di queste osservazioni dentro un container, indica quale namespace Linux è responsabile dell'effetto:

  • A. "ps aux dentro il container mostra solo 3 processi, ma l'host ne ha 200"
  • B. "Il container si chiama webapp-01, l'host si chiama prod-srv-12"
  • C. "Il container non vede l'interfaccia eth0 dell'host, ha il suo eth0 virtuale"
  • D. "Dentro il container sono root (UID 0), ma dall'esterno ps mostra il processo come UID 1000"
  • E. "Il container ha una sua /etc/passwd completamente diversa da quella dell'host"
Mostra soluzione
A → PID namespace (vista separata degli ID di processo).
B → UTS namespace (hostname + domain separati).
C → NET namespace (stack TCP/IP separato).
D → USER namespace (UID mapping tra container e host). Questa è la base dei container rootless.
E → MNT namespace (filesystem separato, il container ha la sua /).
ESERCIZIO 3

VM, container o bare-metal?

Per 3 workload aziendali, scegli VM, container o bare-metal e motiva:

  • A. API Python stateless (FastAPI), 20-30 req/s, deploy 5-10 volte al giorno via CI/CD
  • B. Database Oracle 12c legacy, 500 GB dati, usato 24/7 da 200 utenti, performance 10k IOPS, nessun appetito per migrazioni
  • C. Training ML notturno, 4 GPU per 6 ore, Python+PyTorch+CUDA, dataset 2 TB, una tantum gira-produce-spegne
Mostra soluzione
A → Container. Stateless + deploy frequenti + horizontal scaling = cloud-native. Immagine piccola, rebuild fast in CI/CD, scaling in pochi secondi. Esempio concreto: Kubernetes deployment con autoscaler.

B → VM. Legacy monolitico, performance critica, licenze già sostenute, dipendenze OS-level complesse. VM dedicata con risorse riservate. Isolamento forte perché una compromissione sarebbe devastante.

C → VM o bare-metal. Dipende: VM con GPU-passthrough funziona ma ha overhead. Bare-metal se servono massime performance (training di giorni). Container con nvidia-runtime è accettabile ma meno comune in produzione ML training.

Regola pratica: stateless + cambia spesso → container. Stateful + legacy + critical → VM. Bare-metal solo per edge case performance.
B · Database fundamentals
ESERCIZIO 4

SQL o NoSQL?

Per ognuno di questi casi, scegli la famiglia più adatta e spiega perché in una frase:

  • A. Core banking di una banca italiana: conti correnti, bonifici, estratti conto
  • B. Catalogo prodotti e-commerce con attributi molto variabili per categoria
  • C. Real-time leaderboard di un gioco mobile con 10M utenti attivi
  • D. Dati di fatturazione telefonica (CDR) con retention di 7 anni e query analitiche rare
  • E. Sessioni utente di un'app web con TTL di 30 minuti
Mostra soluzione
A → SQL. Transazioni ACID, integrità forte, constraint stretti (saldo mai negativo). PostgreSQL o Oracle.
B → NoSQL document store (MongoDB). Schema flessibile per attributi variabili (un laptop ha CPU/RAM, un vestito ha taglia/colore). Anche PostgreSQL con JSONB funziona bene.
C → NoSQL in-memory (Redis sorted set). Massime performance per operazioni ZADD/ZRANGE, AP consistency accettabile.
D → SQL con partitioning, o data warehouse analitico. Volume grande ma query strutturate. PostgreSQL + TimescaleDB se time-series.
E → NoSQL key-value (Redis). TTL nativo, zero sovrastruttura, AP perfetto per dati ephemeral.
ESERCIZIO 5

ACID a prova di viaggio

Un bonifico di 1000€ da conto A a conto B richiede 2 query: UPDATE conti SET saldo = saldo - 1000 WHERE id = 'A'; poi UPDATE conti SET saldo = saldo + 1000 WHERE id = 'B';. Descrivi quale proprietà ACID è violata (e cosa succede) se:

  • A. Il server si spegne tra le due UPDATE
  • B. A ha saldo iniziale 500€ e il constraint CHECK (saldo >= 0) esiste
  • C. Un altro utente prova a fare un bonifico simile in parallelo e legge il saldo di A mentre la prima transazione è a metà
  • D. Il commit è andato a buon fine ma il disco fallisce prima di persistere
Mostra soluzione
A → Atomicity. Senza, A ha perso 1000€ e B non li ha ricevuti: 1000€ svaniti. Con atomicity, al restart il WAL rollback dello step 1.
B → Consistency. Il constraint viene violato (500 - 1000 = -500). La transazione fallisce e rollback atomico. Il DB resta in stato valido.
C → Isolation. L'altro utente potrebbe vedere il saldo sporco (read uncommitted) o un phantom read. I livelli di isolation (SERIALIZABLE) bloccano la concorrenza.
D → Durability. Violata se il commit è confermato al client ma non ancora fsync-ato. In produzione si usa synchronous_commit = on per attendere fsync prima del "OK commit".
ESERCIZIO 6

CAP theorem · posizionamento

Per ognuno di questi sistemi distribuiti, indica se è CA, CP o AP e spiega in una frase:

  • A. PostgreSQL single-instance
  • B. MongoDB replica set con primary-secondary, default settings
  • C. Cassandra con consistency level ONE
  • D. DynamoDB con "eventually consistent reads"
  • E. ZooKeeper (coordination service)
Mostra soluzione
A → CA. Non è distribuito, non c'è partizione possibile. Consistency e availability garantiti finché l'unico nodo è up.
B → CP. Se il primary è isolato dai secondary, si ferma (elezione di nuovo primary). Sacrifica availability per consistency.
C → AP. Consistency level ONE accetta la scrittura da un singolo nodo; replica successiva. Alta availability, consistency eventuale.
D → AP. Letture da qualsiasi replica, dato possibile obsoleto. Alta disponibilità.
E → CP. ZooKeeper usa Zab (Paxos-like) per consistency forte. Se il quorum non è raggiunto, smette di accettare scritture (fail-stop).

Nota: in pratica P è sempre richiesta (le reti cadono), quindi la vera scelta è tra C e A durante una partizione.
C · PostgreSQL e sicurezza DB
ESERCIZIO 7

Lettura pg_hba.conf · trova i problemi

Guarda questo pg_hba.conf proposto per produzione. Identifica i problemi riga per riga:

# TYPE    DATABASE   USER       ADDRESS         METHOD
local     all        postgres                   trust
host      all        all        0.0.0.0/0       md5
host      production webapp     10.0.0.0/8      password
host      all        admin      0.0.0.0/0       scram-sha-256
hostssl   finance    finance    10.0.5.0/24     scram-sha-256
Mostra soluzione
Riga 1 — local all postgres trust: CORREGGI. In dev va bene, in produzione pericoloso (qualsiasi utente OS con sudo -u postgres psql diventa root DB). Preferire peer.
Riga 2 — host all all 0.0.0.0/0 md5: MAI. Due errori: 0.0.0.0/0 = mondo intero, md5 = deprecato.
Riga 3 — host ... password: MAI. Il metodo password invia la password in chiaro sul wire. Sostituire con scram-sha-256 o hostssl + scram-sha-256.
Riga 4 — admin da 0.0.0.0/0: MAI. Anche con scram-sha-256 forte, un admin accessibile dal mondo intero è un attack vector enorme. Restringere a subnet bastion o VPN.
Riga 5 — hostssl finance finance_app 10.0.5.0/24 scram-sha-256: OK. TLS obbligatorio, subnet specifica, user+DB mirati.

Red flag universali da ricordare: 0.0.0.0/0, trust, md5, password.
ESERCIZIO 8

sslmode · scegli il valore giusto

Per ognuno di questi scenari, scegli il valore di sslmode appropriato tra disable, allow, prefer, require, verify-ca, verify-full:

  • A. App Python in produzione che si connette a RDS PostgreSQL con certificato AWS
  • B. Script locale che si connette a un PostgreSQL sul tuo stesso laptop via 127.0.0.1
  • C. Tool di backup che si connette al DB produzione via VPN
  • D. Configurazione di default che un collega ha messo in un client: "usa TLS se il server lo offre, altrimenti vai in chiaro"
Mostra soluzione
A → verify-full. Standard produzione. TLS obbligatorio + CA + hostname match. Previene MITM.
B → disable o require. Loopback locale, TLS overhead inutile se il server è sullo stesso host. Se il server accetta TLS, require va bene.
C → verify-full. Anche via VPN, TLS è difesa in profondità. Se il certificato è firmato da CA interna, il sslrootcert punta alla CA aziendale.
D → Il collega ha usato prefer (default di libpq). Pericoloso: vulnerabile a downgrade attack. Un attaccante MITM può strippare TLS e il client accetta plaintext. Correggere in require minimo, verify-full idealmente.
ESERCIZIO 9

Encryption at rest · disegna la difesa in profondità

Sei l'architetto di un DB PostgreSQL su AWS che contiene dati clienti sensibili (nome, SSN, numero carta di credito). Proponi una strategia di encryption at rest usando più layer. Per ogni layer spiega cosa protegge e cosa no.

Esempio di soluzione
Layer 1 · EBS encryption (volume cloud): attivato di default (customer-managed key via KMS). Protegge se qualcuno riesce a scaricare snapshot o volumi. Non protegge da attaccante con credenziali IAM legittime.

Layer 2 · pgcrypto column-level su SSN e numero carta. PGP_SYM_ENCRYPT(value, key) con chiave in AWS KMS. Protegge i dati anche se qualcuno ha SELECT sulla tabella. Non protegge da chi ha accesso alla chiave KMS.

Layer 3 · Access control: DB role per l'app ha SELECT solo sulle colonne non cifrate; solo il servizio di decrypt (lambda con IAM role specifico) ha accesso alla chiave KMS.

Layer 4 · pgAudit attivo su tabella clienti (SET (audit='read, write')). Qualsiasi accesso viene loggato e forwardato a CloudWatch + Splunk. Retention 7 anni (GDPR).

Cosa questa pila NON protegge: SQL injection nell'app (prossima lezione!), memory dump del server DB quando è acceso, rubare il disco fisico mentre è in uso e sbloccato, insider con accesso root al server. La sicurezza è sempre a layer, niente è bulletproof.
ESERCIZIO 10

Configurare pgAudit — compliance GDPR

Il CISO chiede: "tutti gli accessi in lettura ai dati anagrafici clienti devono essere loggati e conservati 7 anni, secondo GDPR". Come configureresti pgAudit e l'infrastruttura di log?

Soluzione
1. Configurazione PostgreSQL: 
shared_preload_libraries = 'pgaudit'
pgaudit.log = 'write, role, ddl'
log_connections = on
log_disconnections = on
log_line_prefix = '%m [%p] %q%u@%d '
log_destination = 'jsonlog'   # PG 15+
2. Abilitare READ logging solo sulla tabella sensibile (per non esplodere il volume log): 
ALTER TABLE clienti SET (audit='read, write');
3. Forward dei log a SIEM:
  • Filebeat/Fluentd legge /var/log/postgresql/*.log
  • Spedisce a Elasticsearch / Splunk / Datadog
  • Integrazione con SIEM per alert su pattern sospetti (es. SELECT * senza WHERE)
4. Retention 7 anni:
  • S3 Glacier Deep Archive per log oltre 1 anno
  • Lifecycle policy che sposta da S3 Standard → Glacier → Deep Archive
  • Costo ~$1/TB/mese su Deep Archive
5. Proteggere i log stessi:
  • Bucket S3 con object lock in compliance mode (no-delete)
  • Accesso ai log solo per auditor con approval workflow
  • Log dell'accesso ai log (meta-audit)
Callback M1: defense in depth + log è tutto + immutabilità degli audit.
