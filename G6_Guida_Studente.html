1 · Cos'è l'hardening

L'hardening è la disciplina di ridurre la superficie di attacco di un sistema tramite configurazioni sicure, rimozione di componenti non necessari e applicazione di principi di minimo privilegio — prima che il sistema entri in produzione e mantenute per tutto il suo ciclo di vita.

Quattro principi cardine guidano ogni operazione di hardening:

  • Least privilege: ogni account, servizio, processo ha solo i permessi strettamente necessari. È il principio più citato e il meno applicato: nelle aziende reali, il 70-80% degli account utente ha più permessi del necessario perché concedere è facile e revocare è doloroso.
  • Minimal footprint: disinstallare ciò che non serve. Ogni pacchetto in più è codice attaccabile, CVE potenziali, processo che consuma RAM, log da analizzare. È il motivo per cui i container di produzione partono spesso da immagini Alpine o distroless.
  • Secure defaults: configurazioni sicure di default. Storicamente trascurato: nessuno legge manuali, e i default permissivi hanno generato milioni di compromissioni (MongoDB senza password esposti su Internet, S3 bucket pubblici, telecamere IP con admin/admin).
  • Disciplined patching: patch rapide e ripetibili, con finestre di manutenzione, piano di rollback, test in staging, tracking delle CVE.
⚠ Hardening ≠ patching. Un sistema completamente patchato con configurazione permissiva resta vulnerabile. Una VM Ubuntu 22.04 aggiornata all'ultimo kernel ma con SSH aperto a 0.0.0.0/0 e root login abilitato è più vulnerabile di una Ubuntu 20.04 non aggiornata ma hardenata. Patching e hardening sono complementari, non alternativi.

2 · Defense in depth e framework di riferimento

L'hardening è uno strato nella defense in depth, non la muraglia unica. I 6 strati canonici, dal più esterno al più profondo:

  • Perimetro: Firewall, IDS/IPS, WAF
  • Segmentazione: VLAN, microsegmentazione, Zero Trust
  • Host: Hardening OS ← cuore di L6
  • Applicazione: Secure coding, input validation, SAST/DAST
  • Dato: Encryption at rest/in transit, DLP
  • Identità: IAM, MFA, least privilege, access review

Un singolo strato buca. La defense in depth accetta il fallimento e prepara il livello successivo. L'hardening agisce principalmente su tattiche MITRE ATT&CK di Defense Evasion, Privilege Escalation, Lateral Movement, Persistence.

I tre framework di hardening principali

Esistono tre famiglie di standard che guidano operativamente l'hardening:

  • CIS Benchmarks (Center for Internet Security): standard de-facto del mondo enterprise. Copre 100+ tecnologie (OS, DB, cloud, container). Due livelli: L1 (baseline essenziale, basso impatto) e L2 (defense-in-depth, richiede analisi di impatto). Ubuntu 22.04 ha ~700 controlli. Gratuito per uso personale, formato PDF.
  • DISA STIG (US Dept. of Defense): standard militare/governativo USA. Più stringente di CIS. 3 severity (CAT I/II/III). Obbligatorio in ambienti federali DoD e NATO. Template Ansible/Puppet ufficiali disponibili.
  • NIST SP 800-series (National Institute of Standards): meno prescrittivo, più "architetturale". SP 800-53 Rev.5 è il catalogo di ~1000 controlli che si mappa su FedRAMP, HIPAA, FISMA, e indirettamente su NIS2, DORA (EU).
In Italia / EU: CIS è la scelta prevalente nel privato, NIST è il riferimento per compliance normativa (NIS2, DORA, Cyber Resilience Act). Per Leonardo SpA, contractor defense, il pattern è ibrido: baseline CIS sui sistemi generali, STIG o equivalenti per progetti governativi/defense, allineamento NIST per reportistica compliance.

Come si legge un controllo CIS

Ogni controllo CIS ha formato standard. Esempio 5.2.8 · Ensure SSH root login is disabled:

  • Profile: Level 1 - Server (applicabile senza breaking change)
  • Severity: Medium
  • Description: cosa fa il controllo
  • Rationale: perché farlo (accountability nei log)
  • Audit: grep -E '^\s*PermitRootLogin' /etc/ssh/sshd_config
  • Remediation: sudo sed -i 's/^#\?PermitRootLogin.*/PermitRootLogin no/' /etc/ssh/sshd_config && sudo systemctl reload sshd

Il formato standard permette tracciabilità (auditor cita "sezione 5.2 fallita" senza ambiguità) e automazione (audit command e remediation sono lanciabili da script o da tool come Ansible, OpenSCAP, Inspec).

3 · Hardening Linux

In sei aree — account, SSH, filesystem, servizi, firewall host, audit — sta il 90% del CIS Ubuntu. Gli altri controlli sono spesso variazioni sui temi.

Account, sudo, PAM

I controlli chiave: root login disabilitato, password aging (PASS_MAX_DAYS 90), account inattivi lockati automaticamente, sudoers senza NOPASSWD wildcards, PAM con pam_pwquality (complessità) e pam_faillock (lockout dopo N tentativi), UID 0 unico (solo root).

PAM (Pluggable Authentication Modules) è il meccanismo di autenticazione Linux: /etc/pam.d/ contiene file per ogni servizio (sshd, sudo, login). Ogni file ha stack di moduli con 4 tipi (auth, account, password, session). La configurazione corretta di PAM blocca il 99% degli attacchi SSH brute-force automatizzati.

L'anti-pattern più comune nelle aziende: accumulo di account dormienti. "Nuovo dipendente → creo account. Dipendente esce → poi lo cancello" e il "poi" non arriva mai. Risultato: decine di account con credenziali valide di ex-dipendenti. Il controllo è semplice: cronjob che lockia account senza login da >30 giorni (lastlog + usermod -L), access review trimestrale formalizzata.

SSH hardening

Il servizio di accesso remoto più sfruttato. Un IP pubblico nuovo su porta 22 riceve il primo tentativo di login in meno di 60 secondi e migliaia al giorno. Le direttive minime in /etc/ssh/sshd_config:

  • PermitRootLogin no — il più importante
  • PasswordAuthentication no + PubkeyAuthentication yes — solo chiavi
  • MaxAuthTries 3 — meno fallimenti prima del disconnect
  • ClientAliveInterval 300 + ClientAliveCountMax 2 — kick sessione dopo 10 min idle
  • AllowUsers admin@10.0.0.0/24 — whitelist utenti + subnet sorgente
⚠ Regola operativa cruciale: mai modificare sshd_config senza una seconda sessione SSH già aperta come paracadute. Quasi ogni sysadmin senior ha perso l'accesso a un server remoto per questo. Testa la config prima del reload: sudo sshd -t && sudo systemctl reload sshd.

Filesystem, servizi, firewall host

Filesystem layout: /tmp, /var, /home su partizioni separate con mount options nosuid, noexec, nodev su /tmp. Bloccano exploit che scaricano payload in /tmp e li eseguono.

Gestione servizi: systemctl list-unit-files --state=enabled mostra spesso 30-40 servizi, realisticamente ne servono 10. Ogni servizio in più = porta potenzialmente aperta + codice potenzialmente vulnerabile + log da analizzare.

Firewall host (UFW/nftables): ufw default deny incoming + ufw default allow outgoing + apertura esplicita delle porte necessarie. È la seconda linea dopo il firewall di rete.

Audit e tool automatici

auditd registra chiamate di sistema selezionate: modifiche a file critici (/etc/passwd, /etc/shadow), esecuzione di comandi privilegiati (sudo, su), cambi di ownership, login falliti via PAM hooks.

I tool di assessment automatici che vedrai in ambiente reale:

  • Lynis — audit rapido (~2 min), output "hardening index" 0-100 tracciabile nel tempo. sudo lynis audit system.
  • OpenSCAP — scanner di compliance che consuma profili XCCDF standard (CIS, STIG). Report HTML con evidence e remediation.
  • Chef Inspec — "compliance as code": profili Ruby versionati in Git, integrazione CI/CD.
Pattern moderno "Compliance as Code": infrastructure-as-code (Terraform) + configuration-as-code (Ansible) + compliance-as-code (Inspec) + policy-as-code (OPA). Tutto versionato in Git, tutto peer-reviewed, tutto testato, tutto automaticamente applicato. Lo vedremo in dettaglio nel Modulo 4 (DevSecOps & Automation).

4 · Hardening Windows

Windows offre infrastrutture native più ricche di Linux per il governo della configurazione: Group Policy per enforcement centralizzato, Microsoft Security Baseline come baseline pronti, LAPS per password locali, Defender come EDR integrato.

Microsoft Security Baseline e GPO

La Microsoft Security Baseline è un set ufficiale di impostazioni GPO raccomandate da Microsoft per Windows 11 / Server 2022. Scaricabile dal Security Compliance Toolkit, contiene ~2000 impostazioni GPO pre-configurate (autenticazione, lockout, firewall, audit, Defender, AppLocker).

Le Group Policy Objects (GPO) sono il meccanismo di enforcement distribuito via Active Directory. Ordine di applicazione LSDOU: Local → Site → Domain → OU. In caso di conflitto vince l'ultima applicata (salvo flag Enforced che inverte la logica). Verifica delle GPO attive: gpresult /h report.html.

⚠ Applicare Security Baseline direttamente all'OU "Computers" può causare breaking change massive. Il workflow corretto è: scarica Baseline → importa in GPMC → applica a OU di test → verifica con PolicyAnalyzer → rollout graduale su ondate.

LAPS, UAC, Defender, BitLocker

LAPS (Local Administrator Password Solution) risolve un problema endemico: pre-2015 la password admin locale era identica su tutti i PC aziendali. Un singolo PC compromesso dava credenziali che funzionavano ovunque via Pass-the-Hash. LAPS genera password random per macchina, custodita in AD, rotata ogni 30 giorni. Oggi è integrato nativamente in Windows 11/Server 2022 (Windows LAPS).

UAC (User Account Control): separa utente standard da token elevato. Richiede elevazione esplicita per operazioni privilegiate. Mai disabilitarlo su endpoint. Il pattern "sempre lavora come utente non-admin, eleva solo quando serve" è una delle misure più efficaci.

Microsoft Defender for Endpoint: AV + EDR integrato. Le ASR Rules sono il pezzo pregiato — 16 regole che bloccano tecniche d'attacco specifiche: "Block all Office applications from creating child processes" (macro weaponizzate), "Block execution of potentially obfuscated scripts", "Block credential stealing from LSASS". In ambienti enterprise, attivarle in audit mode per 30 giorni, misurare falsi positivi, poi switch a block mode.

BitLocker: full disk encryption con TPM 2.0 + PIN. Protegge da furto fisico del dispositivo spento. Non protegge da malware in OS running (dati in RAM/disco in chiaro quando PC è acceso e loggato). Obbligatorio su laptop aziendali.

PowerShell hardening

PowerShell è amato dagli attaccanti "fileless": sempre presente, firmato, pieno accesso a .NET, LotL (Living-off-the-Land). Statistica: ~38% degli incidenti SOC moderni coinvolgono PS come tecnica post-exploitation.

La risposta difensiva ha tre livelli:

  • Visibilità: Script Block Logging (Event ID 4104) registra ogni script eseguito dopo decodifica. L'offuscamento base64 è inutile contro questo log.
  • Restrizione: Constrained Language Mode limita PS alle operazioni essenziali (no .NET arbitrary, no COM, no Add-Type).
  • Delega granulare: JEA (Just Enough Administration) permette di creare endpoint PowerShell con capability limitate (un operatore IT esegue solo "Restart-Service SQLSERVER" e niente altro).
Mimikatz è lo strumento di riferimento per credential harvesting. Dump password in chiaro, hash NTLM, Kerberos ticket dalla memoria LSASS. La versione PowerShell (Invoke-Mimikatz) gira in-memory, non tocca disco, bypassa AV signature-based. Le contromisure moderne: Credential Guard (Windows 10 Enterprise+) isola LSASS in VM Hyper-V separata, inaccessibile anche a SYSTEM.

5 · Automazione e scala enterprise

10 server li fai a mano. 1000 server no. 10000 server sono un problema di ingegneria.

I tre tool principali del panorama EU/Italia:

  • Ansible — standard de-facto in EU. Agentless (bastano SSH/WinRM), playbook YAML. Il ruolo ansible-lockdown.ubuntu_22_cis applica CIS L1 su 500 host in parallelo in 30-60 minuti.
  • Chef Inspec — testing framework. Non applica, verifica. Perfetto per integrazione CI/CD: ogni commit che modifica configurazione scatena test Inspec, deploy bloccato se fallisce.
  • Puppet / Salt — state-based, agent-based. Enforcing continuo contro drift. Puppet Enterprise ha compliance reporting integrato.

Le sfide enterprise reali

Il gap tra hardening "da manuale" e hardening "nel mondo reale" è sostanziale:

  • Legacy: Windows Server 2008 ancora in produzione con app non aggiornabili
  • Third-party vendor: "non modificare la config, SLA garantito solo con default"
  • Falsi positivi: applicazioni che si rompono su controlli L1
  • Cicli di approvazione: modificare GPO richiede CAB (Change Advisory Board)
  • Ambienti eterogenei: RHEL + Ubuntu + Windows + Solaris tutti insieme
  • Drift: config applicata e poi modificata nel tempo

Le risposte operative: compensating controls (se non posso hardenare, isolo in VLAN → microseg L5), tiered baseline (must/should/could), ambiente di test identico alla produzione, single source of truth (Ansible + Git), risk register per eccezioni, drift detection continua con alert SIEM.

6 · Kali Linux e Metasploit

Kali Linux è la distribuzione di riferimento per attività offensive. Debian-based, mantenuta da Offensive Security, ~600 strumenti preinstallati organizzati in 13 categorie (Information Gathering, Vulnerability Analysis, Web Application, Exploitation, Post-Exploitation, Forensics...).

🚨 Disclaimer etico-legale fondamentale. In Italia, l'art. 615-ter c.p. punisce l'accesso abusivo a sistema informatico con reclusione fino a 3 anni (fino a 8 se aggravato). Gli strumenti Kali sono legali in Italia, ma il loro uso fuori da contesti autorizzati è reato. Per Leonardo SpA, contractor defense, ogni attività offensiva richiede autorizzazione scritta, scope definito e ROE (Rules of Engagement) precise.

Nmap: information gathering

Nmap è il primo strumento di ogni attacco. Modalità principali:

  • nmap -sn 192.168.56.0/24 — host discovery (ping scan)
  • nmap -sS 192.168.56.50 — SYN scan (richiede root, stealth)
  • nmap -sV -O 192.168.56.50 — versione servizi + OS fingerprinting
  • nmap -A -T4 192.168.56.50 — aggressive (rumoroso, informativo)
  • nmap --script vuln 192.168.56.50 — NSE scripts per vulnerabilità note

L'output di nmap è l'input per le fasi successive: la versione precisa del servizio rivelata da -sV permette di cercare exploit noti (searchsploit, ExploitDB), le porte aperte guidano la scelta dei moduli Metasploit.

Metasploit Framework

Framework modulare di exploitation, ~2300 exploit, ~1200 payload, ~1000 moduli ausiliari. Cinque tipi di moduli:

  • Exploits: codice che sfrutta una vulnerabilità per ottenere esecuzione
  • Payloads: codice eseguito post-exploit (shell, meterpreter, reverse/bind)
  • Auxiliary: scanner, fuzzer, DoS, brute-force
  • Post: enumeration, pivoting, persistence post-compromissione
  • Encoders: codifica payload per evadere AV/IDS

Il payload più usato è Meterpreter: staged, ~300KB, gira interamente in memoria (DLL injection), ~100 comandi built-in (screenshot, keyscan, hashdump, migrate process).

Syntax msfconsole fondamentale: search <keyword>, use <path>, show options, set RHOSTS ..., exploit.

7 · Privilege escalation Linux e Windows

L'accesso iniziale (foothold) di solito arriva come utente a basso privilegio (www-data, apache, nobody). Il vero lavoro post-exploitation è il privilege escalation: diventare root o SYSTEM.

Privilege escalation Linux

Quattro vettori dominano:

  • SUID abuse: binari con flag SUID (eseguiti come owner, spesso root). find / -perm -4000 -type f 2>/dev/null. Se un SUID binary ha capacità shell-escape (find con -exec, vim con :!, awk con system), escalation immediata.
  • sudo misconfig: il vettore più sfruttato realmente. sudo -l mostra cosa puoi fare. Se vedi NOPASSWD: /usr/bin/vim /etc/hosts sei root: sudo vim /etc/hosts poi :!/bin/bash.
  • Cron jobs: script di root scrivibili da utente normale → attaccante modifica script, aspetta il cron, root shell.
  • Kernel exploits: Dirty COW (CVE-2016-5195), Dirty Pipe (CVE-2022-0847), PwnKit (CVE-2021-4034). Ultima risorsa, rumorosi, rischio crash.
GTFOBins (gtfobins.github.io) è il database di riferimento per privilege escalation Linux. Per ogni binario, elenca i modi in cui può essere abusato per shell escape, SUID abuse, sudo abuse. Diventa il primo riferimento durante il lab: hai sudo senza password su X? Vai su GTFOBins, cerca X, copia-incolla. È il motivo per cui i sudoers devono essere estremamente restrittivi.

Privilege escalation Windows

Pattern diversi per via dell'architettura di sicurezza Microsoft:

  • Unquoted Service Paths: servizi con path non quotato contenente spazi → DLL injection. Vestigia di installer legacy.
  • Token Impersonation: SeImpersonatePrivilege (account IIS, MSSQL) → attack chain "Potato" (PrintSpoofer, RoguePotato, GodPotato) che forza autenticazione NTLM relay per ottenere SYSTEM.
  • Credential Harvesting: Mimikatz dump LSASS → password/hash utenti loggati. Contromisura moderna: Credential Guard.
  • AlwaysInstallElevated: GPO che permette MSI eseguiti come SYSTEM da utente non-admin. Raro nei default moderni ma ancora presente in deployment mal-configurati.

LOLBAS (lolbas-project.github.io) è il corrispondente Windows di GTFOBins: ~200 binari Windows firmati Microsoft abusabili (certutil per download, regsvr32 per exec, mshta, wmic, bitsadmin).

8 · Pass-the-Hash e lateral movement

In Active Directory, il furto di credenziali da una macchina permette di muoversi sulle altre. Pass-the-Hash e Kerberoasting sono le due tecniche iconiche del lateral movement.

Pass-the-Hash (PtH)

Difetto architetturale di NTLM: il protocollo usa l'hash NTLM della password (non la password stessa) come challenge-response. L'hash è funzionalmente equivalente alla password — chi ha l'hash si autentica ovunque NTLM è accettato senza conoscere la password originale.

Pattern classico: compromesso PC1 come admin locale → Mimikatz dump hash → stesso hash funziona su PC2, PC3... (pre-LAPS) → trova PC con admin dominio loggato → Mimikatz dump credenziali dominio → Domain Admin → Golden Ticket → controllo totale.

Difesa chiave: LAPS. Password admin locale random per macchina = hash diverso per macchina = PtH si ferma al primo PC.

Kerberoasting

Sfrutta una feature by-design di Kerberos: qualunque utente autenticato nel dominio può richiedere Service Ticket (TGS) per qualsiasi servizio. Il TGS è cifrato con la chiave derivata dalla password dell'account di servizio → brute-force offline con hashcat o john.

Gli account di servizio legacy con password scelte manualmente ("Password123!") cadono in secondi. Un dominio AD medio ha 5-20 account Kerberoastable, il 30% cede al crack.

Difese: Managed Service Accounts (password random >100 char gestite da Windows), Protected Users group (no NTLM), AES-only encryption, Tier Model (admin di Tier 0 non si loggano mai su Tier 2).

Come la microsegmentazione spezza il lateral

In reti flat, il blast radius di un singolo endpoint compromesso è potenzialmente l'intera rete. Con microsegmentazione identity-based, il blast radius è 1 host. Il ransomware moderno (Conti, LockBit, Akira) ha fase di lateral movement di giorni/settimane: senza lateral, il ransomware non può mappare la rete, quindi il deployment massivo simultaneo (fase finale) non avviene.

9 · Il lab guidato: cosa abbiamo fatto

Il lab ha coperto il workflow minimale di un pentest interno in 6 step, riproducendo un attacco end-to-end:

  1. Recon network: nmap -sn 192.168.56.0/24 — scopri host attivi
  2. Recon host: nmap -sV -p- 192.168.56.50 — versione servizi
  3. Exploit vsftpd: Metasploit, use exploit/unix/ftp/vsftpd_234_backdoor, set RHOSTS, exploit
  4. Recon locale: id, uname -a, sudo -l
  5. Privilege escalation: sudo find . -exec /bin/sh \; -quit (GTFOBins pattern)
  6. Verifica e exit: id → uid=0(root), exit

Il CVE di vsftpd 2.3.4 (CVE-2011-2523, "smiley face backdoor") è stato scelto didatticamente: è deterministico (sempre funziona, nessuna dipendenza da offset memoria), memorabile (il trigger è username che termina con ':)'), dà shell root direttamente. Ha 15 anni, è patchato in ogni sistema decente — la sua presenza nel lab simula un sistema legacy non aggiornato, scenario comune nel mondo reale.

Mappatura attacco → controlli (esercizio chiave):
• Fase 1 (nmap scan): host firewall + IDS + rimozione servizi inutili
• Fase 2 (exploit vsftpd): patching disciplinato + minimal footprint + auditd
• Fase 3 (reverse shell): EDR + network segmentation (outbound policy)
• Fase 4 (SUID → root): sudoers restrittivi + no NOPASSWD su binari shell-escape
Questo è il cuore del mindset Purple team: capire l'attacco per costruire la difesa.

10 · Chiusura Modulo 1 · i 4 pattern trasversali

Il Modulo 1 in 6 lezioni:

  • L1: Fondamenti di rete e segmentazione (8 apr)
  • L2: Routing, DNS, TLS, VPN (10 apr)
  • L3: Firewall, NAT, WAF (15 apr)
  • L4: VPN pratica e sicurezza perimetrale (17 apr)
  • L5: Microsegmentazione, Zero Trust, SDN (22 apr)
  • L6: Hardening, attacchi laterali, chiusura (24 apr)

Dietro le 6 lezioni, 4 pattern trasversali che ricorreranno in tutti i moduli successivi:

Pattern 1 · Defense in depth

Strati multipli e diversi. Un singolo controllo buca; la catena no. Esempio: un laptop aziendale protetto da perimetro (VPN), identità (MFA), host (BitLocker), applicazione (app sandboxata), dato (file encryption).

Pattern 2 · Identità > IP

Le policy basate su identità (utente, workload, service account) sono più robuste di quelle basate su IP/subnet. L'era del "firewall by IP" è finita nel cloud/BYOD/container. Esempio: service principal con permessi specifici su API Kubernetes, indipendente dal nodo fisico del pod.

Pattern 3 · Log è tutto

Senza telemetria non c'è security. Raccogli, correla, alerta. Esempio: Script Block Logging di PowerShell ha rivelato migliaia di attacchi fileless che AV signature-based non vedeva. Lo approfondiremo nel Modulo 5 (SOC & Incident Response).

Pattern 4 · Automazione

A mano non scala. Infrastructure-as-Code + Compliance-as-Code. Esempio: pipeline Ansible applica baseline CIS + Inspec verifica compliance + pipeline fallisce se hardening index < 75. Lo approfondiremo nel Modulo 4 (DevSecOps).

Setup Podman (obbligatorio per il lab in aula L7)

🔧 Podman · Installation guide
Windows (WSL2) / macOS (brew) / Linux nativo · ~30 min install + verifica

Perché Podman e non Docker Desktop? Docker Desktop richiede licenza a pagamento per uso aziendale. Podman è FOSS, rootless by default (più sicuro), CLI quasi identica a Docker. Alternativa accettabile: Docker Engine su Linux nativo.

Azioni richieste:

  1. Installa Podman
  2. Verifica con podman --version e podman run hello-world
  3. Pull delle 3 immagini M2: podman pull postgres:16, podman pull mysql:8, podman pull nginx:alpine
  4. Avvia 3 container insieme, verifica podman ps
