Definisci un hypervisor in 2 frasi

Senza guardare le slide, spiega cos'è un hypervisor e le sue 3 proprietà chiave.

Esempio soluzione
Un hypervisor è uno strato software (o firmware) che astrae l'hardware fisico e permette di eseguire più sistemi operativi completi in isolamento reciproco sullo stesso host. Le 3 proprietà chiave sono isolation (kernel/memoria/device separati per VM), resource pooling (scheduler che divide CPU/RAM/storage tra VM) e portability (la VM è un file trasportabile tra server).

Stack a confronto

Disegna (o descrivi) lo stack completo di un hypervisor Type 1 e uno Type 2, dal basso verso l'alto.

Soluzione
Type 1 (bare-metal):
Hardware fisico → Hypervisor (ESXi/KVM/Hyper-V) → Guest OS 1, 2, 3, ...

Type 2 (hosted):
Hardware fisico → Host OS (Windows/macOS/Linux) → Hypervisor (VirtualBox/VMware WS) → Guest OS 1, 2, ...

Il type 2 ha un layer in più (l'host OS) che introduce overhead ma semplifica installazione.

3 CVE hypervisor

Cerca online (o ricorda dalla lezione) 3 CVE o classi di attacchi noti contro hypervisor. Per ognuno spiega cosa permetteva.

Soluzione tipica
VENOM (CVE-2015-3456): heap overflow nel floppy controller QEMU. Permetteva escape da VM a host, eseguendo codice nel processo QEMU.

CVE-2022-31705 (VMware ESXi): heap overflow nel device USB emulato. Permetteva a un guest di eseguire codice sull'host.

Spectre/Meltdown/L1TF (2018): side-channel attacks via cache CPU. Un guest può leggere memoria di altri guest sulla stessa CPU fisica. Mitigazione: patch microcode + kernel.

Mitigazioni standard: patching hypervisor tempestivo, rimozione device virtuali non necessari (floppy!), trust zone segmentation.

7 namespace a memoria

Elenca i 7 namespace Linux e cosa isola ciascuno. Va bene una versione sintetica.

Soluzione
1. PID — process ID (container vede i propri PID da 1)
2. NET — interfacce di rete, routing, firewall
3. MNT — mount / filesystem separato
4. IPC — shared memory, semafori, queues
5. UTS — hostname + domain
6. USER — UID/GID mapping (base rootless)
7. CGROUP — vista limitata della gerarchia cgroup

cgroups · scrivi i comandi

Scrivi il comando podman run per lanciare un container Alpine con i seguenti limiti: max 1 CPU, 256 MB di RAM, max 50 processi, read bandwidth massima 10 MB/s sul disco /dev/sda.

Soluzione
podman run -it \
  --cpus=1 \
  --memory=256m \
  --pids-limit=50 \
  --device-read-bps=/dev/sda:10mb \
  alpine sh
Note: --cpus accetta anche valori frazionari (es. 0.5). --memory suffissi: b, k, m, g. Su Linux ci vogliono i privilegi di accesso al device.

VM vs container · 5 differenze

Elenca 5 differenze principali tra VM e container, con una breve spiegazione.

Soluzione
1. Isolamento: VM forte (kernel separato), container medio (kernel condiviso).
2. Peso immagine: VM GB (OS completo), container MB (solo userland).
3. Tempo avvio: VM secondi/minuti, container millisecondi.
4. Densità: VM decine per host, container centinaia.
5. Portabilità: VM = file OVA/VMDK, container = immagine OCI da registry.
6. Uniformità host-guest (bonus): VM supporta OS diversi, container richiede stesso kernel dell'host.

Perché Podman e non Docker Desktop

Spiega in 3 punti le differenze architetturali che favoriscono Podman in contesto enterprise.

Soluzione
1. FOSS, no license. Apache 2.0, nessuna licenza commerciale richiesta. Docker Desktop dal 2022 richiede licenza per aziende >250 dipendenti o >$10M revenue.
2. Daemonless. No demone root permanente. Podman è una CLI che forka direttamente. Meno attack surface, meno complessità operativa.
3. Rootless by default. I container girano come utente normale dell'host. Un'evasione lascia l'attaccante con privilegi utente, non root. Difesa strutturale importante.

Nota: Docker Engine (il motore senza GUI) continua a essere gratuito su Linux server. La licenza tocca solo Docker Desktop (la GUI su Mac/Windows).

Lab pratico · PostgreSQL in container

Scrivi la sequenza di comandi per:
1. Avviare un container PostgreSQL 16 Alpine con password secret, esposto sulla porta 5432, chiamato pg-lab
2. Verificare che è running
3. Entrare con psql come user postgres
4. Controllare lo stato (dentro psql)
5. Uscire e fermarlo

Soluzione
# 1. Avvio
podman run -d \
  --name pg-lab \
  -e POSTGRES_PASSWORD=secret \
  -p 5432:5432 \
  postgres:16-alpine

# 2. Verifica
podman ps
# deve mostrare pg-lab running, status Up

# 3. Entra con psql
podman exec -it pg-lab psql -U postgres

# 4. Dentro psql
\conninfo       -- info connessione
\l              -- lista database
\du             -- lista user/ruoli
SELECT version();

# 5. Esci e ferma
\q
podman stop pg-lab

ACID a memoria

Elenca le 4 proprietà ACID e una spiegazione da 1 frase ciascuna.

Soluzione
A · Atomicity: la transazione è un blocco indivisibile, o tutto o niente (rollback al crash).
C · Consistency: il DB resta in stato valido, i constraint sono sempre rispettati.
I · Isolation: transazioni concorrenti non si vedono fino al commit (4 livelli SQL standard).
D · Durability: dopo il commit, i dati sono persistiti sul disco (WAL + fsync).
11

Livelli di isolation

Elenca i 4 livelli di isolation ANSI SQL dal più permissivo al più stretto e indica quale problema ciascun livello previene.

Soluzione
1. READ UNCOMMITTED — permette letture sporche, phantom, non-repeatable. Raramente usato.
2. READ COMMITTED (default PostgreSQL) — previene letture sporche. Phantom e non-repeatable ancora possibili.
3. REPEATABLE READ — previene letture sporche + non-repeatable. Phantom possibili (in alcuni DB).
4. SERIALIZABLE — previene tutto. Transazioni come se serializzate.

Trade-off: più alto = più sicuro ma meno concorrenza (più lock/blocchi).

CAP theorem · casi limite

Vero o falso, motiva ogni risposta:

  • A. "Un sistema distribuito può essere CA senza sacrificare nulla"
  • B. "MongoDB è AP per default"
  • C. "PostgreSQL single-instance è CP"
  • D. "Durante una partizione di rete, un sistema CP smette di rispondere alle scritture"
Soluzione
A → Falso. CA è possibile solo in sistemi non-distribuiti (single node). In un sistema distribuito reale P è un vincolo, non una scelta: le reti cadono.
B → Falso. MongoDB default è CP (replica set con primary-secondary): se il primary è isolato, elezione, downtime scrittura.
C → Falso. Non è distribuito → è CA (consistency + availability). Non ha senso parlare di P.
D → Vero. CP sacrifica A quando c'è partizione: nodi fuori dal quorum smettono di accettare scritture per preservare consistency.

PostgreSQL · architettura e connection pool

Un'app ha 200 web worker concorrenti che aprono connessioni dirette a PostgreSQL. Dopo poche ore il DB è lento e risponde con errore "too many connections". Cosa sta succedendo e qual è la soluzione?

Soluzione
Cosa sta succedendo: PostgreSQL forka un processo backend dedicato per ogni connessione. 200 backend × 5 MB ciascuno = 1 GB di RAM solo per i backend, più il costo di context switching. Il parametro max_connections (default 100) protegge da esaurimento risorse: oltre il limite restituisce "too many connections".

Soluzione: connection pool. Installare PgBouncer davanti al DB. L'app apre 200 connessioni a PgBouncer; PgBouncer riusa solo 20-50 connessioni vere verso il DB (pool mode: transaction). L'app non se ne accorge, il DB respira.

Alternative cloud: RDS Proxy (AWS), pool integrato in Azure Database for PostgreSQL.

PostgreSQL vs MySQL · quando scegli cosa

Per ognuno di questi scenari, scegli PostgreSQL o MySQL e motiva:

  • A. App Django nuova con componente GIS (mappe)
  • B. WordPress per il blog aziendale
  • C. Core transactional per un e-commerce con requisiti ACID stretti
  • D. Log aggregation con 50k insert/sec, query analitiche sporadiche
  • E. Startup fintech con analytics pesanti e time-series
Soluzione
A → PostgreSQL. PostGIS è standard de facto per dati geografici, nessuna alternativa FOSS comparabile.
B → MySQL. Ecosistema LAMP, WordPress è nato MySQL-first, molti plugin lo assumono.
C → PostgreSQL. ACID più forte di default, constraint più ricchi, maggiore serietà enterprise.
D → Nessuno dei due in modo "pulito". ClickHouse o TimescaleDB (estensione PostgreSQL) per time-series. Se devi scegliere tra i due: PostgreSQL + TimescaleDB.
E → PostgreSQL + TimescaleDB. Stessa motivazione: time-series + SQL + window functions ricche per analytics.

pg_hba.conf · riscrivi la configurazione

Parti da questo pg_hba.conf sbagliato e scrivi la versione corretta, motivando ogni modifica:

# TYPE   DATABASE   USER    ADDRESS      METHOD
local    all        all                  trust
host     all        all     0.0.0.0/0    md5
host     all        admin   0.0.0.0/0    scram-sha-256
Soluzione
Versione corretta: 
# TYPE     DATABASE   USER       ADDRESS           METHOD
local      all        postgres                     peer
host       all        all        127.0.0.1/32      scram-sha-256
hostssl    appdb      appuser    10.0.1.0/24       scram-sha-256
hostssl    all        admin      10.0.99.0/24      cert
# deny by default implicito
Motivazioni:
• Riga 1: trust → peer + limitare a user postgres. Evita che chiunque sul server diventi superuser DB.
• Riga 2: 0.0.0.0/0 md5 → 127.0.0.1/32 scram-sha-256 + hostssl per subnet app specifica. md5 è deprecato, 0.0.0.0/0 = mondo intero.
• Riga 3: admin da 0.0.0.0/0 → hostssl + cert da subnet bastion. Admin remoto deve essere protettissimo.
• Nessuna regola => deny implicito (PostgreSQL respinge se nessuna regola matcha).

TLS · connection string

Scrivi la connection string PostgreSQL (formato URI) per una produzione, assumendo:

  • DB su prod-db.azienda.local porta 5432
  • User reports password S3cur3!
  • Database analytics
  • CA aziendale in /etc/ssl/ca-azienda.crt
  • Richiesta massima sicurezza TLS
Soluzione
postgresql://reports:S3cur3%21@prod-db.azienda.local:5432/analytics?sslmode=verify-full&sslrootcert=/etc/ssl/ca-azienda.crt
Note:
• sslmode=verify-full: TLS obbligatorio + cert valido + hostname match. Standard produzione.
• sslrootcert: punta al cert della CA aziendale per la validazione.
• ! nella password è url-encoded come %21.
• Se la CA è nel truststore di sistema, sslrootcert può essere omesso.
• Alternativa: separa credenziali in file .pgpass (0600 chmod).

Encryption at rest · confronta i 4 layer

Elenca i 4 layer di encryption at rest e per ciascuno: (a) cosa protegge, (b) cosa non protegge, (c) quando sceglierlo.

Soluzione
Layer 1 · Filesystem (LUKS/BitLocker)
Protegge: furto fisico del disco spento. Non protegge: sistema acceso con disco montato (chiave in RAM). Quando: on-prem server + offline backup.

Layer 2 · Volume cloud (EBS/Azure Disk/GCP PD)
Protegge: furto snapshot, leak di backup. Non protegge: attaccante con credenziali IAM legittime. Quando: sempre in cloud, default on.

Layer 3 · Column-level (pgcrypto)
Protegge: insider con SELECT su tabella. Non protegge: chi ha chiave + logica app. Quando: dati ultra-sensibili (SSN, carte, documenti), con chiavi in HSM/KMS.

Layer 4 · TDE (Transparent Data Encryption)
Protegge: furto data file, trasparente all'app. Non protegge: da chi ha accesso al DB con privilegi. Quando: disponibile e compliance lo richiede. Non nativo in PG community.

Ripetizione rapida · flashcard

Risposte in 1 frase ciascuna:

  1. Che differenza c'è tra hypervisor Type 1 e Type 2?
  2. Cos'è un Linux namespace?
  3. Qual è il metodo auth deprecato di pg_hba.conf e cosa usare al suo posto?
  4. Cos'è il WAL e a cosa serve?
  5. Quale sslmode è lo standard produzione?
  6. Cosa distingue BASE da ACID in una frase?
  7. Quale extension PostgreSQL gestisce l'encryption at column-level?
Risposte
1. Type 1 gira sull'hardware (bare-metal); Type 2 gira sopra un host OS.
2. Meccanismo kernel Linux che dà a un processo una vista separata di una classe di risorse (PID, NET, MNT, IPC, UTS, USER, CGROUP).
3. md5 (deprecato perché vulnerabile a offline cracking); usare scram-sha-256.
4. Write-Ahead Log: il log di tutte le modifiche, scritto prima dei data file; serve per durability e crash recovery.
5. verify-full (TLS obbligatorio + CA valida + hostname match).
6. ACID privilegia consistency immediata, BASE privilegia availability ed eventual consistency.
7. pgcrypto (con funzioni PGP_SYM_ENCRYPT/DECRYPT).
