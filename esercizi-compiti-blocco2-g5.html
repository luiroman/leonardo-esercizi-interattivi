AAA in 3 frasi

Definisci Authentication, Authorization e Accounting in una frase ciascuno, con un esempio concreto.

Soluzione
Authentication: verifica chi sei (es. inserire password + codice OTP).
Authorization: determina cosa puoi fare (es. una volta loggato, puoi leggere file ma non cancellarli).
Accounting: registra cosa hai fatto (es. log "alice ha letto file X alle 14:32").

Fattori MFA · classifica

Per ognuno indica se è "qualcosa che sai", "qualcosa che hai", "qualcosa che sei", o nessuno dei tre:

  • A. PIN della carta di credito
  • B. Impronta digitale
  • C. SMS OTP
  • D. YubiKey
  • E. Riconoscimento facciale
  • F. Token TOTP su Authenticator
  • G. Cookie di sessione del browser
Soluzione
A → sai. B → sei. C → hai (il telefono). D → hai. E → sei. F → hai (il telefono con app). G → nessuno (è uno stato di sessione, non un fattore di autenticazione).
3

Vero MFA?

Per ognuno indica se è MFA "vero" (cioè 2 fattori di categorie diverse) o MFA "finto":

  • A. Password + PIN
  • B. Password + impronta
  • C. Password + SMS OTP
  • D. Impronta + riconoscimento facciale
  • E. YubiKey + PIN sulla YubiKey
Soluzione
A → FINTO. Entrambi "qualcosa che sai".
B → VERO. Sai + sei.
C → VERO. Sai + hai (anche se debole per intercettazione SMS).
D → FINTO. Entrambi "sei".
E → VERO. Hai (la chiave) + sai (il PIN). Pattern molto forte.
4

Perché FIDO2 è phishing-resistant

Spiega in 4-5 punti perché FIDO2/Passkey è resistente al phishing per design (non per attenzione dell'utente).

Soluzione
1. La chiave privata non lascia mai il dispositivo (TPM, secure enclave).
2. L'autenticazione è challenge-response crittografica, niente segreti condivisi da rubare.
3. Il browser verifica l'origine (dominio): se l'utente è su g00gle-login.com invece di google.com, la chiave non firma.
4. Quindi anche se l'utente clicca un link malevolo e inserisce il fattore biometrico, il sito fake non riceve nulla di utile.
5. Niente codici da copincollare, niente push da approvare distrattamente: l'attacco di phishing tradizionale non ha aggancio.
5

SAML, OAuth, OIDC · qual è quale

Per ognuno degli scenari indica quale protocollo è il più appropriato:

  • A. Login a Salesforce con account Microsoft 365 aziendale
  • B. Una mobile app vuole leggere i tuoi contatti Google con il tuo permesso
  • C. Login a Stack Overflow con il tuo account GitHub
  • D. SSO enterprise legacy verso un'app on-prem
Soluzione
A → SAML 2.0 (anche OIDC ormai supportato, ma SAML è lo standard storico per SSO enterprise SaaS).
B → OAuth 2.0 (delega di autorizzazione: l'app accede a risorse Google tue, non sostituisce la tua identità).
C → OpenID Connect (autenticazione: Stack Overflow vuole sapere chi sei, OIDC porta l'identità in JWT).
D → SAML 2.0 (lo standard storico delle integrazioni enterprise, ancora dominante in scenari legacy).

Authorization Code Flow · ricostruisci

Riordina questi step del flow OAuth 2.0 Authorization Code:

  • A. L'app scambia code + client_secret per access_token
  • B. L'utente clicca "Login con Google"
  • C. Google redirect all'app con authorization code
  • D. L'app effettua chiamate API con Bearer token
  • E. Google autentica l'utente (password + MFA)
  • F. Redirect dell'utente al Google authorization endpoint
Soluzione
B → F → E → C → A → D

RBAC vs ABAC · scegli il modello

Per ognuno scegli RBAC o ABAC e motiva:

  • A. Un'azienda con 2000 dipendenti suddivisi in 50 ruoli stabili
  • B. Un sistema sanitario dove l'accesso ai dati di un paziente dipende dal reparto + dal turno + dalla relazione medico-paziente
  • C. Una piccola startup di 15 persone con 4 categorie di utenti
  • D. Un sistema di gestione documenti con classificazione (pubblico, interno, riservato, segreto) e clearance utente
Soluzione
A → RBAC. Numeri grandi ma ruoli stabili: RBAC scala bene.
B → ABAC. Decisione dipende da molti attributi contestuali (reparto, turno, relazione, ora). RBAC esploderebbe.
C → RBAC. Piccoli numeri, semplicità prima di tutto.
D → ABAC (o ibrido). Confronto clearance utente vs classificazione risorsa è ABAC puro.

Least privilege · rivedi una policy

Una policy AWS IAM concede a uno sviluppatore: "Action": "s3:*", "Resource": "*". Lo sviluppatore in realtà deve solo leggere e scrivere oggetti in un bucket specifico per il suo progetto. Riscrivila in formato JSON applicando least privilege.

Soluzione
{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Action": [
      "s3:GetObject",
      "s3:PutObject",
      "s3:DeleteObject",
      "s3:ListBucket"
    ],
    "Resource": [
      "arn:aws:s3:::progetto-x",
      "arn:aws:s3:::progetto-x/*"
    ]
  }]
}
Note: ListBucket sul bucket, GetObject/PutObject/DeleteObject sugli oggetti.

Conditional Access · scrivi una policy

Scrivi (in pseudocodice if-then) una policy Conditional Access per: "Gli utenti del gruppo Finance, quando accedono a SAP da un dispositivo non aziendale, devono passare MFA con FIDO2 e la sessione dura massimo 1 ora".

Soluzione
IF user.group == "Finance"
  AND target.app == "SAP"
  AND device.compliance != "Corporate"
THEN
  require_mfa(method="FIDO2")
  session.max_lifetime = 1h
  session.persistent = false
ELSE IF user.group == "Finance"
  AND target.app == "SAP"
THEN
  require_mfa(method="any")
  session.max_lifetime = 8h

Anti-pattern · trovali

Identifica gli anti-pattern in questa configurazione IAM aziendale:

  • Un account "admin" condiviso tra 3 sysadmin con password in un Excel
  • Service account con password che non scade mai per integrazione SAP-Salesforce
  • Account root AWS protetto da sola password (no MFA)
  • Permessi temporanei concessi 18 mesi fa per un'urgenza, mai rivisti
  • Wildcard "Action": "*" nelle policy di tutti gli sviluppatori
Soluzione
1. Account condiviso → niente accountability. Soluzione: account individuali + ruolo "AdminRole" assumibile via STS, log su chi assume.
2. Service account permanente → rotazione obbligatoria, oppure migrazione a OAuth client credentials con token short-lived.
3. Root senza MFA → gravissimo. MFA hardware locked + alert su qualunque uso del root.
4. Permessi "temporanei" eterni → access review trimestrale, scadenze esplicite.
5. Wildcard sviluppatori → least privilege violato. Permission Boundary che limita lo scope, policy specifiche per sviluppatore/team.

CIS Benchmark · struttura di un controllo

Cerca online "CIS Benchmark Ubuntu Linux" e trova un controllo di esempio. Rispondi: quali sono le 6 sezioni standard di un controllo CIS? Cosa indica la differenza tra Level 1 e Level 2?

Cosa cercare
Le 6 sezioni: ID (numero gerarchico), Description (cosa fa il controllo), Rationale (perché serve), Audit (comando per verificare se sei OK), Remediation (comando per mettersi OK), References.
Level 1: essenziali, applicabili senza rompere funzionalità business. Level 2: defense-in-depth, richiedono analisi di impatto (es. disabilitare IPv6 può rompere applicazioni moderne).

Hardening Linux · i 3 file chiave

Senza cercare, rispondi: quali sono i 3 file fondamentali dell'account management su Linux? Per ognuno, cosa contiene e chi può leggerlo?

Soluzione
1. /etc/passwd — informazioni account (username, UID, GID, home, shell). Leggibile da tutti.
2. /etc/shadow — hash delle password, aging. Leggibile solo da root.
3. /etc/group — appartenenza ai gruppi. Leggibile da tutti.
Controllo critico: solo root deve avere UID 0. Verificare con awk -F: '$3==0' /etc/passwd.

Privilege escalation · sudo e GTFOBins

Vai su gtfobins.github.io. Cerca "find" e poi "vim". Per ciascuno: se un utente ha sudo NOPASSWD su quel comando, come può ottenere una shell root? Copia il comando.

Soluzione
find: sudo find . -exec /bin/sh \; -quit → shell root immediata.
vim: sudo vim -c ':!/bin/sh' → shell root via escape di vim.
Lezione: concedere NOPASSWD su comandi con funzionalità di shell escape è equivalente a dare accesso root completo. Nella Lezione 6 vedremo come auditare i sudoers per questi anti-pattern.

Hash password · identifica l'algoritmo

Questi sono hash estratti da /etc/shadow. Per ognuno, identifica l'algoritmo dal prefisso e indica se è ancora sicuro nel 2026:

  • A. $1$xyz$abcdef...
  • B. $6$rounds=5000$salt$hash...
  • C. $y$j9T$salt$hash...
  • D. $2b$12$salt.hash...
Soluzione
A → MD5 crypt ($1$). NON sicuro: una GPU moderna cracca 100 miliardi di hash/secondo. Da eliminare immediatamente.
B → SHA-512 crypt ($6$). Ancora accettabile ma superato. 5000 iterazioni default è il minimo.
C → yescrypt ($y$). Stato dell'arte (Ubuntu 22.04+). Memory-hard, resiste alle GPU.
D → bcrypt ($2b$). Sicuro con cost 12+. Standard per applicazioni web.

Installa Kali Linux

Installa Kali Linux su VirtualBox. Verifica che funzioni eseguendo questi comandi nel terminale Kali:

  • uname -a (kernel e architettura)
  • nmap --version (network scanner)
  • msfconsole --version (Metasploit)
  • ip addr show (interfacce di rete)

Fai uno screenshot di ciascun output. Configura la rete in modalità Host-Only (192.168.56.0/24) e verifica di poter pingare la tua VM Ubuntu se ne hai una.

Cosa devi vedere
1. Kernel Linux Kali (6.x tipicamente).
2. Nmap versione 7.94+ (preinstallato).
3. Metasploit Framework versione 6.x (preinstallato).
4. Interfaccia eth0 o eth1 con IP 192.168.56.x se Host-Only configurato.

Prerequisito critico: Kali funzionante è necessario per il lab pratico della Lezione 6. Se hai problemi con l'installazione, segnalalo al docente prima della lezione.
