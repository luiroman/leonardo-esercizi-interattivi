Categoria A · MongoDB injection
ESERCIZIO 1

Identifica l'operatore d'attacco

Un endpoint Express per il login fa:

app.post("/login", async (req,res) => {
  const u = await db.users.findOne({
    username: req.body.username,
    password: req.body.password
  })
  if (u) res.json({ok:true, token: signJWT(u)})
})

Un attaccante invia il payload JSON: {"username":{"$ne":null},"password":{"$ne":null}}

Domande: 1) cosa succede? 2) quale operatore è stato iniettato? 3) chi viene loggato?

Mostra soluzione
1) La query diventa findOne({username:{$ne:null}, password:{$ne:null}}) → ritorna il primo utente trovato che ha username e password non null. In MongoDB l'ordine di insertion è preservato → di solito è l'admin (creato per primo).
2) L'operatore $ne (not equal). Si attacca alla chiave del campo trasformandola in operatore.
3) Loggato come admin con il suo JWT firmato. Auth bypass completo.

Difesa minima: if (typeof req.body.username !== "string") return res.status(400). Una riga.
ESERCIZIO 2

Enumeration con $regex

Un endpoint "verifica username disponibile" per la registrazione fa:

app.get("/check", async (req,res) => {
  const exists = await db.users.findOne({username: req.query.u})
  res.json({available: !exists})
})

L'attaccante manda: ?u[$regex]=^a, poi ?u[$regex]=^ab, poi ?u[$regex]=^abc...

Domande: 1) cosa sta facendo? 2) quante richieste servono per estrarre uno username di 10 caratteri minuscoli? 3) come puoi bloccare l'attacco con un solo middleware?

Mostra soluzione
1) Enumeration carattere per carattere. Express con qs parser interpreta u[$regex]=^a come oggetto {u: {$regex: "^a"}}. La risposta available:false conferma che esiste uno username che inizia per "a", poi "ab", ecc.
2) Con 26 lettere e 10 posizioni: ~260 richieste nel caso peggiore (linear scan). In realtà molte meno (l'attaccante fa pruning).
3) express-mongo-sanitize: rimuove ogni chiave che inizia per $. app.use(mongoSanitize()). In alternativa: type check forte (typeof === "string") o validation schema (Zod).
ESERCIZIO 3

$where: trova il bug

Un endpoint per filtrare prodotti per range di prezzo:

app.get("/products", async (req,res) => {
  const {min, max} = req.query
  const products = await db.products.find({
    $where: `this.price >= ${min} && this.price <= ${max}`
  }).toArray()
  res.json(products)
})

Domande: 1) trova 2 payload che sfruttano il bug — uno per DoS e uno per leak. 2) qual è la difesa corretta?

Mostra soluzione
1) DoS: ?min=0&max=1; while(true){} → loop infinito JS server-side, blocca il thread MongoDB. Leak: ?min=0&max=1; return JSON.stringify(this) → ritorna l'intero documento anche se la query "logicamente" filtrava. Peggio: ?min=0&max=1; sleep(5000) per timing-based exfiltration.
2) Bandire $where. Riscrivere con operatori standard: db.products.find({price: {$gte: Number(min), $lte: Number(max)}}). Convertire min/max a numero (cast esplicito), validare con Zod (z.number().nonnegative()). Mai usare $where con input utente — è la regola.
Categoria B · Difesa MongoDB
ESERCIZIO 4

Costruisci i 4 layer

Hai un endpoint POST /signup che riceve {username, password, email, age}. Scrivi i 4 layer di difesa:

  • Layer 1: type check inline
  • Layer 2: schema Mongoose
  • Layer 3: validator Zod centralizzato (middleware)
  • Layer 4: configurazione globale di express-mongo-sanitize
Mostra soluzione
// Layer 1: type check inline (fail-fast)
if (typeof req.body.username !== "string") return res.status(400)
if (typeof req.body.email !== "string") return res.status(400)

// Layer 2: schema Mongoose
const userSchema = new Schema({
  username: {type: String, required:true, trim:true, minlength:3},
  password: {type: String, required:true, minlength:8},
  email: {type: String, required:true, match:/.+@.+/},
  age: {type: Number, min:13}
})

// Layer 3: Zod centralizzato
const signupSchema = z.object({
  username: z.string().min(3).max(50),
  password: z.string().min(8),
  email: z.string().email(),
  age: z.number().int().min(13)
})
router.post("/signup", validate(signupSchema), signupHandler)

// Layer 4: globale
app.use(mongoSanitize({onSanitize: ({req,key}) => logger.warn("sanitize",key)}))
I 4 layer sono indipendenti. Se uno fallisce, gli altri reggono. Non è ridondanza inutile: ogni layer copre attacchi diversi.
ESERCIZIO 5

Redis: trova l'injection

Una cache Redis viene usata così:

app.get("/profile/:id", async (req,res) => {
  const raw = await redis.sendCommand(
    `GET user:${req.params.id}`
  )
  res.send(raw || "not found")
})

L'attaccante chiama: GET /profile/abc%0D%0AFLUSHALL

Domande: 1) cosa succede sul server Redis? 2) come si corregge il codice?

Mostra soluzione
1) %0D%0A è \r\n URL-encoded. Il driver invia a Redis: GET user:abc\r\nFLUSHALL\r\n. RESP è line-based: Redis riceve due comandi e esegue FLUSHALL (cancella tutto il database). Disastro.
2) Usare l'API "by argument" del driver, che escapa i parametri: 
const raw = await redis.get(`user:${req.params.id}`)
// oppure più sicuro: validare l'id come numerico/uuid prima
if (!/^[a-f0-9-]+$/.test(req.params.id)) return res.status(400)
Aggiungi anche ACL Redis: ACL SETUSER appuser on >pwd ~user:* +get +set -flushall. Anche se l'injection passa, FLUSHALL viene rifiutato.
Categoria C · pgAudit
ESERCIZIO 6

Setup pgAudit per scenario

Sei DBA di un'app SaaS multi-tenant con tabella invoices (sensibile, tenant_id) e products (catalogo pubblico). 50.000 query/giorno. Devi soddisfare 3 requisiti:

  • Audit ogni GRANT/REVOKE e ogni CREATE/ALTER/DROP
  • Audit ogni operazione su invoices (read e write)
  • NON audit le SELECT su products (volume alto, contenuto pubblico)

Domanda: scrivi i comandi pgAudit per configurare questo setup minimale.

Mostra soluzione
-- 1. Session audit per ROLE e DDL (always-on, basso volume)
ALTER SYSTEM SET pgaudit.log = 'role, ddl';

-- 2. Object audit per invoices via ruolo dedicato
CREATE ROLE audit_role NOLOGIN NOINHERIT;
GRANT SELECT, INSERT, UPDATE, DELETE
  ON invoices TO audit_role;
ALTER SYSTEM SET pgaudit.role = 'audit_role';

-- 3. products NON è grant-ato a audit_role → SELECT su products non loggate

-- ricarica
SELECT pg_reload_conf();
Il vantaggio: il volume di log scende di 100x perché products (catalogo, tante SELECT) non genera record. Solo ROLE/DDL (rari) + tutto su invoices (sensibile) → segnale pulito per il SIEM.
ESERCIZIO 7

Parsa un log entry

Hai questo log entry pgAudit:

YYYY-MM-DD 14:23:11.987 UTC [9876] LOG:  AUDIT: SESSION,5,1,WRITE,UPDATE,
TABLE,public.users,UPDATE users SET role='admin' WHERE id=$1,<not logged>

Domande: 1) chi ha fatto cosa? 2) è un evento sospetto? perché? 3) come puoi ricostruire chi (utente DB) ha eseguito la query, dato questo entry?

Mostra soluzione
1) Qualcuno ha fatto un UPDATE su public.users impostando role='admin' per un utente con id non loggato (è $1, parametro). È stato un evento di tipo SESSION (logged perché pgaudit.log include 'write').
2) SÌ, sospetto. Una promotion a admin è un'azione critica: dovrebbe avvenire raramente, da specifici account, in specifiche finestre. Una regola SIEM su questo pattern (UPDATE users SET role) genera sempre un alert.
3) Il PID è [9876]. Per risalire al ruolo DB serve correlare con i log di connessione PostgreSQL (log_connections=on): trovi il record di apertura sessione con stesso PID e timestamp vicino → connection authorized: user=app_admin. In jsonlog c'è il campo user già nel record.
Categoria D · Row-Level Security
ESERCIZIO 8

Scrivi la policy RLS

Tabella documents(id, owner_id, title, body, is_public). Vuoi che ogni utente veda:

  • I propri documenti (owner_id = utente corrente)
  • I documenti pubblici (is_public = true)

L'app setta la sessione con SET app.user_id = '...'. Domanda: scrivi la policy RLS completa (USING + WITH CHECK).

Mostra soluzione
ALTER TABLE documents ENABLE ROW LEVEL SECURITY;

CREATE POLICY documents_visibility ON documents
  FOR ALL TO app_role
  USING (
    owner_id = current_setting('app.user_id')::int
    OR is_public = true
  )
  WITH CHECK (
    owner_id = current_setting('app.user_id')::int
  );
Nota la differenza intenzionale tra USING e WITH CHECK: USING permette di vedere documenti pubblici di altri, WITH CHECK non permette di creare documenti per conto di altri (owner_id deve essere te). Senza questo dettaglio, un utente potrebbe inserire INSERT INTO documents (owner_id, ...) VALUES (42, ...) creando un documento "appartenente" all'utente 42.
ESERCIZIO 9

FORCE RLS: la trappola

Hai abilitato RLS sulla tabella invoices con policy multi-tenant. La tua app si connette come ruolo app_owner (lo stesso che ha creato la tabella con CREATE TABLE). Apri psql come app_owner e fai SELECT * FROM invoices.

Domanda: 1) cosa vedi? 2) perché? 3) due modi per correggere il problema.

Mostra soluzione
1) Vedi TUTTE le righe di tutti i tenant. RLS è ignorato.
2) Il proprietario della tabella bypassa RLS by default in PostgreSQL. È un comportamento progettato per evitare lock-out del DBA, ma è la prima causa di RLS inefficace in produzione.
3) Due soluzioni:
-- a. FORCE RLS sulla tabella
ALTER TABLE invoices FORCE ROW LEVEL SECURITY;

-- b. Separazione ruoli (preferita)
CREATE ROLE app_role;  -- ruolo applicativo, NON proprietario
GRANT SELECT,INSERT,UPDATE,DELETE ON invoices TO app_role;
-- l'app si connette come app_role, mai come app_owner
La soluzione (b) è preferita architetturalmente: app_owner fa solo migrations/DDL. FORCE RLS è la safety net.
Categoria E · Detection e SIEM
ESERCIZIO 10

Code review live · trova le 4 issue

Trova i 4 problemi di security nel codice qui sotto. Hint: SQLi, type, multi-tenant, ruoli DB.

// === API SaaS multi-tenant per fatturazione ===
// connection: postgres://app_owner:secret@db/saas (super)
router.get("/invoices", async (req, res) => {
  const { search, sort } = req.query
  const sql = `SELECT * FROM invoices
              WHERE customer LIKE '%${search}%'
              ORDER BY ${sort}`
  const rows = await pg.query(sql)
  res.json(rows)
})
router.post("/invoices", async (req, res) => {
  await pg.query(
    "INSERT INTO invoices(amount, customer) VALUES($1,$2)",
    [req.body.amount, req.body.customer])
  res.json({ ok: true })
})
Mostra soluzione
Issue 1 · SQL injection classico: search e sort sono concatenati nella stringa. Payload: ?search='; DROP TABLE invoices--. Fix: prepared statement per search; per sort (che non si parametrizza) usa una whitelist di colonne ammesse.

Issue 2 · Multi-tenant assente: l'INSERT non setta tenant_id. Senza RLS, vedi gli invoices di tutti. Senza tenant_id nell'INSERT, crei record orfani. Fix: ENABLE RLS + policy su tenant_id = current_setting('app.tenant_id') + SET app.tenant_id per ogni request.

Issue 3 · Ruolo DB sbagliato: la connessione usa app_owner (super, proprietario). RLS sarebbe bypassato anche se attivato. Fix: ruolo app_role non-proprietario, con grant minimi.

Issue 4 · Type check assente sull'INSERT: req.body.amount potrebbe essere stringa, oggetto, array. Anche con prepared statement, se il driver fa cast implicito, valori inattesi entrano nel DB. Fix: Zod validation prima del query (amount: z.number().positive()).

Bonus: pgAudit non è abilitato — non c'è audit trail forense.
